# ADR-0016. Загрузка файлов через свой сервер

**Статус:** принято · **Дата:** 2026-08 · **Шаг:** 5.6

## Контекст

К шагу 5.6 редактор разбора умел всё, кроме главного для куратора:
положить табы. Таблицы `media_assets` и `attachments` существовали
с шага 5.1, страница песни умела показывать материалы и выдавать по ним
подписанные ссылки (ADR-0013), но заполнить их было нечем — единственная
загрузка в проекте, фотография участника, написана под одну конкретную
задачу.

Вводные, определившие решение:

- три куратора, файлы — PDF до 25 МБ, партитуры Guitar Pro, минусовки;
- видео в наше хранилище не попадает и не должно (ADR-0014);
- сервер — один VPS на четыре гигабайта памяти;
- хранилище — S3-совместимое у российского поставщика.

## Рассмотренные варианты

### 1. Подписанная ссылка на загрузку (прямо в хранилище)

Браузер получает от нас временный адрес и отправляет файл в хранилище,
минуя приложение. Так написано в PRD v0.1 §8.2 и так делают при больших
объёмах.

**Против:**

- требует настройки правил CORS на стороне хранилища; у российских
  поставщиков это нередко обращение в поддержку, а не переключатель;
- локальная разработка без облака перестаёт работать — нужен второй,
  ненастоящий путь загрузки;
- появляется двухшаговый обмен «запросить ссылку → подтвердить загрузку»
  и вместе с ним файлы, о которых база не знает;
- размер и содержимое проверяются постфактум.

### 2. Серверное действие с `FormData`

Тот же путь, что у фотографии профиля.

**Против:** у серверных действий есть предел размера тела запроса, и
поднять его до пятидесяти мегабайт значит поднять его для каждой формы
в проекте. Прогресса отправки они не дают вовсе — а куратор, отправивший
двадцать мегабайт без индикатора, нажимает кнопку второй раз и получает
два одинаковых таба.

### 3. Обработчик адреса, байты через наш сервер ✅

`POST /api/media/upload`, тело — сами байты, имя файла — заголовком.
В браузере отправка идёт через `XMLHttpRequest` ради прогресса.

## Решение

Выбран вариант 3.

**Цена — трафик через наш сервер.** При переносе архива это около
гигабайта разово, дальше несколько файлов в неделю. На фоне сотен
гигабайт видеотрафика, идущего мимо нас через сеть доставки, это шум.

**Порог пересмотра.** Возвращаемся к варианту 1, если появится
загрузка видео из браузера или файлы тяжелее ста мегабайт. Договор
`StorageProvider` менять при этом не придётся — добавится один метод.

### Что следует из решения

**Вид файла определяется по расширению, а не по типу от браузера.**
У Guitar Pro нет зарегистрированного типа содержимого: браузер
присылает `application/octet-stream` и для партитуры, и для чего угодно
ещё. Побочная выгода важнее главной: тип, присланный браузером, задаёт
тот, кто загружает, и файл, объявленный картинкой, но содержащий
разметку со скриптом, выполнился бы в браузере того, кто его откроет.
Тип назначаем мы, по белому списку расширений.

**Белый список, а не чёрный.** «Всё, кроме опасного» — способ однажды
забыть очередное расширение.

**Пределы разные по видам.** Guitar Pro 5 МБ, PDF 25 МБ, минусовка
50 МБ, картинка 10 МБ. Один предел на всё либо не пускает партитуру,
либо пускает в закрытое хранилище часовое видео.

**Тело читается кусками с обрывом при превышении.** Заголовок с длиной
проверяется первым, но доверия ему нет: без пообъёмного счёта достаточно
объявить один размер и отправить другой, чтобы исчерпать память сервера.

**Порядок записи: строка в базе → байты в хранилище → отметка
о готовности → привязка.** Так ключ хранилища известен базе до того, как
файл появится, и оборванная загрузка оставляет след в состоянии
«загружается», по которому её найдёт ночная уборка. Обратный порядок
оставлял бы в хранилище файлы, о которых никто не помнит, — а
перечислять содержимое хранилища мы не умеем и уметь не хотим: этот
метод в договоре `StorageProvider` отсутствует намеренно.

**Файл удаляется только вместе с последней привязкой.** Один файл может
быть привязан к нескольким объектам: минусовка нужна и на странице
песни, и в уроке, который её разбирает.

**Права проверяются в слое приложения, а не в модуле медиа.** Право
положить таб к разбору — это право править ЭТОТ разбор, со всей его
областью «только свой контент». Знает об этом модуль разборов, а модуль
медиа знает про хранилище и о разборах не подозревает. Свести их можно
только в слое приложения — реестр в `src/app/_lib/attachment-access.ts`.

**`media.upload` требуется для добавления, но не для правки.**
Переименовать, переставить и убрать материал со своего черновика куратор
может всегда — это часть права `songs.edit`. Право `media.delete`
из PRD v0.3 относится к общей медиатеке (Этап 9), а не к материалам
собственного разбора.

## Последствия

**Хорошие**

- Загрузка работает локально без облачной учётной записи.
- Прогресс виден, повторных нажатий нет.
- Один путь кода на разработку и на боевой сервер.
- Компонент `FileDrop` и обработчик не знают о разборах: уроки, эфиры
  и новости получат загрузку добавлением двух строк в реестр.

**Плохие**

- Байты проходят через приложение: при загрузке файла на 50 МБ он
  целиком оказывается в памяти процесса. При трёх кураторах это
  приемлемо, при тридцати — нет.
- На посреднике перед приложением нужно разрешить тело запроса
  до 50 МБ (см. OPERATIONS.md §3).
- Обложек разбора этот механизм не касается: от картинок-обложек
  проект отказался осознанно (см. `src/ui/patterns/song-cover.tsx`).

## Отменяет

Пункт PRD v0.1 §8.2 «загрузка видео напрямую в видеохостинг из браузера
(presigned upload)» в части файлов. Для видео решение не менялось:
ролик кладётся в панели хостинга, в платформу вводится его
идентификатор (ADR-0014).
