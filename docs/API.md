# Серверный слой

Правила, по которым код обращается к серверу. Единые для всего проекта:
одинаковые вещи должны выглядеть одинаково, иначе через год половина
обработчиков окажется без проверки прав.

---

## Что выбрать: действие или адрес

| Случай                                                      | Что использовать                                         |
| ----------------------------------------------------------- | -------------------------------------------------------- |
| Пользователь что-то сохраняет, публикует, удаляет           | **Действие сервера** (`defineAction`)                    |
| Обращается внешняя система: Telegram, система развёртывания | **Обработчик адреса** (`route.ts`)                       |
| Отдаём файл или подписанную ссылку                          | **Обработчик адреса**                                    |
| Участник загружает небольшой файл (фотография)              | **Действие сервера**, файл внутри `FormData`             |
| Участник загружает крупный файл (видео)                     | **Прямая загрузка в хранилище** по временной ссылке      |
| Читаем данные для отрисовки страницы                        | **Ничего:** серверный компонент вызывает сервис напрямую |

Отдельного слоя API между страницами и базой нет — страницы выполняются
на сервере и обращаются к сервисам модулей.

## Действие сервера

```ts
'use server'

import { z } from 'zod'

import { requirePermission } from '@/modules/access'
import { defineAction } from '@/shared/server'

const input = z.object({
  songId: z.string().uuid(),
  title: z.string().min(1, 'Укажите название'),
})

export const renameSong = defineAction({
  name: 'songs.rename',
  input,
  handler: async ({ songId, title }) => {
    const song = await findSongById(songId)
    if (!song) throw errors.notFound('Разбор не найден')

    // Область действия «только свой контент» проверяется здесь:
    // для неё нужен сам объект, а он загружается только сейчас
    await requirePermission(await getCurrentUserId(), 'songs.edit', song.curatorId)

    return updateSongTitle(songId, title)
  },
})
```

`defineAction` берёт на себя проверку входных данных, обработку ошибок,
запись в журнал и отправку настоящих поломок в Sentry. Это собрано в одном
месте именно потому, что иначе пришлось бы повторять в каждом обработчике
и рано или поздно где-нибудь забыть.

---

## Формат ответа

Один на весь проект:

```ts
// успех
{ ok: true, data: { … } }

// ошибка
{
  ok: false,
  code: 'validation_failed',
  message: 'Проверьте заполненные поля',
  fields: { title: 'Укажите название' },   // если ошибка в форме
  incidentId: '…'                          // если это настоящая поломка
}
```

Благодаря единому формату интерфейс всегда знает, что показать:
сообщение целиком или подсветку конкретного поля.

---

## Коды ошибок

| Код                     | Когда                                           | HTTP |
| ----------------------- | ----------------------------------------------- | :--: |
| `unauthorized`          | Нет сессии или истекла                          | 401  |
| `forbidden`             | Прав не хватает                                 | 403  |
| `subscription_required` | Нет активной подписки                           | 402  |
| `not_found`             | Объект не найден или скрыт                      | 404  |
| `validation_failed`     | Данные формы не прошли проверку                 | 422  |
| `conflict`              | Действие невозможно: публикация пустого разбора | 409  |
| `rate_limited`          | Слишком много попыток                           | 429  |
| `upstream_unavailable`  | Недоступен видеохостинг, Telegram, хранилище    | 503  |
| `internal`              | Настоящая поломка                               | 500  |

Первые семь — ожидаемые ситуации: короткая строка в журнале, без Sentry.
Последние две — поломки: стек в журнале и оповещение.

Создавать ошибки через готовые помощники:

```ts
throw errors.notFound('Разбор не найден')
throw errors.forbidden()
throw errors.validation({ title: 'Укажите название' })
throw errors.conflict('Нельзя опубликовать разбор без частей')
```

## Проверка прав

**Правило без исключений:** любое действие, меняющее данные или отдающее
закрытое содержимое, начинается с `requirePermission`.

```ts
// право без привязки к объекту
await requirePermission(userId, 'songs.create')

// право с областью действия: третий аргумент — владелец объекта
await requirePermission(userId, 'songs.edit', song.curatorId)
```

Если у права область `own`, а владелец объекта — другой человек, вызов
выбросит `forbidden`.

Скрытая в интерфейсе кнопка — это удобство, а не защита.

## Ограничение частоты

Для чувствительных действий:

```ts
enforceRateLimit({
  action: 'login',
  subject: ipHash,
  limit: 5,
  windowSeconds: 300,
})
```

Счётчики в памяти процесса. При перезапуске обнуляются — это осознанное
ограничение, см. комментарий в `shared/security/rate-limit.ts`.

## Работа с базой

Запросы пишутся **только** в `repository.ts` внутри модуля.
Компоненты и действия обращаются к данным через сервисы.

Когда запросы разбросаны по проекту, изменение одной таблицы превращается
в поиск по сотне файлов, а проверки прав неизбежно где-нибудь забываются.

---

## Служебные адреса

| Адрес                          | Назначение                                                        |
| ------------------------------ | ----------------------------------------------------------------- |
| `GET /api/health`              | Проверка живости: 200, если приложение и база отвечают, иначе 503 |
| `GET /api/media/[id]/download` | Скачивание материала: проверка подписки → 302 на хранилище        |
| `POST /api/media/upload`       | Загрузка материала куратором: байты в теле запроса                |
| `POST /api/video/authorize`    | Разрешение на воспроизведение. Сюда обращается видеохостинг       |

Появятся дальше:

| Адрес                             | Когда   |
| --------------------------------- | ------- |
| `GET /api/auth/telegram/callback` | Этап 2  |
| `POST /api/telegram/webhook`      | Этап 2  |
| `GET /api/media/[id]/playback`    | Шаг 5.4 |

### Скачивание материала

Обработчик адреса, а не действие сервера: скачивание — это переход,
и обычная ссылка работает без JavaScript, открывается в новой вкладке
и правильно объявляется экранным диктором.

```
GET /api/media/[id]/download
  → есть ли сессия            нет → на вход, с возвратом сюда
  → можно ли скачивать вид    видео и внешние табы — никогда
  → обработан ли файл         нет → понятное объяснение
  → оплачена ли подписка      нет → на страницу продления
  → подписанная ссылка на 15 минут → 302, Cache-Control: no-store
```

Файл через наш сервер не проходит. Ключ объекта в хранилище наружу
не уходит: в разметке страницы лежит идентификатор материала.
Подробности — [ADR-0013](adr/0013-song-page-and-file-delivery.md).

### Загрузка материала

Второй и последний случай, когда действия сервера не хватает. Причины
две: у действий есть предел размера тела запроса, и они не сообщают
о прогрессе отправки. Куратор, отправивший двадцать мегабайт без
индикатора, нажимает кнопку второй раз и получает два одинаковых таба.

```
POST /api/media/upload?entityType=song|arrangement&entityId=<uuid>
  заголовок x-file-name: имя файла, закодированное encodeURIComponent
  тело: сами байты, без формы

  → есть ли сессия                нет → 401
  → не слишком ли часто           60 загрузок за 10 минут на человека
  → к чему прикладываем           вид объекта из белого списка
  → можно ли ему                  media.upload + право править ЭТОТ объект
  → что за файл                   по расширению, ДО чтения тела
  → чтение потока                 обрыв при превышении предела вида файла
  → строка в базе → байты в хранилище → готово → привязка
  → ActionResult, как у действий
```

Отвечает тем же форматом, что действия сервера: интерфейс разбирает
успех и ошибку одинаково, независимо от того, каким путём пришёл ответ.

Всё, что делается с уже загруженным, — подпись, порядок, разрешение
скачивать, удаление — остаётся обычными действиями. Через обработчик
идут только байты. Подробности — [ADR-0016](adr/0016-file-uploads.md).

### Разрешение на воспроизведение

**Единственный обработчик, который вызываем не мы, а нас.** При каждой
попытке воспроизведения видеохостинг спрашивает, можно ли этому человеку
смотреть этот ролик. Без ответа `200` ключ расшифровки не выдаётся,
и зашифрованное видео не проигрывается вовсе.

```
POST /api/video/authorize        { id, token, ip, user_agent }
  → тот ли, за кого себя выдаёт      логин и пароль в заголовке
  → подпись ключа верна?             иначе 403
  → ключ выдан на ЭТОТ ролик?        иначе 403
  → подписка активна ПРЯМО СЕЙЧАС?   иначе 403
  → 200
```

**Здесь нет политики fail-open,** в отличие от всей остальной платформы:
при любом сомнении — отказ. Fail-open существует, чтобы сбой у посредника
не наказывал участника; здесь же сомнение означает незнание, кто перед нами.

Ответ бессодержателен намеренно: причина отказа остаётся в журнале.
Подсказка «ключ истёк» против «ключ от другого ролика» помогает только
тому, кто подбирает.

Адрес обработчика прописывается в хостинге один раз: `pnpm kinescope:setup`.
Обращения приходят **из интернета** — с localhost проверить нельзя.
Подробности — [ADR-0014](adr/0014-video-playback-authorization.md).

## Чего не делать

- **Не проверять права в middleware.** Он не является границей безопасности.
- **Не возвращать текст ошибки базы наружу.** «duplicate key value violates
  unique constraint» не поможет гитаристу и раскрывает устройство системы.
- **Не писать запросы к базе в компонентах.** Только через сервисы модуля.
- **Не создавать обработчик адреса там, где хватит действия сервера.**
  Действие типизировано от формы до базы, обработчик адреса — нет.
