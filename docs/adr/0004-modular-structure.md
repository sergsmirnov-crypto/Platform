# ADR-0004. Деление кода по модулям, а не по слоям

**Статус:** принято · **Дата:** 2026-08

## Контекст

Есть два способа разложить код: по техническим слоям
(`controllers/`, `services/`, `models/`) и по предметным модулям
(`songs/`, `streams/`, `access/`).

Требование продукта: после каждого этапа должно быть возможно изменить,
заменить или удалить часть функциональности с минимальными правками.
Проект через год может перейти к другой команде.

## Решение

Деление по модулям. Каждый модуль в `src/modules/<имя>` устроен одинаково:

```
schema.ts       описание таблиц
types.ts        типы и схемы валидации
repository.ts   запросы к БД — единственное место, где есть SQL
service.ts      бизнес-правила
permissions.ts  какие права нужны для каких действий
actions.ts      точки входа с фронтенда
strings.ts      тексты интерфейса
components/     компоненты модуля
index.ts        публичный API модуля
```

Правило зависимостей: `app → modules → shared`. Только вниз.
Модули не обращаются к внутренностям друг друга — только через `index.ts`.

**Правило проверяется автоматически** правилом `no-restricted-imports`
в `eslint.config.mjs`. Нарушение — ошибка сборки, а не замечание в code review.

## Обоснование

При делении по слоям одна функция размазана по пяти папкам: чтобы понять,
как работают разборы, нужно открыть пять мест. При делении по модулям всё,
что относится к разборам, лежит в одной папке.

Практическое следствие: «удалить функциональность» превращается в «удалить папку
и одну строку из меню», а не в археологию по всему проекту.

## Последствия

- Немного больше файлов на старте: даже маленький модуль имеет полную структуру.
- Общий код нужно осознанно выносить в `shared/`, иначе он расползётся копиями.
- Тексты интерфейса лежат в `strings.ts` рядом с модулем. Это заготовка
  под возможную английскую версию без установки библиотеки локализации.
