# ADR-0007. Фиксация версий TypeScript и ESLint

**Статус:** принято · **Дата:** 2026-08

## Контекст

При настройке проекта последние версии инструментов оказались несовместимы
между собой:

- **TypeScript 7.0** — новый компилятор, переписанный на Go ради скорости.
  `typescript-eslint` его не поддерживает и отказывается запускаться.
- **ESLint 10** — изменён внутренний интерфейс работы с областями видимости.
  `typescript-eslint` 8.x падает с ошибкой `scopeManager.addGlobals is not a function`,
  несмотря на заявленную в описании пакета совместимость.

## Решение

- TypeScript зафиксирован на **6.x**
- ESLint зафиксирован на **9.x**
- Next.js 16 и React 19 — последние версии, они работают без ограничений

## Обоснование

Линтер с доступом к типам — часть контура качества: именно он проверяет
архитектурные границы между слоями (см. ADR-0004) и ловит целый класс ошибок
до запуска кода. Отказаться от него ради более быстрого компилятора — плохой
обмен: выигрыш в секундах сборки против потери проверок, которые защищают
проект годами.

Отдельно стоит отметить: заявленная в `peerDependencies` совместимость
не означает работоспособность. Версии проверены запуском, а не по документации.

## Условия пересмотра

Обновляемся, когда `typescript-eslint` выпустит стабильную версию
с поддержкой TypeScript 7 и ESLint 10 (отслеживается в issue #10940
репозитория typescript-eslint). Порядок: сначала ESLint, затем TypeScript,
каждое обновление — отдельным коммитом с прогоном `pnpm check`.

## Последствия

- Проект не использует ускоренный компилятор TypeScript. На нашем объёме кода
  разница в скорости пока незаметна.
- Точные рабочие версии зафиксированы в `pnpm-lock.yaml`, который коммитится
  в репозиторий. У любого разработчика и в CI устанавливается ровно то же самое.
