# История изменений

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
Проект пока не выпущен, поэтому версии не нумеруются — записи ведутся по шагам разработки.

## [Не выпущено]

### Новости клуба как главная ветка чата и реакции (ADR-0032)

**Добавлено**

- **Реакции на посты** — фирменные эмодзи из Figma, одна реакция
  от человека. Под постом — панель, в ленте — сводка. Новый модуль
  `reactions`, иконки `ReactionIcon` в дизайн-системе.
- **Новости клуба на главной**: закреплённый анонс и свежие посты.
- **Вид поста**: новость, дайджест, анонс, поздравление — метка
  и фильтр в ленте.
- **Закрепление со сроком**: «до какого дня», по Москве.
- **«Обсудить в чате»** под постом: ссылка на сообщение в Telegram
  или первый чат из настроек.
- Демо-данные: по посту каждого вида.

**Изменено**

- Снят временный блок «Платформа наполняется».

**Исправлено**

- В репозитории не было папки `public`, а `Dockerfile` её копирует —
  сборка образа на сервере падала. Добавлен `public/robots.txt`.
- Повторяющиеся ключи у карточек чатов Telegram.

### Подписка — Toolsy как второй источник оплаты

**Добавлено**

- **Уведомления Toolsy** (`POST /api/toolsy/webhook`): о создании,
  продлении и отмене подписки Toolsy сообщает напрямую, в обход
  Telegram. Подлинность — по подписи `toolsy-signature` (ADR-0031).
- **Ночная сверка с Toolsy**: находит и оплативших, о которых уведомление
  не дошло, и отменивших.
- **Проверка Toolsy при подключении Telegram**: оплативший получает
  доступ сразу, даже если Telegram недоступен.
- Таблица `toolsy_subscriptions`, значение `toolsy` у источника доступа
  (миграция `0018`). Настройки `TOOLSY_API_KEY`, `TOOLSY_WEBHOOK_SECRET`,
  `TOOLSY_PRODUCT_ID`, `TOOLSY_API_BASE_URL`.

**Изменено**

- **Доступ открыт, если оплату подтверждает хотя бы один источник** —
  членство в чате или подписка в Toolsy. Выход из чата больше не
  отнимает доступ у того, чья подписка в Toolsy действует.
- События автомата подписки: `joined_channel` / `left_channel` →
  `paid_confirmed` / `paid_lost`. Внутреннее изменение модуля.
- Сверка чата считает расхождением только реальное изменение членства,
  а не любое «нет в чате».

Без ключей Toolsy платформа работает как раньше, только по чату.

### Инфраструктура

**Изменено**

- **Код хранится в репозитории обычными файлами, а не zip-архивами.**
  Прежнее состояние с архивами сохранено в ветке `archives-zip`.

**Исправлено**

- **Сборка без базы данных.** Подключение к базе создаётся при загрузке
  кода, поэтому без `DATABASE_URL` падала и проверка на GitHub, и сборка
  образа в `Dockerfile` — то есть первое развёртывание. Обе теперь
  получают адрес-заглушку: работающая база сборке не нужна.

### Этап 2 — Авторизация

#### 2.7 — Вход по коду на почту и подключение Telegram

**Изменено**

- **Основной вход — по коду на почту.** Пароля нет: почта → шесть цифр
  из письма → внутрь. Первый вход и есть регистрация.
- **Telegram подключается один раз через бота** — по ссылке
  `t.me/бот?start=ключ`, нажатием «Старт». Нужен только для подтверждения
  подписки, входа он больше не касается.
- **Льготный период после выхода из канала — 1 день вместо 7.**
- **Владелец определяется по почте** (`OWNER_EMAIL` вместо
  `OWNER_TELEGRAM_ID`). `pnpm role:grant` принимает почту или Telegram ID.
- Платные разделы ведут человека без Telegram на экран подключения,
  а не на «подписка закончилась».
- Оферта и политика данных — редакция 2: срок льготного периода
  словами, почта и сервис отправки писем в перечне данных.

**Добавлено**

- **`shared/email/`** — отправка писем: `console` для разработки, `smtp`
  для боевого сервера.
- Таблицы `email_login_codes`, `telegram_link_tokens`, уникальный индекс
  «один способ входа каждого вида на человека». Миграция
  `0017_email_login_and_telegram_link.sql`.
- Экран `/auth/connect` — подключение Telegram с автоматической проверкой.
- Карточка «Вход» в настройках: почта и состояние Telegram.
- Вебхук понимает команду «Старт» с ключом и сразу проверяет членство
  в канале.
- `TELEGRAM_API_BASE_URL` — адрес Bot API в настройках, для промежуточного
  сервера за рубежом.
- `shared/db/errors.ts` — распознавание гонки на уникальности.
- 61 новый тест; сквозная проверка на живой базе (27 сценариев).

**Решения**

- **Код, а не пароль и не ссылка в письме.** Пароль забывают и раздают;
  ссылка на телефоне открывается во встроенном браузере почты.
- **Код в теме письма** — его видно на экране блокировки.
- **Попытка засчитывается до сравнения**, код гасится атомарно,
  действует только последний код адреса.
- **Чужой Telegram не переносится молча** — бот объясняет, что делать.
- **Сначала Telegram, потом знакомство**, но только для тех, у кого нет
  доступа: владельца и ручные выдачи подключение не держит.
- **Вход через виджет Telegram выключен, а не удалён** —
  `TELEGRAM_LOGIN_ENABLED=true` возвращает его вместе с адресом
  `/auth/telegram`.

**Ограничения**

- Сменить почту или подключённый Telegram сам участник пока не может —
  через кураторов.
- Нужна настройка почты на домене (SPF, DKIM), иначе письма в спаме.
- Участник без доступа к Telegram вовсе не оплатит подписку через
  Tribute — это ограничение платёжной схемы, а не входа.

Подробности решений — [ADR-0030](adr/0030-email-login-and-telegram-linking.md).

### Этап 10 — Дополнительные возможности

#### 10.7 — Новости клуба

**Добавлено**

- **Модуль `news`**: таблица `news_posts`, запросы, сервис, тексты.
- **Лента `/app/club/news`** и страница новости вместо заглушек.
- **Управление `/app/manage/news`**: список, создание, редактор,
  публикация, удаление.
- **`shared/blocks/`** — блочный формат содержимого переехал из модуля
  курса; отрисовщик и редактор блоков стали общими компонентами.
- **Пятая группа в общем поиске** и **пятый тип уведомлений**
  («Новости клуба», доставка вечерней сводкой).
- Четыре новых действия в журнале, миграция `0015_news_posts.sql`.

**Решения**

- **Формат содержимого — общий с уроками.** Свой формат означал бы
  второй редактор, второй отрисовщик и два разных набора возможностей
  у людей, пишущих в одном и том же клубе.
- **Новости — не лента и не блог.** Ни реакций, ни комментариев:
  живое общение уже в Telegram (v0.1, приложение А).
- **Выжимка отдельным полем**, а не первым абзацем: первый абзац часто
  начинается с «Друзья, привет!».
- **Адрес строится один раз** и не меняется при правке заголовка —
  ссылка уже разослана в Telegram.
- **Дата публикации ставится один раз.** Снятая и возвращённая новость
  не прыгает наверх ленты и не приходит людям вторым уведомлением.
- **Отдельного права «видеть черновики новостей» нет.** Раздел ведут
  те же три человека; признак берётся у `news.edit`.
- **Область действия прав не бывает `own`:** новость пишут от лица
  клуба, делить их на «мои» и «чужие» значило бы делить сам клуб.
- **Удаление насовсем, без архива.** У новости не связано ни прогресса,
  ни заметок; заголовок остаётся в журнале.

**Ограничения**

- **Постраничной навигации нет** — в ленте тридцать последних новостей,
  остальное находится поиском.
- **Обложек у новостей нет.** Картинку можно поставить блоком внутри
  текста; отдельное поле обложки потребовало бы решать, как она
  выглядит в списке, ради раздела, который читают раз в неделю.
- **Черновик новости доступен по прямой ссылке** тем, у кого есть
  `news.edit` — как и черновики в остальных разделах.

Подробности решений — [ADR-0029](adr/0029-news.md).

### Этап 10 — Дополнительные возможности

#### 10.6 — Табы рядом с видео

**Добавлено**

- **Панель табов в режиме репетиции**: PDF и картинки показываются
  рядом с записью, переключение между несколькими файлами.
- **Обработчик `/api/media/[id]/view`** — тот же файл, что и скачивание,
  но с заголовком «показать» вместо «сохранить».
- **Признак `inline`** у подписи ссылки в хранилище.
- **Правило `canViewInline`** в модуле медиа, с тестами.

**Решения**

- **Опасение про подписанные ссылки не подтвердилось.** Рамка
  обращается к нашему обработчику, а не к хранилищу напрямую, поэтому
  подпись выдаётся заново при каждой загрузке, а уже открытый PDF живёт
  в памяти браузера.
- **Отдельный адрес показа, а не признак у скачивания.** Показать можно
  PDF и картинку, скачать — ещё и Guitar Pro с минусовкой; общий признак
  однажды передали бы для Guitar Pro и получили пустой экран.
- **Без сессии — отказ, а не перенаправление на вход:** страница входа,
  отрисованная внутри рамки, выглядит как поломка вёрстки.
- **На телефоне — отдельная вкладка, а не ужатая рамка.** Табы это
  мелкие цифры на шести линейках; встроенный просмотрщик даёт
  разведение пальцами, поворот и полный экран.
- **Рамка не отрисовывается, а не прячется стилями** — скрытая рамка
  всё равно загрузила бы файл.
- **Правая колонка появляется только при наличии табов.** Половина
  разборов табов не имеет вовсе (v0.2 §3.2).

**Ограничения**

- **Guitar Pro не показывается** — только скачивается. Отрисовщик
  нотного стана в браузере это отдельный продукт.
- **Синхронного скролла табов за видео нет.** Он требует разметки
  тактов по времени для каждого разбора; PDF такой разметки не несёт.
- **Обычная страница разбора не изменилась** — там материалы
  по-прежнему скачиваются.

Подробности решений — [ADR-0028](adr/0028-inline-tabs.md).

### Этап 10 — Дополнительные возможности

#### 10.5 — Режим репетиции

**Добавлено**

- **Страница `/app/learn/songs/[slug]/rehearse`** — полноэкранный режим
  для занятия с гитарой в руках.
- **A–B зацикливание** отрезка: одна кнопка ставит начало и конец.
- **Зацикливание части разбора** одним нажатием, без расстановки отметок.
- **Метроном**: темп из карточки песни, доли в такте 2/3/4/6, акцент
  на сильную долю.
- **Крупные кнопки скорости** (0,5× — 1,25×) вместо мелких на обычной
  странице.
- **Экран не гаснет**, пока режим открыт; разрешение запрашивается
  заново после сворачивания вкладки.
- **`shared/playback/`** — чистые правила зацикливания и метронома,
  26 тестов.
- Кнопка входа на странице разбора, маршрут `routes.app.learn.rehearse`.

**Решения**

- **Отдельный адрес, а не разворачивание плеера.** Режим открывается
  по ссылке, переживает перезагрузку, закрывается кнопкой «назад» —
  и не тянет за собой описание, похожие разборы и заметки.
- **Zustand не понадобился.** Архитектурный документ предполагал его
  именно для этого экрана; на практике всё состояние не покидает одно
  поддерево. Документ поправлен: несбывшееся предсказание стоит
  отменять, а не исполнять ради консистентности.
- **Зацикливание — в событии времени плеера, а не опросом по таймеру.**
  Шаг опроса добавлялся бы к задержке, и петля каждый раз заезжала бы
  за край на разную величину. Возврат срабатывает за четверть секунды
  до конца — ровно на шаг событий плеера.
- **Прыжок назад делается до отметки о просмотре**, иначе зацикливание
  писало бы в прогресс откат каждые несколько секунд.
- **Метроном планирует удары по часам звуковой подсистемы.**
  `setInterval` даёт слышимо кривой счёт; метроном, который плывёт,
  хуже отсутствующего — под него подстраиваются.
- **Одна кнопка вместо двух полей с временем.** Отрезок задают во время
  игры; два поля потребовали бы остановиться и переписать секунды.

**Ограничения**

- **Тюнера нет.** Микрофон, определение высоты тона, борьба
  с обертонами и проверка на живых инструментах — работа, сопоставимая
  со всем остальным режимом. Тюнер, показывающий не то, хуже
  отсутствующего.
- **Табов рядом с видео нет.** Материалы отдаются по подписанной ссылке
  с коротким сроком жизни; показ PDF рядом с видео требует решить,
  что делать, когда ссылка протухла посреди занятия.
- **Отрезок не сохраняется** между заходами: его ставят под конкретное
  место, к которому в следующий раз возвращаться не обязательно.
- **Отрезок короче полутора секунд не принимается** — плеер не успевает
  разогнаться после перемотки.

Подробности решений — [ADR-0027](adr/0027-rehearsal-mode.md).

### Этап 10 — Дополнительные возможности

#### 10.4 — Глобальный поиск

**Добавлено**

- **Страница `/app/search`** вместо заглушки: разборы, уроки, эфиры
  и кураторы одной строкой, результаты сгруппированы по разделам.
- **Кнопка поиска в шапке** и сочетание `⌘K` / `Ctrl+K`.
- **`shared/search/`** — разбор поискового запроса переехал сюда
  из модуля разборов вместе с 28 тестами.
- **`search-repository.ts` в четырёх модулях**: разборы, курс, эфиры,
  клуб. Каждый со своим запросом и своим индексом.
- Сведение результатов — `app/app/_lib/search.ts`.
- Настройка `app.config.ts` → `search.perGroup` (5).

**Решения**

- **Группы по разделам, а не общий рейтинг.** Ранги из четырёх запросов
  несопоставимы: `ts_rank_cd` считает вес внутри своего вектора,
  а у разбора вектор из четырёх полей, у эфира — из двух. Приводить
  их к общей шкале — значит придумывать коэффициенты, которые нечем
  обосновать.
- **Порядок групп постоянный**, а не «где больше нашлось»: иначе нужный
  раздел приходится каждый раз искать глазами заново.
- **Четыре запроса вместо одного `UNION`.** Уходят параллельно, стоят
  миллисекунды, зато каждый читаем и живёт в своём модуле.
- **Кураторы ищутся подстрокой.** Их трое; поисковый вектор ради трёх
  строк никогда себя не окупит.
- **`⌘K` открывает страницу, а не всплывающее окно.** Оверлей означает
  поиск на лету и собственную разметку ради экономии одного перехода;
  страница даёт адрес, который можно отправить и к которому работает
  кнопка «назад».
- **Право видеть черновики — своё в каждом разделе.** Куратор разборов
  не находит поиском черновики курса.

**Ограничения**

- **Поиск по нажатию, а не на лету.** Следствие того, что запрос живёт
  в адресе.
- **По пять результатов в разделе, без «показать ещё».** Поиск отвечает
  на вопрос «есть ли такое»; не нашедший уточняет запрос.
- **Заметки и уведомления не ищутся.** Заметок у человека десятки,
  и искать среди них нечего; уведомления — указатели на содержимое,
  которое и так находится.
- **Содержимое уроков не ищется** — только название и краткое описание.
  Текст лежит в JSON, и вытаскивать его выражением вычисляемой колонки
  значило бы получить неотлаживаемое выражение.

Подробности решений — [ADR-0026](adr/0026-global-search.md).

### Этап 10 — Дополнительные возможности

#### 10.3 — Уведомления

**Добавлено**

- **Модуль `notifications`**: каталог типов, правила, запросы, сервис,
  доставка в Telegram. Таблица `notifications` переехала сюда из схемы
  модуля `audit` — без миграции, имя и колонки не менялись.
- **Четыре типа уведомлений**: новые разборы, записи эфиров,
  напоминание об эфире за сутки, предупреждение о конце подписки.
- **Вечерняя сводка** в 19:00 — всё накопившееся одним сообщением.
- **Лента** `/app/me/notifications` и колокольчик со счётчиком в шапке.
- **Настройки доставки** в личном кабинете: каждый тип отдельно,
  сохраняется сразу, без кнопки «Сохранить».
- **Четыре фоновые задачи**: сводка (19:00), уборка ленты (3:50),
  напоминание об эфире (каждый час), предупреждение о подписке (11:00).
- **Оповещение при публикации** разбора и записи эфира —
  `app/app/_lib/announce.ts`.
- Таблица `notification_preferences`, миграция
  `0014_notification_preferences.sql`, 20 тестов правил.
- Настройки — `app.config.ts` → `notifications.*`: размер ленты,
  срок хранения (полгода), час сводки, окно напоминания, порог
  предупреждения о подписке.

**Решения**

- **«Одно уведомление в день» — устройство доставки, а не счётчик.**
  Считать и обрезать значило бы терять содержание: человек не узнал бы
  о втором разборе никогда. Вместо этого всё, кроме срочного, копится
  до вечерней сводки и уходит одним сообщением.
- **Строка создаётся всегда, доставка отдельно.** Лента показывает
  историю тому, у кого Telegram заблокирован; `sent_at` отвечает
  на вопрос «почему мне не пришло» без похода в логи.
- **Типы живут в коде, настройки — в базе как отклонения.** Новый тип
  появляется в коде и сразу работает у всех, кто не отказывался.
- **Ничего не выключено по умолчанию**, а предупреждение о подписке
  нельзя выключить вовсе: это не новость, а предупреждение о потере
  оплаченного доступа.
- **Очередь `notification.send` убрана из каталога.** Она была заведена
  на Этапе 1 и оказалась не нужна: срочное создают фоновые задачи,
  а всё остальное ждёт сводки. Веб-процессу очередь не нужна вовсе.
- **Напоминание об эфире — окно «через 24–25 часов».** Задача идёт
  каждый час; выборка «ближайшие сутки» дала бы двадцать четыре
  напоминания об одном эфире.
- **Создание уведомлений не ломает публикацию.** Куратор, получивший
  ошибку после успешной публикации, нажмёт ещё раз и получит дубль.
- **Счётчик в шапке не обновляется в фоне.** Опрос раз в минуту —
  полторы тысячи запросов в сутки ради цифры, которая обновится
  и при следующем переходе.

**Ограничения**

- **Уведомлений о новых уроках курса нет.** Урок выходит внутри модуля,
  и «опубликован урок 7» без контекста ничего не говорит. Осмысленный
  повод — завершённый модуль; вернуться стоит вместе с новостями клуба.
- **Отметка о прочтении только целиком.** Уведомление читают, открывая
  то, на что оно указывает.
- **Пропущенный запуск задачи — пропущенное напоминание.** Догонять
  намеренно не пытаемся.
- **Telegram-кнопок в сообщениях нет** — обычный текст со ссылкой.

Подробности решений — [ADR-0025](adr/0025-notifications.md).

### Этап 10 — Дополнительные возможности

#### 10.2 — Заметки с таймкодами

**Добавлено**

- **Таблица `user_notes`** в модуле `library`: текст, необязательное
  время, привязка к варианту разбора, уроку или записи эфира.
- **Блок «Мои заметки»** на страницах разбора, урока и эфира: создание,
  правка, удаление, переход по времени.
- **Кнопка «Отметить текущее место»** — берёт время прямо у плеера.
  Поля для ввода времени руками нет.
- **Связь плеера с соседями по странице** —
  `_components/playback-context.tsx`: плеер сообщает о себе, соседи
  спрашивают управление.
- **Страница «Мои заметки»** `/app/me/notes` вместо заглушки: заметки
  разложены по записям, каждая ведёт на нужную секунду.
- **Параметр `?t=` на страницах разбора и урока** — раньше его понимали
  только эфиры. Разбор параметров адреса вынесен в `_lib/query.ts`.
- Счётчик заметок в личном кабинете.
- Пределы — `app.config.ts`: `library.maxNotes` (500),
  `library.maxNoteLength` (1000).
- Миграция `0013_user_notes.sql`, 17 тестов правил.

**Решения**

- **Заметка привязана к варианту разбора, а избранное — к песне.**
  Отложить — намерение про произведение; заметка — метка на дорожке
  конкретной записи. У среднего уровня она другая, чем у начального.
- **Заметка всегда личная, и общей не станет.** Поля «видна всем» нет
  и не планируется: человек пишет для себя и в тех выражениях, в каких
  думает. Обсуждение разбора — другая сущность.
- **Время подставляется кнопкой.** Участник пишет заметку с гитарой
  в руках и работающим видео; просить его переписать «2:14» в поле —
  значит не получить ни одной заметки.
- **Список меняется на месте, без обновления страницы.** Обновление
  пересоздало бы плеер: видео с начала, потерянный буфер, сброшенное
  место. Награда за заметку не должна быть такой.
- **Владелец проверяется в самом запросе**, а не отдельной сверкой после
  загрузки. Забытая сверка не видна ни в коде, ни в типах.
- **Порядок заметок — по времени в ролике, а не по дате создания.**
  Заметки с таймкодами это разметка дорожки: человек ставит их в том
  порядке, в каком спотыкается, а читает в том, в каком играет.

**Ограничения**

- **Заметки нельзя искать.** При двух-трёх десятках это не нужно;
  вернуться стоит вместе с общим поиском по платформе.
- **Правка только на странице записи.** Страница «Мои заметки» —
  для чтения; кода в браузере на ней нет вовсе.
- **Нет отмены удаления.** Вместо неё подтверждение в диалоге:
  восстанавливать заметку неоткуда.
- **Время не проверяется на длину записи.** Заметка на 40-й минуте
  ролика, из которого потом вырезали половину, останется — плеер просто
  перемотает в конец.

Подробности решений — [ADR-0024](adr/0024-notes-and-player-link.md).

### Этап 10 — Дополнительные возможности

#### 10.1 — Личная библиотека: избранное

**Добавлено**

- **Модуль `library`**: таблица `favorites`, чистые правила, запросы,
  сервис, тексты. Хранит вид и идентификатор — о самом содержимом
  не знает ничего.
- **Кнопка «Отложить»** на страницах разбора, эфира и урока. Состояние
  показывается сразу, до ответа сервера; при отказе возвращается назад
  с сообщением.
- **Страница «Избранное»** `/app/me/favorites` вместо заглушки: вкладки
  «Всё · Разборы · Эфиры · Уроки» со счётчиками, список строками,
  снятие прямо из списка.
- **Счётчик отложенного** в личном кабинете вместо описания раздела,
  когда есть что считать.
- `getStreamLinks` в модуле эфиров — справка без требования записи:
  отложить анонс законно.
- Предел отложенного — `app.config.ts` → `library.maxFavorites` (500).
- Миграция `0012_favorites.sql`, 14 тестов правил.

**Решения**

- **Отдельный модуль, а не поле в `progress`.** Прогресс пишет плеер сам
  каждые несколько секунд, избранное — только человек руками. Разный
  источник записи и разный жизненный цикл: в общей таблице половина
  строк существовала бы ради `position_sec`, половина — ради галочки.
- **Избранное на песню, прогресс на вариант разбора.** Проходят
  конкретный уровень конкретного куратора, а откладывают песню целиком.
  Привязка к варианту осыпала бы отложенное при переходе с начального
  уровня на средний.
- **Право видеть черновики — своё в каждом разделе.** Список собирается
  тремя «читателями» вместо одного: куратор разборов не обязан видеть
  черновики курса.
- **Видимость проверяется перед вставкой.** Иначе кнопка становится
  способом узнать о существовании чужого черновика: прислал идентификатор
  наугад, получил «отложено» — значит, он есть. При удалении проверки
  нет, иначе строка на снятый с публикации разбор осталась бы навсегда.
- **Перечень видов объявлен в `types.ts`, а не в схеме** — отступление
  от общего порядка проекта. Кнопка работает в браузере, и перечень
  в `schema.ts` утянул бы туда драйвер базы данных.
- **Один клиентский компонент вместо формы с перезагрузкой.** Плата —
  около килобайта кода на странице разбора, которая до этого не имела
  в браузере ничего. Перезагрузка остановила бы плеер и потеряла место
  просмотра — за галочку это слишком дорого.
- **История просмотров не делается: она уже есть.** Блок «Недавнее»
  на странице «Мой прогресс» и есть история. Отдельное хранилище было бы
  второй копией тех же данных.

**Ограничения**

- Кнопки на карточках каталога нет — сознательно, см. DECISIONS.md.
- Постраничной навигации в списке нет: он ограничен пределом в 500.
- Заметки с таймкодами (`user_notes`) — следующий шаг, 10.2.
- В `resume.ts` остаётся прежняя неточность: один «читатель» с правом
  `course.view_drafts` применяется и к эфирам. Задевает только показ
  черновиков куратору в блоке «Недавнее». Правится отдельно.

Подробности решений — [ADR-0023](adr/0023-favorites-model.md).


### Этап 9 — Администрирование

#### 9.7 — Обзор управления

**Добавлено**

- **Экран «Управление → Обзор»** `/app/manage` вместо заглушки: заботы,
  счётчики за неделю, последние действия команды, быстрые кнопки
  «Новый разбор» и «Новый эфир».
- **Пять поводов для беспокойства**, каждый из которых иначе никак
  не всплывает: прошедший эфир без записи, опубликованный модуль курса
  без уроков, не загрузившиеся файлы, подписки без сверки, забытые
  черновики разборов.
- Сводные запросы в модулях `songs`, `streams`, `course`, `media` —
  каждый со своей проверкой права.
- Срок «черновик забыт» — `app.config.ts` → `manage.staleDraftDays`
  (14 дней).
- 10 тестов правил обзора.

**Решения**

- **Наверху заботы, а не числа.** Экран отвечает на вопрос «что мне
  сейчас делать». Статистика ниже: она полезна, но ничего не побуждает
  сделать, и первой строкой предлагала бы куратору любоваться цифрами.
- **Показываются только тихие поломки.** То, о чём система сообщает сама
  (ошибка при сохранении, отказ в правах), здесь не дублируется. Место
  на экране занимает лишь то, что молчит: эфир без записи выглядит
  нормально до тех пор, пока участник не откроет его и не найдёт пустоту.
- **Ноль не прячется и не подсвечивается.** «За неделю опубликовано 0
  разборов» — самое полезное число на экране. Клуб живёт неровно, неделя
  без публикаций — норма, а не авария.
- **Разница между «спросили и всё хорошо» и «не спрашивали».** Куратору
  без прав на курс нельзя показывать «всё в порядке»: он ничего
  не проверял. Поэтому ответ модуля равен `null`, а не нулю.
- **Сборка живёт в слое приложения** (`_lib/manage-overview.ts`): экрану
  нужны шесть предметных областей сразу, и модуль, знающий обо всех,
  стал бы свалкой. Так же устроена кнопка «Продолжить» на главной.
- **Ничего не запрашивается без права.** Проверка стоит до обращения
  к модулю, а не после: иначе куратор получал бы отказ в правах посреди
  отрисовки главной страницы раздела.

**Ограничения**

- Счётчики считаются при каждом открытии: кэша нет. На нынешних объёмах
  это несколько миллисекунд; если экран станет тяжёлым, кэшировать
  надо не запросы, а страницу целиком.
- Новости в обзор не попали — раздела ещё нет (Этап 10).

#### 9.6.1 — Разрыв кольца `access` ↔ `audit`, модуль `settings`

Технический шаг: поведение платформы не изменилось ни в одном месте.

**Изменено**

- **Модуль `access` больше не пишет в журнал.** Изменения ролей и прав
  записывает слой действий (`manage/team/_actions/team.ts`), получая
  от модуля то, что изменилось. Так уже работали эфиры, курс
  и материалы — теперь приём общий для всего проекта.
- **Настройки платформы вынесены в модуль `settings`**: каталог, проверка
  значений, чтение, правка, тексты и таблицы `app_settings`
  и `feature_flags`. Миграции не потребовалось — имена таблиц те же.
- **Проверки прав вернулись внутрь модулей.** `getAuditLogPage` требует
  `audit.view`, `updateSetting` — `settings.edit`. Исключений из правила
  «право проверяется в модуле» в проекте больше нет.
- Модуль `audit` отвечает ровно за одно: журнал действий.

**Решения**

- **Кольцо разорвано по стороне записи, а не чтения.** Записать факт
  может кто угодно, а спросить право — только тот, кто знает права.
  Значит, зависимость должна идти в одну сторону: журнал → права,
  и никогда обратно. Правило записано в ARCHITECTURE §4.
- **Таблица `notifications` осталась в `audit`.** Ею пока никто
  не пользуется; свой модуль она получит на Этапе 10 вместе
  с уведомлениями. Заводить пустой модуль заранее — значит завести
  папку, в которую год никто не заглянет.
- **Переименование при переезде:** `settings.schema.ts` стал
  `validation.ts`, потому что в этом проекте `schema.ts` — это всегда
  таблицы базы. Два разных смысла у одного имени файла — верный способ
  открыть не тот файл через полгода.

#### 9.6 — Журнал действий

**Добавлено**

- **Экран «Управление → Журнал»** `/app/manage/logs` (право `audit.view`):
  лента событий по дням, поиск, отбор по разделу и сроку, раскрытие
  подробностей, постраничная навигация.
- **Отбор одним нажатием**: по имени — всё, что делал человек;
  по названию — вся история объекта, включая его удаление.
- **Колонка `audit_log.entity_title`** — снимок названия объекта
  на момент действия (миграция `0011`), и индекс по времени.
- **Названия проставлены во всех местах записи**: разборы, варианты
  разборов, эфиры, модули и уроки курса, материалы, настройки.
- **Ночная уборка `audit.cleanup`** (3:45): записи старше года удаляются.
- **Помощник `requireManagePermission`** — единая проверка права
  на страницах управления; девять экранов переведены на него.
- 12 тестов разбора адреса журнала.

**Решения**

- **Название объекта сохраняется в момент действия, а не подтягивается
  при чтении.** Разбор удаляют — строка из `songs` исчезает, и взять
  название становится неоткуда. Именно записи об удалении и ищут чаще
  всего, поэтому без снимка экран показывал бы идентификатор ровно там,
  где нужен ответ.
- **Имя участника, наоборот, берётся при чтении.** Люди удаляются мягко,
  строка остаётся; при этом имя не устаревает после переименования.
- **Ссылки в строке ведут на отбор, а не на объект.** Ссылка на объект
  была бы честной до первого удаления, а половина интересных записей —
  про удалённое.
- **Срок хранения — год** (решение владельца, PRD v0.3 §6). Вопрос
  «как мы делали это в прошлом году» ещё находится, более старое
  не пригождается никогда.
- **Ни сводок, ни рейтингов активности кураторов.** Журнал — инструмент
  разбора случая, а не наблюдения за людьми: трое кураторов, знающих,
  что их действия считают, начинают работать хуже.
- **Право `audit.view` по-прежнему только у администратора и владельца.**
  Показ куратору собственных действий (PRD v0.1) отложен: в клубе,
  где вся команда сидит в одном чате, ценность близка к нулю.

**Ограничения**

- Проверка права для этого экрана живёт в странице, а не в модуле:
  `audit` не может импортировать `access`, потому что `access` уже
  импортирует `audit`. То же вынужденное исключение, что и у настроек
  (см. ROADMAP, «Технический долг»).
- Записи, сделанные до миграции `0011`, остаются без названия объекта
  и показываются как «без названия».

#### 9.5 — Настройки платформы

**Добавлено**

- **Экран «Управление → Настройки»** `/app/manage/settings`
  (право `settings.edit`): ссылка продления подписки, карточки чатов
  Telegram, страница «О клубе».
- **Проверка значений** настроек — чистые схемы, 19 тестов.
- Возврат к исходному тексту у каждой настройки.
- Действие журнала `settings.update`.

**Решения**

- **Страница «О клубе» правится блоками, а не свободным текстом
  с разметкой.** Это первое, что открывает новичок, и человек без
  разработчика, вставивший текст из Word или оставивший незакрытый тег,
  сломал бы её для всех сразу. Блоки сломать нельзя — можно только
  заполнить.
- **Ссылки проверяются на протокол.** Значение попадает прямо
  в атрибут `href`: `t.me/club` без протокола ведёт в никуда,
  а `javascript:` там не место вовсе.
- **Сохранение кнопкой, а не на лету.** Единственное место платформы,
  где так: текст правят абзацами, и промежуточный обрывок фразы не должен
  успевать побывать на живой странице у всех участников.
- **Не больше шести карточек чатов.** Ограничение не техническое: чем
  длиннее список на главной, тем реже открывают хоть одну карточку.
- **Переключателей возможностей нет.** Таблица под них существует
  с Этапа 1, но ни одной возможности, которую стоило бы включать
  частично, пока не появилось. Переключатель без того, что он
  переключает, — мёртвый код, который через год никто не решится
  удалить. Раздел показан пустым с объяснением.

**Отступление от правил проекта**

Право `settings.edit` проверяется **в серверном действии, а не
в сервисе модуля** — единственный такой случай в проекте. Причина:
модуль `access` уже импортирует `audit`, чтобы писать выдачу прав
в журнал, и обратный импорт замкнул бы два модуля в кольцо.

Проверка от этого не слабее (действие тоже выполняется на сервере

лечение — вынести настройки из `audit` в собственный модуль: журнал
действий и тексты страницы «О клубе» не связаны ничем, кроме истории.

**Проверено**

#### 9.4 — Экран подписок: статусы, история, ручная выдача

**Добавлено**

- **Экран «Управление → Подписки»** `/app/manage/subscriptions`
  (право `subs.view`): сводка по состояниям, предупреждение о давней
  сверке, лента событий за неделю, список с отбором по состоянию
  и «требуют внимания».
- **История подписки на карточке участника**: что происходило, когда
  и по какому источнику.
- **Ручная выдача и отзыв доступа** (право `subs.grant`) на карточке
  участника: обязательная причина, необязательный срок.
- Действия журнала `subscription.grant`, `subscription.revoke`.
- Тексты видов событий и источников на русском.

**Решения**

- **Предупреждение о сверке — главное на экране.** Числа по состояниям
  приятно смотреть, но они не требуют действий. Строка «сверка
  не выполнялась больше суток» требует, и это единственное место
  во всей платформе, где видно, что связь с Telegram оборвалась.
- **События сверки помечены отдельно.** Каждое означает, что уведомление
  от Telegram не дошло и расхождение исправила ночная задача. Одно-два
  в месяц нормальны; поток означает сломанный вебхук.
- **Ручная выдача живёт на карточке участника, а не на экране подписок.**
  Повод всегда один: конкретный человек написал, что заплатил, а доступа
  нет. Кнопка в общем списке соблазняла бы решать частные случаи,
  не открыв человека.
- **Причина обязательна у выдачи и у отзыва.** Ручная выдача переживает
  события из Telegram, то есть человек может остаться с доступом надолго
  после того, как перестал платить.
- **История подписки видна только при праве `subs.view`.** Куратор
  со списком участников в чужие платежи не заглядывает.
- **Участники без записи о доступе на экране не показываются:** они есть
  в списке участников, а здесь ничего не сообщают.

**Ограничения**

- Список ограничен сотней записей и не разбит на страницы: при двухстах
  пятидесяти участниках с записью о подписке это почти всегда весь список.
  Постраничная навигация появится, когда понадобится.
- Ручная выдача не отменяет списание в Tribute — платформа платежами
  не управляет. В окне выдачи об этом сказано прямо.
- Экспорта отчёта нет.

**Проверено**

- `pnpm check` — 732 теста, ошибок нет.
- `pnpm build` — сборка проходит, маршрут на месте.

#### 9.3 — Живая подписка: уведомления Telegram и ночная сверка

Закрывает долг Этапа 2. До этого шага статус подписки не мог измениться
сам: человек оплачивал через Tribute, попадал в закрытый канал, а платформа
об этом не узнавала.

**Добавлено**

- **Обработчик уведомлений** `POST /api/telegram/webhook`: проверка секрета,
  защита от повторной доставки по `update_id`, ответ 200 сразу и обработка
  после ответа.
- **Разбор уведомлений** — чистые функции: событие о составе закрытого
  канала, изменение прав самого бота, всё остальное. 20 тестов.
- **Ночная сверка** в 4:00: проверяет действующих и льготных, кого
  не сверяли сутки; исправляет расхождения, пишет отчёт.
- **Команда `pnpm telegram:webhook`**: регистрация адреса, `--check`
  и `--delete`.
- Настройки `reconcileBatchSize`, `reconcileStaleHours`,
  `reconcileAlertThreshold`.

**Решения**

- **Интеграции с Tribute нет и не нужно.** Источник истины — членство
  в закрытом канале. Если Tribute поменяет API или его заменят другим
  сервисом, здесь не изменится ничего.
- **Отвечаем 200 даже на ошибку обработки.** Повторная доставка того же
  уведомления её не починит, а расхождение подберёт ночная сверка.
  Единственное исключение — неверный секрет: это не Telegram.
- **Занятие уведомления до ответа, обработка после.** Обратный порядок
  означает повторную доставку каждый раз, когда обработка оказалась
  медленнее, чем ждёт Telegram.
- **Событие сохраняется, даже если человека нет на платформе.** Он мог
  оплатить и попасть в канал, ни разу не заходя; при первом входе доступ
  откроется сам.
- **Потеря ботом прав администратора пишется уровнем «ошибка».** Это
  единственная поломка, которая иначе проходит совершенно молча:
  уведомления просто перестают приходить, платформа продолжает работать
  по последнему известному состоянию и не замечает обрыва связи.
- **Недоступность Telegram не отбирает доступ.** Состояние помечается
  непроверенным, участник продолжает работать (fail-open, PRD v0.1 §7.4).
- **Сопоставление «участник ↔ Telegram» делает фоновая задача,**
  а не модуль подписок: тот ничего не знает о способах входа, иначе два
  модуля ссылались бы друг на друга по кругу.

**Ограничения**

- Обработка идёт после ответа Telegram, поэтому при падении процесса между
  ответом и обработкой уведомление теряется. Расхождение подберёт ночная
  сверка — на сутки позже.
- Отчёт о расхождениях пока только в журнале приложения. Экран
  с расхождениями — шаг 9.4.
- Уведомлений участнику («подписка истекает») нет: это Этап 10.

**Требует действий при развёртывании**

1. `TELEGRAM_WEBHOOK_SECRET` и `TELEGRAM_CHANNEL_ID` в `.env`.
2. Бот — администратор закрытого канала.
3. `pnpm telegram:webhook`.

**Проверено**

- `pnpm check` — 732 теста, ошибок нет.
- `pnpm build` — сборка проходит, маршрут на месте.

#### 9.2 — Команда: роли и персональные права

**Добавлено**

- **Экран «Управление → Команда»** `/app/manage/team` (право `users.roles`):
  список тех, у кого есть роль, с пометкой отклонений «+2 −1».
- **Панель «Настроить»**: выбор роли, свёрнутая тонкая настройка по группам
  прав, переключатель с тремя состояниями (по роли / включено / снято),
  выбор области действия у прав с поддержкой `own`/`all`, «Сбросить к роли»,
  «Убрать из команды».
- **Добавление в команду**: поиск по участникам платформы, роль куратора
  при добавлении.
- Действия журнала `role.grant`, `role.revoke`, `permission.override`,
  `permission.reset`.
- 32 теста правил управления командой.

**Решения**

- **Роль у человека одна.** Модель допускает несколько, интерфейс —
  заменяет. Два пресета на одном человеке дают вопрос «откуда у него это
  право», на который никто не отвечает; точечные отличия — исключениями.
- **Четыре запрета при назначении роли:** себе, роль не ниже своей, роль
  владельца, последний владелец. Каждый закрывает ошибку, которая иначе
  чинится запросом в базу на боевом сервере.
- **Нельзя выдать право, которого нет у самого.** Без этого разделение
  на роли теряет смысл: старший куратор выдал бы себе через чужую карточку
  право выдавать права, а следующим шагом — всё остальное.
- **Отнять можно и то, чего у тебя нет.** Запрет никому ничего не
  открывает, поэтому ограничивать его незачем.
- **Права владельца неотзываемы,** в том числе другим владельцем: иначе
  владельца можно было бы обезоружить, не трогая роль.
- **Недоступные права показываются с объяснением, а не прячутся.**
  Спрятанное право выглядит как поломка платформы; объяснённое — как
  правило.
- **Три состояния переключателя вместо двух.** «По роли» — это не
  «выключено»: право, снятое принудительно, останется снятым и после
  повышения роли. Свести их в одно значило бы однажды повысить куратора
  и не понять, почему он по-прежнему не видит курс.
- **Изменения применяются сразу, без кнопки «Сохранить».** Настройки здесь
  независимы друг от друга, и общее сохранение создало бы состояние
  «часть применилась, часть нет» при первой же ошибке.
- **Роль при добавлении — самая узкая.** Расширить можно сразу же;
  обратный порядок оставляет окно, в котором человек успевает сделать
  лишнее.

**Ограничения**

- Свои роль и права изменить нельзя вообще — ни понизить, ни повысить.
  Это осознанно: понижение запирает самого себя, повышение открывает
  дорогу в два клика. Изменения делает другой администратор.
- Роль владельца назначается только заполнением базы
  (`OWNER_TELEGRAM_ID` + `pnpm db:seed`), из интерфейса — никогда.
- Создания собственных ролей нет: четыре пресета плюс исключения
  покрывают клуб такого размера с запасом.

**Проверено**

- `pnpm check` — 712 тестов, ошибок нет.
- `pnpm build` — сборка проходит, маршрут на месте.

#### 9.1 — Участники: список, карточка, блокировка

**Добавлено**

- **Список участников** `/app/manage/members` (право `users.view`): поиск
  по имени, городу и имени пользователя в Telegram; отбор по состоянию
  доступа, по наличию роли и по блокировке; три порядка показа; постраничная
  навигация по 30 строк.
- **Карточка участника** `/app/manage/members/[id]`: подписка (состояние,
  источник, сроки, когда сверялись), занятия (в клубе с, последний вход,
  сколько уроков и разборов доведено до конца, пройдено ли знакомство)
  и то, что человек написал о себе сам.
- **Блокировка участника** (право `users.ban`): окно с обязательной причиной,
  закрытие всех сессий, запись в журнал действий. Снятие — одной кнопкой.
- Поля `users.blocked_at`, `users.blocked_reason`, `users.blocked_by`
  и миграция `0010_member_moderation`.
- Действия журнала `user.block` и `user.unblock`.
- Настройка `appConfig.manage.membersPageSize`.
- 19 тестов: правила блокировки и разбор параметров адреса.

**Решения**

- **Блокировка — не отсутствие подписки.** Подписка отвечает на вопрос
  «оплачено ли», блокировка — «пускать ли вообще». Вышедший из платного
  канала остаётся участником клуба; заблокированный не попадает
  на платформу вовсе.
- **Проверка блокировки в двух местах, и оба обязательны.** В `resolveSession`
  через запрос сессии — на случай, если сессии закрыть не удалось; и во входе
  через Telegram — иначе человек тут же вошёл бы заново. Условие в самом
  низком слое переживёт и сбой между двумя операциями, и того, кто однажды
  напишет отзыв блокировки без закрытия сессий.
- **Причина обязательна.** Через полгода «а почему он заблокирован»
  спрашивает уже другой человек, и ответ должен находиться в карточке,
  а не вспоминаться.
- **Заблокированному показывается объяснение, а не «не удалось подтвердить
  вход».** Человек, которого молча выбрасывает на страницу входа, идёт
  писать в чат клуба, и разбираться с этим кураторам.
- **Роли выбираются отдельным запросом,** а не присоединением: у человека
  с двумя ролями строка задвоилась бы, и постраничная навигация начала
  бы врать.
- **Поиск включает имя пользователя в Telegram.** Человек пишет в поддержку
  оттуда, и часто это единственное, что о нём известно наверняка.
- **Список, а не сетка карточек.** Карточки хороши, когда выбирают; здесь
  сравнивают — «кто из этих без подписки», «кто не заходил месяц» читается
  только по колонкам сверху вниз.
- **Постраничная навигация с первого дня,** хотя 250 человек влезли бы
  одним списком: переписывать экран, когда участников станет восемьсот,
  будет некому и некогда.
- **Личного на экране нет.** Заметок к разборам, подробностей прогресса
  по конкретным урокам и переписки. Граница проходит по вопросу «нужно ли
  это, чтобы человеку помочь».

**Ограничения**

- Роли и персональные права на карточке пока только показываются —
  выдача появится на шаге 9.2.
- Сведения о подписке доступны только для чтения; ручная выдача и отзыв —
  шаг 9.4.
- Сверка с Telegram по-прежнему ничем не наполняется: вебхуки и ночная
  сверка — шаг 9.3.

**Проверено**

- `pnpm check` — 680 тестов, ошибок нет.
- `pnpm build` — сборка проходит, оба маршрута на месте.

#### 8.3 — «О клубе», чаты и хаб раздела

**Добавлено**

- **Страница «О клубе»** `/app/club/about`: вступление, тезисы, порядок

- **Хаб раздела** `/app/club`: пять плиток — то, что на телефоне
  заменяет выпадающее меню.

**Решения**

- **Блоки, а не статья.** Свободный текст с разметкой означал бы, что
  человек без разработчика может сломать вёрстку страницы, которую
  первой видит новичок. Блоки заданной формы сломать нельзя — можно
  только заполнить, а пустые поля «три тезиса» и «четыре шага»
  подсказывают структуру лучше, чем чистый лист.
- **Страница заполнена по умолчанию.** Встретить новичка пустой
  страницей «О клубе» нельзя; текст общий, заведомо верный и правится
  под себя.
- **Счётчиков сообщений в карточках чатов нет** — решение владельца
  продукта. Они повышают переходы, но требуют фоновой задачи, ходящей
  в Telegram раз в час; вернёмся к ним вместе с уведомлениями.
- **Частые вопросы раскрываются средствами браузера** (`details`):
  ни строчки кода в браузере, работает с клавиатуры и читается
  экранным диктором.
- **Хаб раздела короткий и ничего не дублирует.** Он существует потому,
  что нижнее меню на телефоне не раскрывает вложенные пункты; на большом
  экране те же разделы есть в боковом меню.

#### 8.2 — Визитки участников

**Добавлено**

- **Поле видимости профиля** (миграция `0009_profile_visibility`):
  `private` по умолчанию, `club` — по решению самого человека.
- **Переключатель в настройках** с честным перечислением того, что
  увидят участники и чего не увидят никогда.
- **Список участников** `/app/club/members`: поиск по имени и городу,
  отбор по городам с числом людей в каждом.
- **Визитка участника** `/app/club/members/[id]`.
- Пункт «Участники» в разделе «Клуб».
- Демо-данные: открыты визитки кураторов и только их.

**Решения**

- **По умолчанию закрыто.** Человек, регистрировавшийся год назад,
  не давал согласия показывать свой город полутора сотням людей.
  Согласие нельзя получить задним числом настройкой по умолчанию.
- **«Открыто» значит «видно участникам клуба», а не «видно интернету».**
  Платформа закрыта целиком, публичной витрины у визиток нет; это прямо
  написано рядом с переключателем.
- **Закрытый профиль не лишает права смотреть** — решение владельца
  продукта. Взаимность («показываешь свою — видишь чужие») выглядит
  справедливее, но означала бы давление: чтобы просто посмотреть, кто
  в клубе, пришлось бы раскрыться.
- **Прогресс, подписка, заметки, избранное и дата последнего входа
  не попадают в визитку никогда.** Их нет ни в запросе, ни в типе —
  показать их невозможно даже по ошибке.
- **Условие видимости живёт в запросе, а не на странице.** Страницу
  однажды напишут заново, компонент скопируют, поле добавят в выборку
  «на всякий случай» — условие в `where` переживёт всё это.
- **Города вместо карты с точками.** Список городов даёт то же ощущение
  «нас много и мы везде», не превращая клуб в справочник, где живёт
  каждый.
- **Закрытая визитка отвечает объяснением, а не «страница не найдена»**,
  и не сообщает ничего сверх: ни имени, ни города, ни того, состоит ли
  человек в клубе.
- **Видимость меняется отдельным действием**, а не полем формы профиля:
  это согласие, и оно не должно включаться при случайном сохранении формы.
- **Удаление аккаунта закрывает визитку.**

- **Страница куратора** `/app/club/curators/[slug]`: короткая биография,
  а под ней — его разборы и эфиры со ссылками «все разборы куратора».
- **Экран управления** `/app/manage/curators`: список карточек, заведение
  новой поиском по участникам, порядок показа.
- **Редактор карточки** `/app/manage/curators/[id]`: заполняет сам
  куратор; старший куратор видит там же удаление.
- **Показ и скрытие карточки** отдельным действием.
- Демо-данные: три заполненные карточки.

**Решения**

- **Карточка — расширение участника, а не отдельный человек.** Первичный
  ключ карточки есть идентификатор пользователя: куратор уже в клубе,
  у него профиль, прогресс и подписка. Отдельная таблица нужна лишь
  потому, что у ста пятидесяти участников из ста пятидесяти эти поля
  пустые, и потому что у карточки своя жизнь — её скрывают, показывают,
  переставляют.
- **Карточка скрывается, а не удаляется.** Куратор уходит в отпуск —
  страница исчезает со списка, разборы остаются, связь «кто вёл»
  не рвётся.
- **Стаж считается от года начала**, а не хранится числом: записанное
  «двенадцать лет» устаревает молча и через год врёт.
- **Порядок задаётся руками.** Кураторы — это люди, и алфавит здесь
  не нейтрален, а случаен: основатель клуба должен стоять первым
  независимо от буквы.
- **Область прав `own` здесь означает «про меня самого»** — единственное
  место на платформе, где владелец записи и есть её предмет. Свою
  карточку правит сам куратор, чужие — старший.
- **Заводит карточку старший, заполняет сам человек.** Обратный порядок
  превратил бы страницу «Кураторы» в список всех, кто захотел; а писать
  чужую биографию за коллегу — работа, которую никто не сделает хорошо.
- **Списки вроде «чему учит» вводятся по одному значению**, а не строкой
  через запятую: «Crosby, Stills & Nash» иначе превратились бы в три
  разных влияния.
- **Содержимое куратора собирает слой приложения**, а не модуль клуба:
  клуб не знает ни о разборах, ни об эфирах, иначе «удалить раздел
  эфиров» перестало бы быть удалением одной папки.

### Этап 7 — Записи эфиров

#### 7.3 — Редактор эфира для куратора

**Добавлено**

- **Список эфиров** `/app/manage/streams`: отбор по этапу жизни
  и «только мои», видно с одного взгляда, у какой записи нет оглавления.
- **Создание эфира** `/app/manage/streams/new`: короткая форма — тема
  и время. Ведущим ставится тот, кто заводит карточку; время по умолчанию —
  ближайшая суббота, 20:00.
- **Редактор эфира** `/app/manage/streams/[id]`: свойства, этап,
  публикация, запись, оглавление, разобранные песни, материалы.
- **Редактор оглавления**: время текстом в любом виде («12:30»,
  «1:02:15», «750»), Enter добавляет следующую строку, порядок
  выстраивается по времени сам, ошибки видны рядом со строкой сразу
  ([ADR-0021](adr/0021-manual-chapter-timecodes.md)).
- **Этап жизни эфира** переключается вручную: скоро → идёт → запись,
  плюс «отменён».
- **Связь с разборами** через поиск по названию и исполнителю; на странице
  разбора сразу появляется ссылка на эфир.
- **Материалы эфира**: конспект и ссылки прикладываются тем же способом,
  что табы к разбору.
- Тесты: правила оглавления и ввод времени в поясе клуба
  (**16 новых тестов**, всего 651).

**Решения**

- **Время задаёт порядок, а не куратор.** У пунктов оглавления нет
  собственного порядка — есть только время. Поэтому перетаскивания нет:
  вспомненный последним пункт дописывается в конец, платформа расставит.
- **Область прав «только свой» считается по ведущему**, а не по создателю
  карточки: анонсы часто заводит один человек на всех, а правит тему
  и выкладывает запись тот, кто эфир вёл. Пока ведущий не назначен,
  владельцем считается создатель — иначе куратор не смог бы править
  эфир, который сам же и завёл.
- **Этап и публикация — два разных переключателя, стоящих рядом.** Этап
  отвечает «что с эфиром происходит», публикация — «видят ли его
  участники». Разнести их по разным углам значило бы получить постоянный
  вопрос «почему участники не видят эфир, я же нажал „идёт“».
- **Публикация анонса не требует записи, публикация записи — требует.**
  Анонс выходит за неделю до эфира, когда записи быть не может;
  а карточка с этапом «Запись» без ролика отправляет участников
  на пустую страницу.
- **Адрес эфира при переименовании не меняется.** Ссылку на анонс
  куратор кидает в чат клуба, и она обязана открываться через год,
  когда на её месте лежит запись.
- **Оглавление и связи сохраняются целиком, а не по пункту.** У них нет
  собственной жизни — ни ссылок, ни прогресса, — поэтому замена короче
  на полсотни строк и не может рассинхронизироваться.
- **Ввод времени всегда московский** — поле формы проходит через
  `toClubInputValue`, чтобы куратор в отпуске за границей не назначил
  эфир не на тот час.

**Изменено**

- Таймкоды (`parseTimecode`, `formatTimecode`) переехали в общий слой:
  ими пользуются и разборы, и эфиры. Две копии уже успели разойтись
  в поведении на отрицательных числах.
- Редактор материалов и действия над ними переехали из папки разборов
  в общую: их используют разборы, варианты и эфиры. Параметр `songSlug`
  заменён на `publicPath` — редактор больше не предполагает, что
  материалы бывают только у песни.
- Реестр допустимых объектов для материалов пополнился эфиром.

#### 7.2 — Экраны эфиров для участника

**Добавлено**

- **Архив записей** `/app/streams`: поиск по теме с задержкой, отбор
  по куратору, страницы, полоса «идёт прямо сейчас» наверху, полоса
  просмотра на карточках, разные пустые состояния для «не нашлось»
  и «записей ещё нет».
- **Ближайшие эфиры** `/app/streams/upcoming`: короткий список анонсов
  без фильтров.
- **Страница эфира** `/app/streams/[slug]`: один адрес на три состояния —
  анонс, идущий эфир, запись. Плеер с оглавлением, разобранные песни,
  материалы.
- **Оглавление записи**: нажатие на пункт перематывает уже загруженный
  ролик без перезагрузки страницы; те же пункты уходят на дорожку плеера
  и видны в полноэкранном режиме.
- **Ссылка на момент записи**: `?t=2820` открывает эфир на 47-й минуте.
  Сильнее сохранённого места просмотра — по такой ссылке приходят
  осознанно.
- **Время эфира с часовым поясом**: сервер пишет «20:00 МСК», браузер
  дописывает «у вас — 19:00», если пояс отличается.
- **«Добавить в календарь»** — обработчик `/api/streams/[slug]/calendar`
  отдаёт файл события; эфир попадает в календарь телефона.
- **Ближайший эфир на главной** — блок, которого нет вовсе, когда
  анонсов не назначено.
- **Эфиры в кнопке «Продолжить»**: недосмотренная запись подхватывается
  наравне с уроком и разбором.
- **«Эту песню разбирали в эфирах»** — блок на странице разбора,
  обратная сторона связи из 7.1.
- Тесты: разбор адреса архива, работа со временем и файл календаря
  (**32 новых теста**, всего 635).

**Решения**

- **Архив — главная страница раздела, анонсы — вторая.** Эфир проходит
  раз в неделю, записей сорок: девять из десяти заходов — «посмотреть
  то, что пропустил». Идущий прямо сейчас эфир при этом поднимается
  в архив полосой, чтобы не потеряться из-за расположения списков.
- **Одна карточка на анонс и на запись.** Это один эфир на разных
  этапах жизни — как и одна строка в базе. Различается только правая
  колонка: отсчёт до начала или длительность записи.
- **Один адрес на три состояния.** Ссылка, сохранённая из анонса, через
  неделю приводит к записи, а не в никуда.
- **Время всегда пишется с поясом** ([ADR-0020](adr/0020-stream-time-and-reminders.md)).
  В клубе десяток человек за рубежом; «эфир в 20:00» для них не значит
  ничего.
- **«В календарь» вместо «Напомнить».** Уведомления — Этап 10; кнопка,
  которая ничего не напоминает, хуже отсутствующей. Файл календаря даёт
  то же самое сегодня и без нашего участия.
- **Оглавление видно и без подписки.** Оно и есть лучший довод её
  продлить: видно, что в записи есть нужные пять минут.
- **Область просмотра эфира — свой компонент, а не общий с разбором.**
  Совпадает разметка, а не смысл: у разбора части — структура урока
  с отметками «разобрал», у эфира оглавление — навигация по разговору.
- **Фильтров в архиве два, а не шесть.** При сорока записях поиск
  и отбор по куратору закрывают всё; год и тема заняли бы место на
  экране, ничего не давая.

**Изменено**

- Тип материала (табы, минусовки) и компонент их списка переехали
  в общие: их показывают и разборы, и эфиры. В модуле разборов
  сохранено прежнее имя типа — страницы не тронуты.
- Функция русского склонения, написанная трижды, вынесена
  в `shared/utils/plural.ts` с тестом.
- Обложка эфира больше не приходит пустой: в 7.1 запрос возвращал
  вместо неё `null`, потому что таблица медиа присоединялась один раз.
- Демо-данные: у эфира с записью появился материал — чтобы проверить
  соответствующий блок.

#### 7.1 — Модель данных эфиров

**Добавлено**

- Модуль `streams`: таблицы `streams`, `stream_chapters`, `stream_songs`,
  чтение с учётом прав на черновики, поисковая колонка.
- Правила состояний эфира (**24 теста**): «скоро», «идёт», «запись
  готовится», «запись», «отменён»; когда открывается кнопка
  «присоединиться»; человеческие подписи времени и длительности.
- Миграция `0007_streams.sql` — проверена на чистой базе.
- Демо-эфиры в `pnpm db:demo`: пять штук, по одному на каждое состояние,
  с оглавлением и связью с настоящим разбором.

**Решения**

- **Анонс и запись — одна таблица, а не две.** Это один эфир на разных
  этапах жизни. Разделение означало бы переносить запись из таблицы
  в таблицу в момент, когда куратор выложил видео, — вместе
  с напоминаниями, сохранёнными участниками ссылками и связями
  с песнями.
- **Состояние вычисляется, а не хранится.** Оно зависит от текущего
  времени, и записанное значение устаревает молча: через час после
  эфира база по-прежнему утверждала бы, что он идёт.
- **Этап ставит куратор, время подстраховывает.** Только куратор знает,
  начался эфир или задерживается. Но он же закончит эфир и уйдёт спать,
  не переключив ничего, — поэтому «идёт» дольше трёх часов
  автоматически превращается в «закончился».
- **Наличие видео сильнее поля состояния:** если запись выложена, эфир
  точно прошёл, что бы ни стояло в базе.
- **Кнопка «присоединиться» открывается за 15 минут до начала.** Люди
  приходят заранее, и «ещё нельзя» за две минуты выглядит как поломка.
- **Статус публикации отдельно от этапа жизни.** Разные вопросы: этап —
  «что происходит», статус — «видят ли участники». Куратор готовит анонс
  черновиком за неделю, а запись выкладывает после монтажа.
- **Оглавление — отдельная таблица, а не JSON:** по таймкодам нужен
  переход из плеера, а позже — поиск «в каком эфире разбирали баррэ».
- **Отменённые эфиры не попадают в ближайшие,** но остаются в архиве:
  человек должен понять, что эфир был назначен и не состоялся, а
  не решить, что он его пропустил.

**Переиспользовано без единой правки**

`buildChapters` из модуля медиа — функция писалась для частей разбора
и подошла оглавлению эфира как есть. Права, публикация, поиск, видео
и материалы тоже берутся готовыми.

**Экранов в этом шаге нет** — они в 7.2.

### Этап 6 — Онлайн-курс

#### 6.4 — Редактор курса для куратора

**Добавлено**

- Экран `/app/manage/course`: дерево модулей и уроков, правка на месте,
  порядок кнопками, публикация, удаление с подтверждением.
- Редактор блоков конспекта: абзац, заголовок, список, совет-врезка,
  аккорды. Порядок блоков — теми же кнопками.
- Действия редактора курса и правила в `editor-service.ts`.
- Привязка ролика к уроку по идентификатору из панели хостинга.
- Журнал действий пополнен публикацией, снятием и удалением в курсе.

**Решения**

- **Курс заводится сам при первом открытии экрана.** Заставлять куратора
  «создать курс», когда курс в клубе ровно один, — шаг ради формальности.
- **Права курса не имеют области «только своё».** У разборов она есть:
  базовый куратор правит свои и не портит чужие. Курс один на весь клуб,
  это общий материал, а не чья-то работа, — поэтому `course.edit` даёт
  правку целиком, и по пресетам ролей оно есть у старшего куратора
  и выше.
- **Адрес при переименовании не меняется.** Ссылка, отправленная в чат
  клуба полгода назад, должна открываться и сегодня; опечатка в адресе —
  меньшее зло, чем битые ссылки у полутора сотен человек.
- **Пустой урок опубликовать нельзя** — ни видео, ни текста означает
  страницу с одним заголовком. Это единственная проверка публикации,
  и она про содержимое, а не про оформление.
- **Пустые блоки выбрасываются при сохранении,** а не мешают их набирать:
  человек добавляет блок и только потом печатает.
- **Одинаковые названия дают разные адреса** (`pustoy-urok`,
  `pustoy-urok-2`): два урока с одним названием в модуле — обычное дело.
- **Порядок кнопками, не перетаскиванием** — то же решение и по тем же
  причинам, что у частей разбора (ADR-0015).
- **Блоки, которые нельзя набрать текстом** (картинка, видео, связанный
  разбор), редактор показывает, но не даёт править — и, что важнее,
  **не теряет при сохранении**.

**Проверено на живой базе**

Создание модуля и уроков, расхождение адресов при одинаковых названиях,
отказ публиковать пустой урок, публикация непустого, перестановка,
сохранность конспекта после правки, видимость: участник видит один урок
из трёх, остальные — черновики.

**Этап 6 закрыт.** Курс работает от модели данных до наполнения
без разработчика.

#### 6.3 — «Продолжить», место остановки и личный прогресс

**Добавлено**

- Плеер запоминает место остановки и сам отмечает просмотр: подписка
  на события `TimeUpdate`, `DurationChange` и `Ended`, возврат к месту
  по готовности. Работает и для урока курса, и для разбора.
- Блок «Продолжить» на главной — первое действие после приветствия.
- Страница `/app/me/progress`: доля пройденного курса, счётчики,
  список недавнего.
- Общее действие `progress.playback` в слое приложения — одно на все
  виды содержимого.
- Разрешение прогресса в карточку (`_lib/resume.ts`): прогресс знает
  «вид и идентификатор», курс знает уроки, разборы знают варианты —
  сводит их слой приложения.

**Решения**

- **Отметка раз в 15 секунд времени ролика,** а не по часам: при
  скорости 1.5× пятнадцать секунд ролика проходят за десять, и отметки
  должны следовать за содержимым.
- **Позиция хранится на сервере, а не в браузере.** Начал на компьютере,
  продолжил с телефона на пюпитре — обычный сценарий.
- **Возврат к месту делается по событию готовности плеера:** до него
  плеер не знает длительность и молча проглатывает перемотку.
- **Ошибки отметки глотаются молча.** Сообщение поверх видео ради
  неудавшейся отметки хуже самой неудачи: следующая придёт через
  пятнадцать секунд.
- **«Продолжить» никогда не предлагает законченное,** но и не показывает
  пустоту: брошенное на середине → следующий урок курса → ничего.
  Новичку это выглядит как «Начать курс», отдельного состояния не нужно.
- **На странице прогресса нет ни серий занятий, ни сравнения с другими**
  (PRD §0, пункт 6): сгоревшая серия превращает возвращение после
  перерыва в стыд.

**Исправлено**

⚠️ **Настоящая ошибка, найденная запуском против живой базы.**
В `upsertProgress` дата прохождения вычислялась выражением
`progress.completedAt ?? input.now`. Здесь `progress.completedAt` —
не значение, а описание колонки, и пустым оно не бывает: выражение
всегда возвращало старое значение поверх нового. Строка, дошедшая
до «пройдено» через обновление (а не при первой записи), навсегда
оставалась без даты — и досмотренный до конца разбор снова предлагался
к продолжению.

Ошибка не видна ни по коду, ни в типах и проявляется только на втором
обращении к одной и той же записи. Исправлено на `coalesce` в базе.
Заодно `resume.ts` больше не проверяет дату сам, а спрашивает правило
`isCompleted` — вторая формула того же самого однажды разошлась бы
с первой.

#### 6.2 — Карта курса и страница урока

**Добавлено**

- Карта курса `/app/learn/course`: вертикальный путь, свёрнутые
  пройденные модули, выделенный следующий урок, итог сверху
  («модуль 2 из 3 · осталось около 63 мин»).
- Страница урока: видео, конспект блоками, кнопка «Урок пройден»,
  переход к соседним урокам через границу модуля.
- Отрисовка всех видов блоков: заголовок, абзац, список, совет-врезка,
  аккорды, связанный разбор.
- Действие `course.lesson.complete` — отметка и её снятие.
- `getSongsByIds` в модуле разборов — для блока «связанный разбор».

**Изменено**

- ⚠️ **Плеер переехал** из `learn/songs/[slug]/_components/video-player.tsx`
  в `app/_components/video-player.tsx`: тот же компонент показывает урок
  курса, а позже — запись эфира. **Старый файл нужно удалить вручную**
  (см. README шага).
- Адрес модуля `/app/learn/course/[module]` больше не отдельная страница,
  а перенаправление на карту курса к нужному модулю. Показывать ей было
  нечего: список уроков модуля и так виден на карте, причём вместе
  с соседними модулями — то есть с ответом на вопрос «сколько осталось».

**Решения**

- **Путь, а не сетка карточек.** Сетка правильна для библиотеки, где
  человек выбирает. Курс проходят по порядку, и сетка врёт: показывает
  сорок равнозначных вариантов там, где верный ровно один.
- **Сворачивание на `<details>`,** а не на состоянии в браузере: карта
  курса не содержит клиентского кода вовсе.
- **Кнопка «пройден» стоит после конспекта, а не в шапке.** В шапке её
  нажимают, не открыв урок, и прогресс перестаёт что-либо означать.
- **Отметка показывается сразу, до ответа сервера.** Если сервер отказал,
  галочка возвращается назад: человек не должен уйти с уверенностью,
  что урок засчитан.
- **Замка у уроков нет** — ни одного, включая значки. Он появился бы
  только вместе с блокировкой прохождения, которой у нас нет.

**Найдено при разработке**

Линтер повторно поймал обращение модуля курса к чужим модулям — на этот
раз к прогрессу и разборам. Исправлено: отметка о прохождении берётся
из карты курса, которая уже приехала одним запросом, а связанные разборы
разрешает слой приложения. Модуль курса теперь не знает о разборах
ничего.

**Отложено осознанно**

Автоматическая отметка по просмотру 90% ролика. Правило написано
и покрыто тестами на шаге 6.1, но требует событий от плеера
видеохостинга — их подключение идёт вместе с запоминанием места
остановки в 6.3, где то и другое нужно одновременно.

#### 6.1 — Модель данных курса и прогресса

**Добавлено**

- Модуль `course`: таблицы `courses`, `course_modules`, `lessons`,
  чтение с учётом прав на черновики, поисковая колонка урока.
- Формат содержимого урока — список блоков (**13 тестов**): заголовок,
  абзац, список, совет-врезка, аккорды, изображение, видео, связанный
  разбор.
- Правила устройства курса (**20 тестов**): следующий незакрытый урок,
  проценты модуля и курса, соседи для навигации, сквозная нумерация.
- Модуль `progress`: полиморфная таблица и правила прохождения
  (**21 тест**).
- Миграция `0006_course_and_progress.sql` — проверена на чистой базе.
- Демо-курс в `pnpm db:demo`: 3 модуля, 8 уроков, включая черновик,
  урок без длительности и урок со ссылкой на настоящий разбор.

**Решения**

- **Содержимое урока — свой формат блоков, а не дерево стороннего
  редактора** ([ADR-0018](adr/0018-lesson-content-blocks.md)). Чужой
  формат меняется с их версиями, отрисовывать его пришлось бы всё равно
  самим, а куратор получал бы свободу напечатать кашу из шрифтов.
  Осознанное ограничение: выделения внутри абзаца нет.
- **Чтение содержимого никогда не бросает исключение.** У `jsonb` нет
  типа: лежать может запись прошлогодней версии или правка руками.
  Испорченный блок выбрасывается, урок показывается.
- **Прогресс — одна полиморфная таблица**
  ([ADR-0019](adr/0019-progress-model.md)). Плата за главную кнопку
  платформы: «Продолжить» отвечает на вопрос «что человек трогал
  последним» одним запросом вместо объединения четырёх.
- **Пройдено при 90% просмотра**, ручная отметка сильнее автоматики,
  доля просмотра только растёт, положение — всегда последнее.
- **Уроки не запираются** до прохождения предыдущих: замок защищает
  методику ценой оттока.

**Найдено при разработке**

- Линтер поймал обращение модуля курса к сервису модуля прогресса.
  Исправлено правильно: соединение с таблицей прогресса в запросе
  курса (разрешённое исключение) плюс чистая функция `isCompleted`
  из публичного входа. Побочная выгода — один запрос вместо двух.

**Проверено на живой базе**

Участник видит 7 уроков, куратор — 8 (включая черновик). Ручная отметка
и просмотр 90% дают «пройдено», перемотка назад не снижает засчитанное,
оставшееся время считается только по непройденным и не выдумывает
длительность там, где её не указали, навигация переходит через границу
модуля.

**Экранов в этом шаге нет** — они в 6.2.

### Этап 5 — Разборы

#### 5.7 — Поиск по разборам

**Добавлено**

- Полнотекстовый поиск PostgreSQL: вычисляемая колонка `songs.search_vector`
  с весами полей, индекс GIN, миграция `0005_song_search.sql`.
- Расширение `pg_trgm` — устойчивость к опечаткам и подсказки.
- Разбор поискового запроса чистыми функциями (**28 тестов**): исправление
  раскладки, транслитерация в двух вариантах, сборка выражения.
- Порядок «по совпадению»: применяется при поиске по умолчанию, пункт
  в списке сортировки появляется только при наличии запроса.
- Поиск по меткам: «фингерстайл» находит песни с такой меткой.
- Пустое состояние «Возможно, вы имели в виду» со ссылками на песни.
- `Highlight` в дизайн-системе: подсветка найденного фирменным маркером.

**Что теперь работает** (проверено на живой базе с демо-данными)

| Запрос | Раньше | Теперь |
| ------ | ------ | ------ |
| `matters nothing` | пусто | Metallica — Nothing Else Matters |
| `Тщерштп` | пусто | Metallica — Nothing Else Matters |
| `металлика` | пусто | Metallica — Nothing Else Matters |
| `фингерстайл` | пусто | The Beatles — Blackbird |
| `металика` | пусто | подсказка на Metallica |
| `ыф` | пусто | пусто, без ложных срабатываний |

**Решения**

Подробно — [ADR-0017](adr/0017-song-search.md).

- **Средствами базы, без поискового сервиса.** Meilisearch оправдан
  примерно от трёх тысяч единиц содержимого; у нас 280.
- **Вычисляемая колонка, а не поле, которое заполняет сервис.** Обновление
  из кода работает до первой правки в обход сервиса, после чего поиск
  молча перестаёт находить песню.
- **Варианты запроса уходят одним выражением через «или»,** а не тремя
  попытками подряд: порядок попыток — это решение о том, что важнее,
  и его лучше принимает ранжирование.
- **Метки не денормализуются** в текстовую колонку: это ещё одно место,
  которое однажды разойдётся с данными и будет молча врать. Совпадение
  проверяется подзапросом.

**Найдено при разработке** — все три случая выявлены запуском против
настоящего PostgreSQL, ни один не был виден по коду:

- Поиск по началу слова у исправленных вариантов давал ложные совпадения:
  запрос `ыф` превращался в `sa:*` и совпадал с «Sarah» и «Satisfaction».
  Введён порог: догадкам поиск по началу разрешён с четырёх букв.
- `similarity` не годится для подсказок — наказывает за разницу в длине
  и даёт 0,21 там, где `word_similarity` даёт 0,70. Заменено, порог
  подобран на живых данных.
- Запрос «металлика» находил меньше, чем «метал»: транслитерация давала
  `metallika` вместо `metallica`. Добавлен второй вариант, где «к»
  пишется латинской `c`. Поиск, в котором дописывание букв ухудшает
  результат, человек считает сломанным.

#### 5.6 — Загрузка файлов

**Добавлено**

- Обработчик `POST /api/media/upload`: приём материала с проверкой прав,
  вида файла и размера. Тело читается кусками и обрывается при превышении.
- Правила приёма файлов в модуле медиа: белый список расширений, пределы
  по видам, подпись по умолчанию, разбор внешних ссылок (**30 тестов**).
- Блок «Материалы» в редакторе разбора — у песни и у каждого варианта:
  загрузка, подпись, порядок, разрешение скачивать, удаление.
- Ссылка на интерактивные табы (Soundslice) как отдельный вид материала.
- `FileDrop` в дизайн-системе: перетаскивание и обычный выбор файла,
  полоса прогресса. О бизнес-логике не знает.
- `uploadFile` — отправка с прогрессом на `XMLHttpRequest`.
- Ночная задача `media.cleanup`: уборка оборванных загрузок старше суток.
- Журнал действий пополнен снятием материала.

**Решения**

Подробно — [ADR-0016](adr/0016-file-uploads.md).

- **Байты идут через наш сервер, а не прямо в хранилище.** Прямая загрузка
  требует настройки CORS у поставщика, ломает локальную разработку без
  облака и добавляет второй путь кода. Плата — трафик через VPS; при трёх
  кураторах это шум. Порог пересмотра записан в ADR.
- **Обработчик адреса, а не действие сервера.** У действий есть предел
  размера тела и нет прогресса: куратор, отправивший двадцать мегабайт
  без индикатора, нажимает кнопку второй раз.
- **Вид файла — по расширению, тип содержимого назначаем мы.** У Guitar Pro
  нет зарегистрированного типа; заодно закрыт файл, объявленный картинкой,
  но содержащий разметку со скриптом.
- **Пределы разные по видам:** Guitar Pro 5 МБ, PDF 25 МБ, минусовка 50 МБ,
  картинка 10 МБ. Один предел на всё либо не пускает партитуру, либо пускает
  в хранилище часовое видео.
- **Сначала строка в базе, потом байты.** Оборванная загрузка оставляет
  след, по которому её найдёт уборка. Обратный порядок оставлял бы файлы,
  о которых никто не помнит.
- **Файл удаляется вместе с последней привязкой,** а не с первой: одна
  минусовка может использоваться и на странице песни, и в уроке.
- **Право загружать отделено от права править.** Переименовать и убрать
  материал со своего черновика куратор может всегда; `media.upload` нужен
  для добавления новых файлов.

**Изменено**

- Из модуля разборов убраны функции, работавшие с таблицами модуля медиа
  напрямую. Привязки целиком переехали в медиа, право на объект проверяет
  слой приложения через новый реестр `src/app/_lib/attachment-access.ts`.
- `ARCHITECTURE.md`: уточнено, что «файлы не проходят через сервер»
  относится к чтению. При записи правило другое и обосновано отдельно.

**Не сделано намеренно**

- **Загрузка обложек разбора.** Проект осознанно отказался от
  картинок-обложек в пользу типографских (см. `song-cover.tsx`); механизм
  загрузки готов, возврат — решение владельца продукта, а не разработчика.
- **Экран «Миграция».** Отменён: выгрузка из Telegram делаться не будет.

#### 5.5 — Редактор разбора

**Добавлено**

- Экран `/app/manage/songs`: список разборов с фильтрами по состоянию
  и «мои», сортировка по времени правки.
- Экран `/app/manage/songs/new`: создание разбора двумя полями.
- Экран `/app/manage/songs/[id]`: песня, варианты, части, публикация
  на одной странице.
- Схемы проверки редактора (13 тестов) и правила публикации (11 тестов).
- Слой записи разборов: создание, правка, порядок частей, состояния.
- Действия сервера для всех операций редактора.
- Разбор таймкодов «2:14» ↔ 134 секунды (10 тестов).
- Привязка ролика Kinescope по идентификатору.
- Журнал действий пополнен событиями разборов.

**Решения**

Подробно — [ADR-0015](adr/0015-song-editor.md).

- **Одна страница вместо мастера.** Мастер требует пройти себя до конца,
  а куратор заводит разбор в перерыве между делами. Создание — две строки,
  дальше правка в любом порядке, сохранение по блокам.
- **Препятствия публикации видны до нажатия**, а не после. Кнопка при этом
  не блокируется: сервер проверит сам, а заблокированная кнопка без
  объяснения — та же ошибка, только раньше.
- **Видео для публикации не требуется.** Иначе разбор нельзя выпустить,
  пока не смонтированы все ролики, — неделя, в течение которой участники
  не видят даже того, что песня в работе.
- **Кнопки «выше/ниже» вместо перетаскивания.** Перетаскивание ломается
  на сенсорных экранах внутри прокрутки и недоступно с клавиатуры;
  частей шесть, переставляют редко.
- **Таймкоды в человеческом виде.** Куратор переписывает то, что видит
  в плеере; счёт в уме даёт ошибки.
- **Видео пока по идентификатору.** Полноценная загрузка — 5.6: сделанная
  наспех, она срывается на сороковой минуте без объяснений.
- **Действия сервера живут в слое приложения**, а не в модуле: модуль
  не имеет права читать cookie, тот же код работает в фоновых задачах.

**Найдено при разработке**

- Схема молча превращала неверное значение в пустое: куратор, напечатавший
  год «2400», обнаружил бы, что поле само опустело. Заменено на честную
  ошибку по полю. Поймано тестом.
- Шаблоны структуры разбора уже существовали в модуле с шага 5.1 — вторая
  копия удалена, существующая доработана до устойчивости к значениям
  из браузера.
- Разборы обращались во внутренности модуля медиа. Переставлен порядок:
  сначала проверка права трогать разбор, потом создание записи о ролике.
  Побочно закрыта возможность плодить записи без прав.

**Ограничения**

- Загрузка файлов и обложек — шаг 5.6.
- Переназначение куратора варианта, отложенная публикация — интерфейса
  пока нет.
- Экран «Миграция» перенесён в 5.6: массовая разметка упирается
  в ту же загрузку.

**Проверено**

- Сборка, типы, линтер, форматирование, **467 тестов** — проходят.

#### 5.4 — Видео

**Добавлено**

- Слой видеохостинга `shared/video`: договор `VideoProvider`, реализация
  для Kinescope и «выключенная» реализация для разработки без учётной записи.
- Ключ воспроизведения: подписанный, привязанный к паре «человек + ролик»,
  живёт два часа (14 тестов).
- Обработчик `POST /api/video/authorize` — сюда обращается Kinescope
  за разрешением при каждой попытке воспроизведения.
- Плеер на странице разбора: водяной знак с именем участника, оглавление
  из частей, переход к части нажатием, скорость 0.5×–1.5×.
- Правила показа: текст водяного знака и сборка оглавления (7 тестов).
- `pnpm kinescope:setup` — разовая настройка адреса разрешений в Kinescope.
- Общий доступ к секрету приложения (`shared/config/secrets`): его теперь
  используют и сессии, и ключи воспроизведения.
- Псевдоним Telegram доступен модулю: нужен водяному знаку, потому что
  имена в клубе повторяются.

**Решения**

Подробно — [ADR-0014](adr/0014-video-playback-authorization.md).

- **Разрешение вместо подписанной ссылки.** Kinescope сам спрашивает
  у нас при каждом воспроизведении. Подписка закончилась в среду — видео
  перестало играть в среду, а не доиграло до конца срока ссылки.
- **Ключ привязан к ролику.** Подсмотреть ключ на одном разборе
  и подставить к другому не выйдет.
- **Свой формат ключа, не JWT.** Приём в проекте уже принят: ключи сессий
  устроены так же. JWT принёс бы зависимость и класс ошибок вокруг выбора
  алгоритма, не дав ничего — читать этот ключ, кроме нас, некому.
- **Отдельный ключ подписи, выведенный из секрета приложения.** Подпись
  воспроизведения не должна быть принята там, где ждут подпись сессии.
- **Здесь нет fail-open.** При любом сомнении — отказ. Fail-open существует,
  чтобы сбой у посредника не наказывал участника; здесь же сомнение
  означает незнание, кто перед нами.
- **Водяной знак — имя и псевдоним, не почта.** Имя работает социально;
  почта превратила бы знак в утечку персональных данных.
- **Скорость воспроизведения вынесена наружу плеера.** При разборе её
  меняют по десять раз за занятие, лезть в меню настроек — мучение.
- **Память браузера о позиции отключена.** Своя память (Этап 10)
  переживает смену устройства, браузерная — нет.

**Ограничения**

- Обработчик разрешений обязан быть доступен из интернета: с localhost
  проверить нельзя, нужен туннель (`cloudflared`).
- Загрузка роликов из браузера — шаг 5.5, вместе с редактором.
- Части со своим отдельным роликом видны в списке, но переходом
  не открываются: переключение роликов появится, когда такие разборы
  возникнут.
- `VIDEO_PROVIDER=bunny` больше не существует: значения `kinescope`
  и `none`. Реализации Bunny не было и раньше — выбор такого значения
  привёл бы к падению при первом просмотре.

**Проверено**

- Сборка, типы, линтер, форматирование, **430 тестов** — проходят.
- Работа с Kinescope вживую не проверялась: нет учётной записи.

#### 5.3 — Страница песни

**Добавлено**

- Экран `/app/learn/songs/[slug]`: шапка со свойствами инструмента,
  переключатель уровней и вариантов, структура частей с якорями,
  материалы, сводка варианта, похожие разборы.
- Выбор варианта разбора (`arrangement-selection.ts`) — 24 теста.
- Модуль `media` дорос до рабочего: правила обращения с файлами
  (15 тестов), чтение реестра, выдача подписанных ссылок.
- Обработчик `GET /api/media/[id]/download` — скачивание материалов
  с проверкой подписки и перенаправлением на хранилище.
- Общий тип `ContentViewer` в `shared/content`: кто читает содержимое
  и видит ли неопубликованное.
- Похожие разборы по общим меткам.
- Элементы дизайн-системы: `PillLink`, `PropertyList`.
- Имя скачиваемого файла в подписи ссылки (`shared/storage`).
- Демонстрационные материалы: настоящие файлы в `.storage`, включая
  случаи «обрабатывается» и «интерактивные табы».

**Решения**

Подробно — [ADR-0013](adr/0013-song-page-and-file-delivery.md).

- **Уровень и вариант живут в адресе.** Ссылку на конкретный уровень
  пересылают в чат клуба, и она обязана открыть именно его. Уровень
  не является ключом: схема допускает два разбора одного уровня
  от разных кураторов, поэтому рядом появился `?v=<id>`.
- **Уровень из адреса применяется только точным совпадением.** Подмена
  ближайшим означала бы, что человек принял разбор для начинающих
  за продвинутый.
- **При подборе по профилю ближайший уровень берётся в сторону
  упрощения.** Разобрать песню ниже своего уровня скучно, но возможно;
  выше — невозможно, и человек уходит.
- **Файлы отдаёт обработчик адреса, а не действие сервера.** Скачивание —
  переход, и обычная ссылка даёт всё сразу: работу без JavaScript,
  открытие в новой вкладке, правильное объявление экранным диктором.
- **Ключ объекта в хранилище наружу не уходит.** В разметке лежит
  идентификатор материала; постоянного адреса у закрытых файлов
  не существует по определению.
- **Ошибки скачивания ведут туда, где человек может что-то сделать:**
  не вошёл — на вход, кончилась подписка — на страницу продления.
- **Нерабочих кнопок нет.** Ни избранного, ни заметок, ни режима
  репетиции, ни «Редактировать разбор» — каждая появится со своим шагом.
- **Прогресс не показывается даже заглушкой.** Число «3 из 6», взятое
  из воздуха, — это не демонстрация, а ложь в интерфейсе.
- **Место под плеер занято плашкой с заданными пропорциями,** чтобы
  подключение видеохостинга не сдвинуло страницу.

**Исправлено**

- **Режим «смотреть как участник» не работал на каталоге разборов.**
  Маска режима накладывается в слое приложения, а модуль разборов
  спрашивал права напрямую и получал настоящие: куратор, включивший
  режим, продолжал видеть черновики. Теперь модули содержимого
  принимают `ContentViewer`, собрать который можно единственным
  способом — helper в слое приложения. Неверный вызов больше
  не собирается, вместо того чтобы тихо работать не так.

**Найдено при разработке**

- Одинаковая ссылка-«таблетка» существовала в трёх местах каталога
  тремя копиями стилей. Вынесена в `PillLink`; заодно разделены
  два состояния, которые копии путали: выбранный фильтр и текущее
  положение.

**Ограничения**

- Видео нет: плеер — шаг 5.4. Части без видео показываются без кнопки
  воспроизведения, и это нормальное состояние черновика.
- Прогресс, избранное, заметки и режим репетиции — Этап 10.
- Кнопка «Редактировать разбор» появится с редактором (5.5).
- В локальной разработке подписи ссылок нет вовсе, поэтому имя
  скачиваемого файла там берётся из ключа хранилища.
- Похожие разборы считаются по общим меткам. Рекомендации
  по поведению — Этап 10, они заменят функцию, не задевая страницу.

**Проверено**

- Сборка, типы, линтер, форматирование, **409 тестов** — проходят.

#### 5.2 — Каталог разборов

**Добавлено**

- Экран `/app/learn/songs`: сетка карточек, фильтры, подборки, поиск,
  сортировка, постраничная навигация.
- Типографские обложки (`SongCover`) — 7 тестов.
- Быстрые подборки: «Для новичка», «Разберу за вечер», «Русский рок»,
  «Фингерстайл», «Без перестройки».
- Фильтр по времени разбора и значения фильтров из реальных данных.
- 11 новых тестов фильтров и подборок.

**Решения**

- **Обложки типографские, а не картинки.** Обложек альбомов у нас нет:
  скачивать их — чужие права на изображения в платном сервисе, просить
  кураторов подобрать 280 штук — работа, которой они заниматься
  не станут. Цвет устойчиво выводится из адреса песни: случайный
  превратил бы каталог в мигающую мозаику, и человек перестал бы
  узнавать карточки, которые уже видел.
- **Фильтры — ссылки, а не галочки.** Бесплатно получаются работающая
  кнопка «назад», ссылка на «фингерстайл в DADGAD», отрисовка сразу
  на сервере без мигания пустым списком и работа без JavaScript.
  Расплата — переход страницы на нажатие; при двадцати четырёх
  карточках незаметно.
- **В фильтрах только те значения, что реально встречаются.** Список
  из двадцати восьми жанров, двадцать из которых ничего не находят, —
  способ отучить человека пользоваться фильтрами.
- **Любое изменение фильтра возвращает на первую страницу.** Остаться
  на седьмой при трёх найденных — это пустой экран без объяснения.
- **Две разные пустоты различаются.** «Ничего не нашлось по фильтрам»
  лечится сбросом, «разборов ещё нет» — нет. Одинаковое сообщение
  заставило бы искать несуществующую кнопку.
- **Ссылкой сделана вся карточка, а не название.** Попасть пальцем
  в строку текста на телефоне трудно, промахнуться по карточке нельзя.

**Найдено при разработке**

- Линтер запретил синхронизировать поле поиска с адресом через эффект.
  Правильное решение оказалось короче: строка каталога пересоздаётся
  по ключу при смене запроса, и поле получает новое начальное значение
  без лишней отрисовки.

**Ограничения**

- Поиск идёт подстрокой по названию и исполнителю. Полнотекстовый поиск
  с учётом опечаток и словоформ — шаг 5.6.
- Прогресс на карточках не показывается: учёта прогресса ещё нет (Этап 10).
- Сортировка «от простого к сложному» досчитывается в приложении
  в пределах страницы.

**Проверено**

- Сборка, типы, линтер, форматирование, **370 тестов** — проходят.

#### 5.1 — Модель данных разборов

**Добавлено**

- Модуль `songs`: песни, варианты разбора по уровням, части разбора.
  Правила предметной области (`domain.ts`) — 39 тестов.
- Разбор фильтров каталога из адресной строки (`catalog-filters.ts`) —
  28 тестов.
- Модуль `taxonomy`: метки — жанры, техники, настроение. 6 тестов.
- Таблица материалов (`attachments`) в модуле медиа: табы, минусовки,
  конспекты привязываются к любому виду содержимого.
- Общие перечисления базы (`shared/db/enums.ts`): состояние публикации
  и виды содержимого.
- Чтение каталога и страницы песни с учётом прав на черновики.
- Команда `pnpm db:demo` — восемь демонстрационных песен для разработки.
- Миграция `0004_songs`: 6 таблиц, 3 перечисления.

**Решения**

Подробно — [ADR-0012](adr/0012-arrangements-model.md).

- **Уровень сложности — отдельная запись, а не колонка песни.** Колонки
  вида `beginner_video_id` ломаются на первом же живом случае: два разбора
  одного уровня от разных кураторов, версия «на акустике» рядом
  с электрической, свой куратор у каждого уровня. Уникальности по паре
  «песня + уровень» намеренно нет.
- **Уровень разбора — та же шкала, что уровень игры в профиле.** Иначе
  пришлось бы изобретать сопоставление двух шкал ради подбора первого
  разбора новичку.
- **Строй гитары — колонка песни, а не метка.** Жанр это интерес,
  а строй — условие: человек не станет перестраивать гитару ради
  одной песни.
- **Видео у части — своё либо отрезок общего.** Чаще куратор снимает
  один ролик и размечает таймкодами; своё видео позволяет переснять
  одну часть, не трогая остальные. Выбор делает функция, а не ограничение
  базы: сообщение об ошибке от базы получил бы куратор.
- **Запланированная публикация открывается по времени.** Иначе куратор,
  назначивший выход на утро понедельника, должен был бы прийти утром
  понедельника и нажать кнопку.
- **Решение «видит ли человек черновики» принимает сервис, а не страница.**
  Передавай его сверху — правило размазалось бы по всем местам, где
  читают разборы, и достаточно один раз забыть.
- **Мусор в адресе каталога игнорируется, а не отвергается.** Ссылки
  правят руками и режут при копировании: `?level=надёжный` показывает
  каталог без фильтра, а не страницу ошибки.

**Найдено при разработке**

- **Миграция вышла неполной и упала бы при применении.** Инструмент
  миграций читал схемы только из модулей и не видел общий файл
  перечислений: колонки ссылались на типы `publication_status`
  и `content_entity`, а команд создать эти типы в миграции не было.
  Ошибка тихая — файл выглядит нормально. Настройка исправлена,
  миграция перевыпущена.
- **Линтер границ поймал настоящую проблему.** Список жанров существовал
  дважды: в профиле участника с шага 4.1 и в новом справочнике меток.
  Разойдясь, они превратили бы подбор разборов по любимым жанрам
  в подбор, который ничего не находит. Список сведён к одному, в модуле
  меток; профиль берёт его оттуда.
- **Тест на неповторимость адресов упал на «Фингерстайле»:** он
  одновременно жанр и техника, и это не ошибка составителя списка.
  Две метки получали один адрес. Теперь вид входит в адресное имя.

**Ограничения**

- Записи в базу нет — только чтение. Создание и правка появятся
  на шаге 5.5 вместе с редактором: писать их сейчас значило бы оставить
  в проекте код, которым никто не пользуется.
- Видео и файлы к демо-разборам не создаются, их место займут настоящие
  на 5.4. Части при этом размечены таймкодами — подсчёт длительности
  проверяется.
- Сортировка «от простого к сложному» досчитывается в приложении:
  у песни несколько уровней сразу, база одной колонкой это не отсортирует.
  На странице из 24 карточек незаметно.
- Полиморфные привязки меток и материалов не защищены внешним ключом.
  Уборка осиротевших записей — обязанность удаляющего кода.

**Проверено**

- Сборка, типы, линтер, форматирование, **352 теста** — проходят.

### Этап 4 — Личный кабинет

#### 4.4 — Настройки личного кабинета

**Добавлено**

- Экран `/app/me/settings`: подписка, активные устройства, оформление,
  удаление аккаунта.
- Карточка подписки: состояние, источник, сколько дней осталось, кнопка
  продления, объяснение при недоступном Telegram.
- Список устройств с понятными подписями вместо строки браузера,
  закрытие одного устройства и «выйти на всех остальных».
- Распознавание устройств (`identity/devices.ts`) — 19 тестов.
- Удаление аккаунта с обезличиванием и подтверждением словом.
- Защита последнего владельца: `isLastOwner` в модуле прав.
- Настройка платформы «ссылка на продление подписки» — владелец сможет
  поправить её сам, когда появится экран настроек (Этап 9).
- Действие `account.delete` в журнале.

**Решения**

Подробно — [ADR-0011](adr/0011-account-deletion.md).

- **Удаление аккаунта — обезличивание, а не стирание строки.** Физическое
  удаление разрушило бы журнал и историю подписки, включая записи
  о действиях других людей. Пометка «удалён» без изменения данных —
  не удаление, а сокрытие. Поэтому личные сведения затираются
  по-настоящему, а строка остаётся якорем для связей.
- **Способы входа удаляются.** Иначе идентификатор Telegram остался бы
  занят, и вернувшийся в клуб человек упёрся бы в свой же удалённый
  аккаунт вместо чистого нового.
- **Про подписку сказано до нажатия.** Платформа не может остановить
  списания — деньги идут через бота в Telegram. Человек, удаливший
  аккаунт в уверенности, что этим всё закончилось, обнаружил бы списание
  через месяц.
- **Подтверждение словом, а не галочкой.** Галочку «я понимаю» ставят
  не читая.
- **Последний владелец не может удалить себя.** Платформа без владельца
  чинится только руками в базе.
- **Текущее устройство в списке закрыть нельзя.** Кнопка «выйти» живёт
  в меню профиля; дублировать её рядом с чужими сессиями — верный способ,
  чтобы человек, спасающийся от чужого входа, выбросил сам себя.
- **Настроек уведомлений нет, и это не забывчивость.** Платформа пока
  ничего не отправляет; переключатели для несуществующих уведомлений
  выглядели бы работающими и вводили в заблуждение. Раздел показывает
  честную заметку и появится вместе с самими уведомлениями (Этап 10).
- **Хеш адреса считается одной функцией** для сессий и для журнала: два
  разных способа означали бы, что записи о входе и о действии нельзя
  сопоставить при разборе спорного случая.

**Ограничения**

- История списаний не показывается: платежи идут в боте, и неполная
  картина у нас разошлась бы с настоящей.
- Подписи устройств приблизительны: браузеры представляются друг другом
  со времён, когда сайты проверяли поддержку Netscape. Точность здесь
  недостижима и не нужна — достаточно узнать своё устройство.
- Прогресс и заметки при удалении аккаунта пока не затрагиваются: их ещё
  нет. Решение о них принимается на Этапе 10 явно, а не наследуется молча.

**Проверено**

- Сборка, типы, линтер, форматирование, **279 тестов** — проходят.
- Миграция базы не нужна: новых полей нет.

**Решения**

Подробно — [ADR-0010](adr/0010-avatar-pipeline.md).

- **Картинка не проверяется, а пересобирается.** Проверять присланный
  файл бессмысленно: расширение подделывается, заголовок формата
  присылает браузер, внутрь картинки дописывается что угодно. Исходный
  файл не сохраняется никогда — из него читаются только пиксели.
  Данные съёмки, включая координаты квартиры, до хранилища не доезжают;
  это закреплено тестом, а не обещанием.
- **Кадрирование делает браузер, окончательную сборку — сервер.**
  Заодно решается формат HEIC с айфонов, который сервер не понимает,
  а сам айфон понимает. И вместо снимка на 5–10 МБ уходит около 200 КБ.
- **В базе идентификатор фотографии, а не адрес.** Смена сети доставки
  не должна быть правкой строк у каждого участника.
- **Имя файла меняется при каждой замене**, поэтому кэширование
  разрешено на год. «Загрузил новое, а висит старое» невозможно.
- **Два размера, 128 и 512 точек.** На будущей странице участников это
  десять мегабайт против одного при каждом открытии.
- **Фотография из Telegram не подставляется** — решение владельца
  платформы, подтверждённое техникой: ссылка на снимок живёт
  на серверах мессенджера и перестала бы открываться при его
  недоступности, вопреки главному принципу платформы.
- **Свой кадратор вместо готовой библиотеки.** Готовая требует
  подключения своего файла стилей и прячет математику рамки там, где
  её нельзя покрыть тестами. Нужное взаимодействие — тридцать строк
  вычислений; вынесенные отдельно, они проверены целиком, включая
  главное свойство: рамка не выходит за край снимка ни при каком
  сочетании масштаба и сдвига.

**Найдено при разработке**

- Первая попытка получить прежний идентификатор фотографии одним
  запросом (`UPDATE ... RETURNING`) была ошибкой: PostgreSQL возвращает
  значение после изменения, а не до. Поймано на проверке кода, до запуска.
  Заменено явным чтением перед записью; расплата — при одновременной
  загрузке с двух устройств может остаться осиротевший файл.
- Тест на разбор формы падал, и правильно: `FormData` превращает в строку
  всё, что не является настоящим файлом, поэтому подделка в этом тесте
  проверяла не то. Заменена настоящим объектом.

**Зависимости**

- `sharp` — обработка изображений. Только на сервере; содержит машинный
  код под операционную систему, поэтому объявлена внешней для сборщика.

**Проверено**

- Сборка, типы, линтер, форматирование, **260 тестов** — проходят.

**Ограничения**

- Файлы прежней фотографии удаляются «по возможности»: при недоступном
  хранилище останется мусор на сорок килобайт и запись в журнале.
  Уборка осиротевших файлов появится вместе с медиатекой.
- Загрузка идёт без процентной шкалы — действия сервера её не дают.
  При двухстах килобайтах достаточно индикатора ожидания.
- Реестр файлов (`media_assets`) фотографиями профилей не заполняется
  намеренно: у них своя жизнь, и в медиатеке кураторов они были бы
  двумя с половиной сотнями лишних строк.
- Фотография лежит в публичном разделе хранилища: знающий точный адрес
  откроет её без входа на платформу. Имя файла неугадываемо; табы,
  материалы и видео остаются закрытыми.

#### 4.2 — Хранилище файлов

**Добавлено**

- Договор хранилища: один набор функций, за которым может стоять любой
  поставщик. Смена провайдера — новый файл и строка в настройках.
- Поставщик S3 (Selectel, Timeweb, Yandex Cloud) и поставщик «папка
  на диске» для разработки.
- Правила имён файлов и проверок загрузки, 17 тестов.
- Проверка настроек при запуске: половина настроек S3 или локальное
  хранилище в бою — приложение не стартует.
- Служебная раздача локальных файлов, в производственной сборке 404.

**Решения**

- **Два вида файлов с разным способом выдачи.** Публичные (аватары,
  обложки) отдаются напрямую из сети доставки с постоянным адресом
  и кэшируются браузером. Закрытые (табы, PDF) — только по ссылке
  с коротким сроком жизни, после проверки подписки. Постоянного адреса
  у них не существует, пересылать такую ссылку бесполезно.
- **Вид доступа — первым участком пути.** Правило доступа к хранилищу
  настраивается по префиксу, и файл, попавший не в ту папку, либо
  не откроется, либо откроется всем. Видно сразу, а не через месяц.
- **SVG не принимается и не будет.** Это документ с разметкой, внутри
  которого может лежать скрипт: он выполнится в браузере участника,
  открывшего чужой аватар. Для фотографий SVG не нужен.
- **Имя файла собирается на сервере, а не берётся от браузера.** `../`
  в названии уводит запись в чужую папку, вторая точка подменяет
  расширение. Обезвреживание покрыто тестами: если они упадут, защита снята.
- **Локальное хранилище в производственной среде запрещено проверкой.**
  Папка на диске исчезает при первом же обновлении платформы вместе
  со всеми аватарами и материалами.
- **Поставщик создаётся один раз.** Клиент S3 держит соединения; создавать
  его на каждый запрос — способ упереться в лимит сокетов на сервере
  с четырьмя гигабайтами памяти.
- **Размер проверяется до записи**, а не после: иначе оплачивается трафик
  за файл, который всё равно будет отвергнут.

**Найдено при разработке**

- Новая проверка настроек сразу уронила тест боевого набора переменных —
  ровно так, как задумано. Набор дополнен настройками хранилища,
  добавлены три теста на само правило.

**Зависимости**

- `@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner` — стандартный
  клиент, работает с любым S3-совместимым хранилищем. Только на сервере,
  в браузер не попадает.

**Проверено**

- Сборка, типы, линтер, форматирование, 214 тестов — проходят.

**Ограничения**

- Реестр файлов в базе (`media_assets`) пока не заполняется: хранилище
  умеет класть и отдавать, учёт появится вместе с первыми загрузками.
- Локальный поставщик не изображает подписанные ссылки: закрытый файл
  отдаётся так же, как публичный. Проверять поведение подписей нужно
  на боевом хранилище.
- Публичный доступ к папке `public/` в хранилище настраивается вручную
  в панели провайдера — это разовое действие при развёртывании.

#### 4.1 — Профиль

**Добавлено**

- Страница профиля: имя, город, год начала игры, уровень, любимые
  исполнители, жанры, о себе, ссылки. Сохранение с разбором ошибок
  по полям.
- Личный кабинет `/app/me` — вход в личные разделы. Нужен из-за телефона:
  там «Я» ведёт сюда, а бокового меню с подразделами нет.
- Поля `favorite_artists` и `favorite_genres` в таблице участников,
  миграция `0002_profile_fields`.
- Компоненты дизайн-системы: `Avatar`, `ChipsInput`, `ToggleGroup`.
- 17 тестов правил профиля.

**Решения**

- **Аватар без фотографии — нейтральный силуэт.** По решению владельца
  платформы фото из Telegram не подставляется. Первая буква имени
  выглядела бы как аватар, который человек не выбирал, пустой круг —
  как поломка интерфейса.
- **Жанры выбираются из списка, исполнители вводятся свободно.**
  Свободный ввод жанров дал бы «рок», «Рок» и «rock» как три разных,
  и подбор материалов по жанру перестал бы работать в тот же день.
  Список исполнителей, наоборот, бесконечен и заранее не составляется.
- **Список ссылок закрытый (ВКонтакте, YouTube, сайт).** Произвольные
  адреса в профиле закрытого клуба — способ размещать рекламу и уводить
  участников на сторону. Telegram не нужен: он известен из способа входа.
- **Идентификатор человека берётся из сессии, а не из формы.** Иначе
  любой желающий переписал бы чужую карточку, подставив другой номер.
  Правка чужих профилей — отдельное право, Этап 9.
- **Свой профиль сразу показывается формой,** без режима просмотра
  и кнопки «Редактировать»: свою карточку открывают затем, чтобы
  что-то поправить.
- **Правила проверки живут в модуле, а не в форме.** Проверка в браузере
  сообщает об ошибке раньше, настоящая всегда происходит на сервере.
- **Незаполненные ссылки не хранятся.** Пустая строка в базе — мусор,
  который потом пришлось бы отличать от «не указано» в каждом запросе.

**Найдено при разработке**

- **Тест поймал ошибку в схеме ссылок:** словарь с ключами из списка
  требовал присутствия всех ключей сразу, и профиль без единой ссылки
  не сохранялся бы. Заменено перечислением необязательных полей.
- **Сборка поймала ловушку, о которой предупреждает сам модуль:**
  клиентская форма импортировала публичный вход `identity`, а он тянет
  серверный код. Тип профиля перенесён в чистый файл `profile.ts`, форма
  берёт правила оттуда. Проверками до сборки это не ловится — только
  `pnpm build`.

**Проверено**

- Сборка, типы, линтер, форматирование, 193 теста — проходят.

**Ограничения**

- Аватар показывается, но не загружается — шаг 4.3.
- Профиль виден только владельцу: публичные карточки участников —
  Этап 8.
- Разделы «Прогресс», «Избранное», «Заметки» в кабинете — заглушки,
  им нужны данные с этапов 5–7.

### Этап 3 — Навигация

#### 3.4 — Главная страница

**Добавлено**

- Главная как список независимых блоков: приветствие, состояние подписки,
  переходы в чаты Telegram, «платформа наполняется».
- Сервис настроек платформы (`app_settings`): ссылки на чаты правятся
  без разработчика. Значения по умолчанию добавлены в `pnpm db:seed`.
- Часовой пояс клуба в продуктовых настройках, 5 тестов приветствия.

**Решения**

- **Главная собирается из блоков, а не пишется одной страницей.** Каждый
  блок — файл, сам берёт данные и сам решает, показываться ли. Добавить
  «Продолжить» на Этапе 5 — создать файл и вписать строку; переделывать
  страницу не придётся.
- **Блоков четыре, а не семь из PRD §5.1.** Остальным нужны разборы,
  эфиры и прогресс, которых пока нет. Собирать их на выдуманных числах
  значит переписать дважды, а участник всё равно увидел бы пустые полки.
- **Карточка подписки показывается, только когда есть что сказать.**
  Человеку с действующей подпиской напоминание не нужно: оно занимает
  первый экран и приучает не читать сообщения платформы.
- **Ссылки на чаты — в настройках, а не в коде.** Сообщество переезжает
  между чатами, и ради этого не должен требоваться разработчик.
- **Отсутствие настройки — не ошибка.** Возвращается значение
  по умолчанию, недоступная база не валит главную целиком. Платформа
  обязана работать на чистой базе.
- **Приветствие считается по времени клуба, а не устройства.** Страница
  собирается на сервере; перенос в браузер потребовал бы рисовать
  приветствие дважды. Цена — одно слово у десятка участников за рубежом.
- **Блок «платформа наполняется» временный,** снимается на Этапе 7.
  Пустой первый экран читается как «платформа не работает», честное
  «вот что здесь будет» — как «идёт работа».
- **Крошек на главной нет:** вести с главной на главную незачем.

**Решено на будущее (Этап 5)**

- «Песни недели» — не сортировка, а **подборка**: кураторский набор песен
  с названием и двумя переключателями, «показывать в каталоге»
  и «показывать на главной». Одним механизмом закрываются и песня недели,
  и быстрые пресеты каталога из PRD v0.1 §5.2. Подробнее — DECISIONS.md.

**Проверено**

- Сборка, типы, линтер, форматирование, 176 тестов — проходят.

**Ограничения**

- Ссылки на чаты в сиде — заглушки `https://t.me/`. Настоящие подставляет
  владелец; экран редактирования появится на Этапе 9.
- Блок подписки для владельца не показывается никогда: у него доступ
  выдан вручную и бессрочно.

#### 3.3 — Навигационная цепочка и единый заголовок страницы

**Добавлено**

- Хлебные крошки на всех вложенных страницах (PRD v0.1 §3.2). На телефоне
  вместо полной цепочки — один крупный переход наверх.
- `PageIntro` — единый верх страницы: путь, заголовок, описание, место
  под кнопки. Правило: каждая страница закрытой зоны начинается с него.
- Реестр разделов и построение цепочки из адреса страницы, 12 тестов.
- Поля страницы заданы в разметке закрытой зоны, а не на каждой странице.
- Все 39 заглушек закрытой зоны переведены на новый заголовок.

**Решения**

- **Цепочка строится из адреса, а не задаётся на странице руками.**
  Заданный вручную путь врёт при первом же переносе страницы: адрес
  поменялся, а путь остался старым, и по коду это не видно.
- **Название конечной страницы приходит от неё самой.** Реестр не может
  знать, что `nothing-else-matters` называется «Nothing Else Matters».
- **Тест сверяет реестр с меню.** Переименовали «Разборы» в меню — крошки
  не могут остаться со старым словом. Расхождение здесь означает, что
  человек считает меню и путь разными разделами.
- **На телефоне показывается один шаг назад, а не вся цепочка.** Путь
  из четырёх звеньев занимает на узком экране две строки и вытесняет
  заголовок за пределы первого экрана.
- **`PageIntro` — клиентский компонент.** Единственная причина: адрес
  текущей страницы, которого серверные компоненты не знают. Кнопки
  в `actions` остаются серверными.
- **Поля страницы — в разметке, а не на страницах.** Иначе через три
  этапа отступы разъедутся, и это будет видно при переходе между
  разделами.
- **Заглушка закрытой зоны отделена от заглушки открытой.** Крошки — это
  знание о структуре платформы, а дизайн-системе такое знание запрещено.
  Общая часть («появится на этапе N») вынесена в `StageNote`.

**Найдено при разработке**

- Тест согласованности с меню сразу нашёл два места, где пункт меню ведёт
  на адрес собственного раздела: «Эфиры → Записи» и «Управление → Обзор».
  Это не ошибка, а вкладка внутри раздела — правило сверки уточнено,
  случай задокументирован в тесте.
- Строгие настройки типов (`exactOptionalPropertyTypes`) потребовали явно
  объявить необязательные свойства компонентов, которые передаются
  насквозь. Поправлено в `PageHeader`, `Breadcrumbs`, `StageNote`.

**Проверено**

- Сборка, типы, линтер, форматирование, 171 тест — проходят.

**Ограничения**

- Названия сущностей в середине пути (модуль курса на странице урока)
  подставляются через `crumbTitles`, но пока негде: данных нет. Появятся
  на этапах 5–6.
- Заголовок вкладки браузера по-прежнему задаётся на каждой странице
  отдельно. Свести его к реестру можно будет, когда страницы получат
  настоящие данные и `generateMetadata`.
- Проверить крошки в браузере можно только с поднятой базой: закрытая
  зона требует сессии.

#### 3.2 — Режим «смотреть как участник»

**Добавлено**

- Режим просмотра платформы глазами обычного участника: раздел
  «Управление», кнопки редактирования и черновики скрываются, из аккаунта
  выходить не нужно (PRD v0.3 §4.3).
- Полоса вверху экрана с кнопкой возврата. Прилипает к верху вместе
  с шапкой и боковым меню, которые на её высоту сдвинуты.
- Меню профиля в шапке: имя, профиль, настройки, режим просмотра,
  оформление, выход.
- `getViewer` — единая точка «кто передо мной и что ему можно» для всей
  закрытой зоны. Единственное место, где применяется маска режима.
- Правило линтера: обращаться к правам в обход `getViewer` внутри
  `src/app/` — ошибка сборки.
- Модуль `audit`: запись действий в журнал. Вход и выход из режима
  фиксируются.
- Проверка прав в разметке раздела «Управление» — раньше её там не было.
- 15 тестов правил режима.

**Решения**

- **Состояние режима — в cookie браузера, а не в базе.** Режим привязан
  к устройству: куратор проверяет вид страницы на телефоне, оставаясь
  в управлении на ноутбуке. В базе включение на телефоне переключило бы
  и ноутбук.
- **Cookie сеансовая.** Закрыл браузер — режим сброшен. Иначе человек
  назавтра полдня удивляется, куда делись его кнопки.
- **В режиме прав не остаётся вовсе, а не «убраны управляющие».**
  У обычного участника ролей нет — пустой набор буквально и есть
  «глазами участника». Список исключений пришлось бы поддерживать вручную
  при каждом новом праве, и однажды его забыли бы пополнить.
- **Режим только отнимает права и никогда не добавляет.** Отсюда следует,
  что состояние можно держать в браузере: подделанная cookie даёт меньше
  возможностей, а не больше. Ни одна проверка доступа от этого не слабеет.
- **Серверные действия проверяют настоящие права, а не маскированные.**
  Безопасность не должна зависеть от значения, которое задаёт браузер, —
  даже когда зависимость безобидна. Через год кто-нибудь повторит приём
  там, где он уже небезобиден.
- **Единая точка вместо проверки в каждой странице.** Сейчас скрывать
  нечего — контента нет. Через три этапа кнопки редактирования будут
  на странице песни, эфира, урока и карточки куратора, а черновики —
  в каталоге, списке эфиров и дереве курса. Обойти двадцать мест и нигде
  не забыть уже не выйдет, а забытое место означает ровно то, ради чего
  режим и делается.
- **Раздел «Управление» в режиме показывает объяснение, а не редирект.**
  Человек нажал на закладку; молчаливое перенаправление на главную
  выглядит поломкой.
- **Запись в журнал не роняет действие.** Сбой записи уходит в журнал
  приложения. Обратный порядок означал бы, что временная проблема с базой
  останавливает работу клуба ради строчки истории.

**Найдено и исправлено**

- **На телефоне нельзя было переключить тему.** Переключатель стоял
  в шапке с `hidden md:inline-flex`, других мест выбора не было.
  Вечерние занятия с телефона — основной сценарий, а тёмная тема, скорее
  всего, станет главной. Переехал в меню профиля, доступное везде.
- **Раздел `/app/manage/*` был открыт любому вошедшему.** В его разметке
  стоял комментарий «проверка прав появится на Этапе 2» — она не появилась.
  Сейчас там заглушки, поэтому не утекло ничего, но до появления
  содержимого дыру надо было закрыть.
- **Конфликт маршрутов на `/auth/telegram`.** Рядом лежали заглушка
  `page.tsx` из шага F1 и настоящий обработчик `route.ts` из шага 2.3 —
  сборка падала. Заглушка удалена.
- **`pnpm-lock.yaml` отставал от `package.json`** на зависимость
  `lucide-react`, добавленную на шаге 3.1. Установка с `--frozen-lockfile`
  (режим по умолчанию на сервере сборки) падала. Файл обновлён.
- Удалены временные элементы шагов 2.2 и 2.4 — `session-indicator`
  и `subscription-badge`. Их работу забрала шапка, сами файлы остались.

**Проверено**

- Сборка, типы, линтер, форматирование, 159 тестов — проходят.
- Приложение поднимается, страницы отвечают, посторонний с закрытой
  страницы уходит на вход с сохранением адреса.

**Ограничения**

- Скрывать пока нечего: контента нет. Проверить режим можно по разделу
  «Управление» и пунктам меню — настоящая ценность включится на Этапе 5
  вместе с черновиками.
- «Посмотреть как участник без подписки» не делается: это другой режим
  с другим поведением, смешивать их в одной кнопке — верный способ
  получить куратора, не понимающего, куда делся доступ к курсу.
- Раздел «Управление» проверяет права грубо: «есть хотя бы одно
  управляющее право». Проверка каждой страницы отдельно — Этап 9, вместе
  с их содержимым.
- Экран журнала действий не сделан: записи пишутся, читать их пока можно
  только запросом к базе. Экран — Этап 9.
- Аватар в меню профиля — первая буква имени. Фотография появится
  на Этапе 4 вместе с загрузкой своей.

#### 3.1 — Оболочка платформы

**Добавлено**

- Боковое меню на компьютере с раскрытием подразделов у активного пункта.
- Нижняя панель на телефоне: пять разделов, кнопки от 44 пикселей.
- Шапка с названием, состоянием подписки, переключателем темы и выходом.
- Структура навигации данными (`_lib/navigation.ts`) + 10 тестов.
- Пункты «Управления» фильтруются по правам на сервере.
- Временная навигация каркаса удалена.
- Зависимость `lucide-react` для иконок.

**Решения**

- **Навигация задана данными, а не разметкой.** Один список рисуют
  и сайдбар, и мобильная панель. Иначе они разъедутся, и на телефоне
  появится пункт, которого нет на компьютере.
- **Пять разделов, потому что столько помещается в мобильную панель.**
  Это не следствие дизайна, а его причина: больше пяти кнопок нельзя
  уверенно нажать пальцем, значит и разделов пять (PRD v0.1 §0, пункт 3).
- **Меню фильтруется на сервере.** Браузер не получает даже названий
  разделов, которые человеку недоступны. Это удобство, а не защита:
  каждая страница управления проверяет права отдельно.
- **Раздел «Управление» не показывается, если внутри нет ни одного
  доступного пункта** — иначе человек попадёт туда, где ему нечего делать.
- Тема по умолчанию — системная: платформа не спорит с настройкой телефона.

**Найдено и исправлено при проверке в браузере**

- У владельца в «Управлении» тринадцать пунктов, и меню не помещалось
  на экран ноутбука — нижние пункты обрезались без возможности прокрутки.
  Меню прилипает под шапкой и прокручивается отдельно от страницы.
- **На телефоне кураторы не могли попасть в «Управление» вообще:**
  бокового меню там нет, а в мобильную панель раздел не входит.
  Вход добавлен в шапку — публиковать разборы с телефона будут.

**Ограничения**

- Хлебные крошки и единый заголовок страницы — шаг 3.3.
- Главная пока остаётся заглушкой: наполнять её нечем до появления
  разборов и эфиров. Структура и пустые состояния — шаг 3.4.

### Этап 2 — Авторизация

#### 2.6 — Разграничение доступа

**Добавлено**

- Проверка сессии в разметке закрытой зоны: посторонний уходит на вход,
  а адрес, куда он шёл, сохраняется.
- Проверка подписки в разметке платных разделов — обучение и эфиры.
- Настоящий экран «Подписка закончилась» вместо заглушки.
- Правило `requiresActiveSubscription` с 5 тестами.
- Проверки собраны в `src/app/app/_lib/guards.ts`.

**Решения**

- **Проверки живут в слое приложения, а не в модуле.** Здесь встречаются
  три модуля — вход, права и подписка, — и решается, что показать человеку.
  Кроме того, перенаправление — понятие Next.js: знай о нём модули,
  их нельзя было бы использовать в фоновых задачах.
- **Проверка подписки не в общей разметке, а в разделах.** Участник
  без подписки не теряет профиль, прогресс, избранное и страницы клуба.
  Это прямо влияет на возвращение: заглянув через полгода, человек видит
  «ты остановился на уроке 7», а не пустоту с предложением
  зарегистрироваться заново (PRD v0.1 §2.2).
- **Список платных разделов задан явно, а не «всё кроме».** Новый раздел
  по умолчанию окажется открытым, и это заметят сразу. Обратная ошибка —
  случайно закрыть профиль или саму страницу продления — дала бы кольцо
  перенаправлений, из которого человек не выберется.
- **Экран продления уводит обратно того, у кого подписка действует.**
  Попав туда по старой ссылке, человек не должен решить, что доступ пропал.

**Проверено в браузере на живой базе**

| Кто | Главная | Профиль | Клуб | Разборы | Курс | Эфиры |
| --- | --- | --- | --- | --- | --- | --- |
| Без входа | вход | вход | вход | вход | вход | вход |
| С подпиской | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Без подписки | ✅ | ✅ | ✅ | продление | продление | продление |

Адрес, куда шёл человек, сохраняется при перенаправлении на вход.

**Ограничения**

- Разграничение пока по разделам, не по отдельным материалам. Каталог
  разборов закрыт целиком, хотя PRD допускает показ списка без плеера.
  Точная настройка появится на Этапе 5 вместе с самими материалами:
  раньше её не на чем проверять.

#### 2.4 — Подписка: состояние доступа

**Добавлено**

- Таблица `channel_memberships` — сырые факты о членстве в закрытом канале,
  с ключом по идентификатору Telegram.
- Конечный автомат подписки `entitlement-policy.ts` — 28 тестов на все
  переходы, включая полный жизненный путь участника.
- Сервис подписок: пересчёт состояния, ручная выдача и отзыв,
  восстановление доступа по накопленным фактам, журнал событий.
- Фоновая задача закрытия доступа с истёкшим сроком, каждую ночь в 3:00.
- Состояние подписки видно в закрытой зоне.
- Миграция `0001_channel_memberships`.

**Решения**

- **Членство в канале хранится отдельно от участников платформы.**
  Человек оплачивает подписку, Tribute добавляет его в канал, Telegram
  присылает событие — а аккаунта на платформе ещё нет, он ни разу
  не заходил. Привязывать такое событие к участнику не к чему, и обычно
  его просто теряют: человек, впервые открыв платформу, видит
  «подписки нет», хотя деньги заплачены. Отдельная таблица с ключом
  по Telegram ID снимает вопрос — факт сохраняется всегда, а при первом
  входе доступ вычисляется из накопленного.
- **Выход из канала даёт льготный период, а не мгновенную потерю доступа.**
  Семь дней покрывают потерянное уведомление, задержку платежа и отпуск.
- **Повторный выход не продлевает льготный период.** Иначе доступ можно
  было бы продлевать бесконечно, входя и выходя из канала.
- **Действующая ручная выдача сильнее автоматики, а ручной отзыв — нет.**
  Ручной отзыв означает «отменить ошибочную выдачу», поэтому человек,
  честно оплативший подписку после отзыва, доступ получит. Для постоянной
  блокировки нарушителя есть отдельный механизм — право `users.ban`.
  Смешивать наказание с подпиской нельзя: иначе оплата снимала бы блокировку.
- **Истёкшая ручная выдача уходит в льготный период, а не в отказ** —
  человек не должен потерять доступ посреди урока.

**Найдено и исправлено при проверке на живой базе**

- **Публичный вход модуля `identity` тянул за собой код Next.js**
  (cookie, серверные действия). Из-за этого процесс фоновых задач
  не смог бы запуститься на боевом сервере — а обнаружилось бы это
  только при развёртывании. Всё, что требует контекста запроса, вынесено
  из `index.ts` и импортируется явным путём, как `env.server` и клиент
  Telegram.
- **Модули `identity` и `subscription` ссылались друг на друга по кругу.**
  Идентификатор Telegram теперь приходит в подписки аргументом: подписки
  ничего не знают о способах входа.
- **Доступ не восстанавливался автоматически при первом входе** — сверку
  надо было звать руками. Встроена в сам вход: теперь любой способ входа
  получает её бесплатно.

**Проверено на живой базе PostgreSQL**

- Полный путь: оплатил → отменил → льготный период → вернулся → ручной
  отзыв → оплатил снова → ручная выдача на 30 дней. Все переходы верны,
  журнал событий полон.
- Оплата до регистрации: событие сохранено без аккаунта, при первом входе
  доступ выдан сразу.

**Ограничения**

- Уведомления от Telegram пока не принимаются: события подаются вручную.
  Вебхук и ночная сверка — шаг 2.5.
- Закрытые страницы пока не проверяют подписку. Разграничение — шаг 2.6.

#### 2.3 — Вход через Telegram

**Добавлено**

- Страница входа `/` с виджетом Telegram и понятными сообщениями об отказе.
- Обработчик возврата `/auth/telegram`: проверка подписи, создание участника
  при первом входе, открытие сессии, перенаправление внутрь платформы.
- `telegram-login.ts` — что делать с человеком, чья подлинность доказана:
  найти, создать, обновить сведения, при необходимости назначить владельцем.
- Выдача ролей в модуле прав: `grantRoleByCode`, `hasAnyRole`.
- `return-to.ts` с 7 тестами — куда возвращать человека после входа.
- Новичок после первого входа попадает на знакомство, остальные —
  туда, куда шли до перенаправления на вход.

**Решения**

- **Виджет работает через перенаправление, а не через обратный вызов
  в браузере.** Данные попадают сразу на сервер и не проходят через код
  страницы, где их было бы легче подменить.
- **Закрыто открытое перенаправление.** Адрес возврата приходит параметром
  из middleware. Если принимать его как есть, ссылка вида
  `/?next=https://похожий-сайт.ru` уведёт человека на чужую страницу
  сразу после успешного входа — и выглядеть это будет нормально, ведь
  он только что вошёл на настоящем сайте. Принимаются только внутренние
  адреса; отдельно отсекаются формы `//сайт` и `/\сайт`, которые выглядят
  внутренними, но уводят наружу.
- **Ограничение частоты проверяется до подписи.** Перебор упирается в лимит,
  не нагружая проверку подписи и базу.
- **Имя и фотография участника не перезаписываются при каждом входе.**
  Человек мог поменять их на платформе осознанно. Обновляется только копия
  данных Telegram — она нужна для поддержки.
- **Роль владельца выдаётся один раз и только при отсутствии любых ролей.**
  Защита от возврата роли тому, у кого её осознанно забрали. Дальше права
  меняются в интерфейсе, а не через файл настроек.
- Причина отклонённой подписи наружу не сообщается: она полезна только тому,
  кто подбирает подпись. Исключение — устаревшие данные, там человеку надо
  просто нажать кнопку ещё раз.

**Ограничения**

- Виджет Telegram работает только на домене, привязанном к боту через
  `/setdomain` у @BotFather. На `localhost` кнопка не появится — там
  используется служебный вход.
- Подписка пока не проверяется: вошедший получает доступ ко всей закрытой
  зоне. Появится на шагах 2.4–2.6.

#### 2.2 — Серверные сессии

**Добавлено**

- Полный жизненный цикл сессии: открытие, распознавание, продление,
  закрытие, закрытие всех устройств, список устройств.
- `hashing.ts` — создание ключей сессии и хеширование с секретом приложения.
- `session-policy.ts` — правила жизни сессии чистыми функциями.
- Cookie сессии, чтение сведений о запросе, хеширование IP.
- Служебная страница входа `/dev/login` для разработки.
- Указатель текущего человека с кнопкой выхода в закрытой зоне.
- Фоновая задача уборки мёртвых сессий, каждую ночь в 3:30.
- 25 тестов: отзыв, истечение, продление, лимит устройств, хеширование.

**Решения**

- **Ротации ключа сессии нет**, хотя PRD v0.1 §7.2 её предполагал.
  Ротация решает проблему JWT, который нельзя отозвать. Серверная сессия
  отзывается мгновенно (ADR-0003), поэтому ротация не даёт ничего,
  а гонки между вкладками браузера создаёт.
- **Кэша сессии с временем жизни нет**, хотя для прав доступа он есть.
  Кэш означал бы, что закрытая сессия ещё полминуты работает, — и главное
  преимущество серверных сессий пропало бы. Вместо этого результат
  запоминается в пределах одной отрисовки страницы обёрткой `cache`
  из React: сколько бы компонентов ни спросили «кто вошёл», запрос к базе
  будет один. Это уточняет формулировку ADR-0003 о «кратковременном кэше».
- **Сессия продлевается не чаще раза в час.** Срок сдвигается на 90 дней,
  поэтому точность не нужна, а запись в базу на каждой открытой странице —
  лишняя.
- **IP-адреса хранятся только хешированными**: адрес — персональные данные.
  Хеш считается с секретом приложения, иначе короткие предсказуемые значения
  перебираются за минуты.
- **Лимит устройств закрывает самые давние сессии**, а не самые новые:
  человек, зашедший с нового телефона, не должен вылететь с того устройства,
  за которым сидит сейчас.
- Служебный вход защищён значением `NODE_ENV`, а не отдельной переменной
  окружения: чем меньше переключателей, тем меньше способов случайно
  оставить дверь открытой на боевом сервере.

**Исправлено при проверке**

- Сборка отклонила файл действий сервера: он может экспортировать только
  асинхронные функции, а проверка режима разработки синхронная.
  Вынесена в отдельный файл `dev-auth.ts`.

**Ограничения**

- Работа с живой базой в среде разработки автора не проверялась —
  PostgreSQL там нет. Код проверен типизацией, сборкой и тестами.

#### 2.1 — Работа с Telegram: проверка подписей и клиент Bot API

**Добавлено**

- `src/shared/telegram/verify.ts` — проверка подлинности данных от Telegram.
  Два алгоритма: виджет входа (ключ `SHA256(токен)`) и Mini App
  (ключ `HMAC(токен, "WebAppData")`). Функции чистые, токен передаётся
  аргументом — проверку можно тестировать, не поднимая приложение.
- `src/shared/telegram/client.ts` — единственное место в проекте, которое
  обращается к Telegram по сети: `getChatMember`, `sendMessage`, `setWebhook`,
  `getWebhookInfo`, `getMe`.
- `src/shared/telegram/membership.ts` — толкование статуса участника канала.
- `src/shared/telegram/types.ts` — типы Bot API, только используемые поля.
- 26 тестов: подмена данных после подписи, чужой токен, отсутствующая
  и укороченная подпись, устаревшие данные, дата из будущего, расхождение
  часов, испорченный JSON, все шесть статусов участника канала.

**Решения**

- **Срок свежести данных входа — 5 минут.** Подпись Telegram сама
  по себе не истекает: перехваченный ответ виджета можно предъявить
  и через месяц. Ограничение по времени — единственная защита
  от повторного использования.
- **Подписи сравниваются за постоянное время** (`timingSafeEqual`).
  Обычное сравнение строк завершается на первом несовпавшем символе,
  и по времени ответа подпись подбирается посимвольно.
- **Недоступность Telegram — не поломка, а ожидаемая ситуация.**
  Сетевые сбои превращаются в ошибку «внешний сервис недоступен»
  и отделены от осмысленного отказа Telegram (`TelegramApiError`).
  Только первое включает политику fail-open: во втором случае
  состояние подписки известно достоверно.
- **Список `allowed_updates` вынесен в константу** `REQUIRED_UPDATE_TYPES`
  и используется при регистрации вебхука. Причина в разделе ниже.
- **Статус `restricted` не означает выход из канала.** Различается полем
  `is_member`. Без этой тонкости ограничение прав в чате отбирало бы
  оплаченный доступ.
- Клиент не реэкспортируется из `index.ts`: он работает только на сервере
  и импортируется явным путём, как и `env.server.ts`.

**Ловушка, которую закрыли заранее**

- Telegram **не присылает уведомления `chat_member` по умолчанию** — только
  если тип явно перечислен в `allowed_updates` при регистрации вебхука.
  Это самая частая причина ситуации «код написан, вебхук зарегистрирован,
  событий нет», причём отказ молчаливый: ни ошибки, ни записи в журнале.
  Поэтому список задан константой в коде, а не параметром команды.

**Ограничения**

- Клиент пока никем не вызывается: пользователей и подписок ещё нет.
  Первое применение — шаг 2.3 (вход), затем 2.5 (вебхук и сверка).
- Повтор при ограничении частоты — однократный и только если Telegram
  просит подождать не дольше 5 секунд. Массовых обращений у нас нет:
  ночная сверка 250 участников идёт около десяти секунд.

- Без cookie обращение к `/app/**` даёт перенаправление 307 на страницу входа.

- С правильной cookie закрытая зона отдаёт 200.

**Известное ограничение**

- `AUTH_ENABLED=false` оставляет закрытую зону открытой. Развёртывание
  с таким значением сделает платформу публичной. Жёсткая проверка
  («в производственной среде обязано быть `true`») появится на шаге F2,
  до первого развёртывания на шаге F10.

#### F10 — Развёртывание и резервные копии

**Добавлено**

- `docker-compose.prod.yml`: три контейнера — база, сайт, фоновые задачи.
  Сайт и задачи собираются из одного образа с разными командами запуска.
- Миграции применяются перед стартом сайта: новая версия кода не должна
  работать со старой структурой базы.
- Порт базы наружу не публикуется: обращаться к ней могут только контейнеры
  из той же сети.
- `scripts/db-backup.sh` — ежедневная копия с отправкой в S3 и удалением
  локальных копий старше недели.
- `scripts/db-restore.sh` — восстановление с подтверждением.
- `docs/OPERATIONS.md` — развёртывание, обязательные настройки, проверка
  работоспособности, откат, разбор аварий, регулярные дела.

**Исправлено при проверке**

- Скрипт копирования сначала выгружал базу конвейером `pg_dump | gzip`.
  Оболочка возвращает код завершения последней команды, поэтому при падении
  выгрузки на сервере оказался бы исправный на вид архив с пустым
  содержимым — и обнаружилось бы это в день, когда копия понадобилась.
  Переписано на выгрузку во временный файл с тремя проверками: код возврата,
  размер, наличие хотя бы одной таблицы.

**Проведены учения по восстановлению**

- База стёрта полностью (0 таблиц).
- Восстановлена из копии: 16 таблиц, владелец с его Telegram ID,
  4 роли, 33 права, 101 связка роль-право — всё на месте.
- После восстановления миграции применяются, фоновые задачи запускаются.

**Что осталось за нами**

- Первое развёртывание требует VPS, домена и хранилища S3 — их пока нет.
  Все файлы для развёртывания готовы, отдельного шага разработки
  не потребуется.
- Отправка ошибок в Sentry — прослойка есть, подключение при появлении
  боевого сервера.

#### F8 — Фоновые задачи

**Добавлено**

- Очередь задач `pg-boss` — внутри той же PostgreSQL, без отдельного сервиса.
- Отдельный процесс `pnpm worker`, использующий те же модули, что и сайт.
- Задача-пульс раз в 5 минут: отличает «задач нет» от «процесс упал три дня
  назад, и никто не заметил».
- Расписания собраны в одном файле `src/worker/schedules.ts`.
- Корректная остановка: при выключении процессу даётся 10 секунд доделать
  текущую задачу, чтобы повтор не задвоил данные.

**Решения**

- Процесс задач отделён от сайта: перезапуск сайта не обрывает задачи,
  а перезагрузка кода при разработке не запускает их заново десятки раз.
- Загрузчик отделён от логики: переменные окружения надо прочитать до того,
  как загрузится модуль, который их читает, а импорты в JavaScript
  выполняются раньше кода.
- Процесс запускается с условием разрешения модулей `react-server`.
  Без него защита «только для сервера» ломает запуск вне Next.js — обнаружено
  при первом запуске.

**Проверено на живой базе**

- Очередь создаёт свои таблицы в отдельной схеме, не смешиваясь с данными.
- Задача по расписанию выполнилась сама.
- Процесс корректно останавливается по сигналу.

#### F6 — Ошибки и наблюдаемость

**Добавлено**

- Разделение ошибок на ожидаемые («не найдено», «нет прав») и настоящие
  поломки. Первые пишутся в журнал одной строкой, вторые — со стеком
  и отправкой в Sentry. Без разделения журнал за неделю заполняется шумом,
  и на оповещения перестают смотреть.
- Журнал `pino` с автоматическим сокрытием секретов и персональных данных:
  токены, ключи сессий, адреса почты и IP вырезаются на любом уровне
  вложенности. Полагаться на внимательность нельзя.
- Идентификатор запроса, который сам подставляется во все записи журнала:
  по одному коду из сообщения об ошибке видно всю цепочку событий.
- Понятные экраны ошибок вместо белого экрана. Показывают код происшествия —
  по нему причина находится в журнале за секунды.
- `LinkButton` — ссылка, выглядящая как кнопка. Отдельный компонент, потому
  что ссылку можно открыть в новой вкладке, а скринридер объявит её
  как переход, а не как действие.

**Ограничение**

- Отправка в Sentry — пока заглушка. Подключим при боевом развёртывании:
  собирать ошибки, пока приложение работает только на компьютере
  разработчика, бессмысленно. Прослойка уже есть, поэтому переписывать
  вызовы потом не придётся.

**Правила, зашитые в систему**

- На жёлтом только чёрный текст: белый даёт контраст 1,6:1 при требуемых 4,5:1.

- Высота кнопок и полей не меньше 44 пикселей: платформой пользуются
  с телефона, часто с гитарой в руках.
- Уровень сложности различается текстом, а не только цветом.
- Анимации отключаются, если человек выключил их в настройках системы.

**Исправлено**

- Проверка настроек при запуске разделена по средам выполнения:
  сборщик выдавал предупреждение, потому что код завершения процесса
  попадал в облегчённую среду, где его нет.

#### F4 — База данных

**Добавлено**

- Drizzle ORM и подключение к PostgreSQL с пулом соединений.
- Схема из 16 таблиц: пользователи и способы входа, сессии, роли и права,
  подписки и события Telegram, реестр медиафайлов, журнал действий,
  настройки, переключатели возможностей, уведомления.
- Первая миграция `0000_init_identity_access`.
- Справочник прав (33 права) и пресеты ролей (куратор, старший куратор,
  администратор, владелец) — описаны в коде, попадают в базу командой
  `pnpm db:seed`.
- Команды: `db:generate`, `db:migrate`, `db:seed`, `db:reset`, `db:studio`.
  Все повторяемые: применённые миграции пропускаются, справочники
  обновляются, а не дублируются.
- Проверка доступности базы в `/api/health`: приложение, которое отвечает,
  но не видит базу, для участников бесполезно.
- `docs/DATABASE.md` — устройство базы, соглашения, порядок изменения таблиц.

**Решения**

- Идентификаторы (UUID версии 7) вычисляет приложение, а не база.
  Встроенная функция `uuidv7()` появилась только в PostgreSQL 18, и привязка
  к ней потребовала бы обновления базы на всех окружениях.
- Правило «модуль не лезет во внутренности соседа» дополнено исключением
  для `schema.ts`: внешние ключи между таблицами по своей природе пересекают
  границы модулей.
- Сборщик схемы `src/shared/db/schema.ts` — единственный файл, которому
  разрешено знать обо всех модулях. Это «точка сборки», без неё инструмент
  миграций не увидит таблицы.

**Проверено на живой базе**

- Миграции применяются, создаются все 16 таблиц.
- Повторный запуск миграций и заполнения ничего не дублирует.
- Права владельца доходят до него сквозным запросом через роли.
- `pnpm db:reset` пересоздаёт базу с нуля.
- `/api/health` отвечает 200 при работающей базе и 503 при остановленной.

#### F2 — Настройки и переменные окружения

**Добавлено**

- Проверка переменных окружения при запуске (`zod`). Приложение с неверными
  настройками не запускается и печатает, какой переменной не хватает,
  что это такое и где её взять.
- Связанные правила, которые нельзя выразить проверкой одного поля:
  на боевом сервере проверка входа обязана быть включена, адрес обязан быть
  по `https`, подключение к базе обязано быть задано; при включённом входе

  защищены пакетом `server-only`), публичные (`env.client.ts`) и продуктовые
  (`app.config.ts` — срок сессии, льготный период, размер страницы каталога).
- Команда `pnpm env:check` — проверка `.env` без запуска приложения,
  с сокрытием значений секретов.
- Понятные описания всех переменных (`env.descriptions.ts`), которые
  показываются в сообщении об ошибке.
- `tsx` для запуска служебных скриптов на TypeScript. Понадобится также

**Закрыто**

## Сборка проекта из архивов шагов (19 августа 2026)

Проект собран в единое целое из полного среза 6.1 и 27 последующих
архивов шагов, наложенных в хронологическом порядке. Порядок определялся
по датам файлов внутри архивов, а не по номерам шагов: шаги 4.5 и 4.6
выполнялись позже шага 9.7.

### Слияние двух разошедшихся ветвей

Шаги 4.5 (правовые документы) и 4.6 (знакомство) велись отдельно
от десятого этапа и не были слиты. Восстановлено вручную:

- `shared/config/app.config.ts` — возвращён блок `operator` с реквизитами
  для правовых документов;
- `shared/db/schema.ts` — подключён модуль `legal`; без этого таблица
  согласий не создавалась в базе;
- `drizzle/0016_legal_acceptances.sql` — миграция перевыпущена
  инструментом: файл существовал, но не был зарегистрирован в журнале
  миграций и потому никогда не применялся;
- `modules/songs` — возвращены `findStarterSongs` и `getStarterSong`
  (подбор первого разбора для нового участника);
- `me/settings` — возвращена карточка правовых документов.

### Исправлена ошибка на боевом пути

`/app/manage` отвечал 500. Причина: объект `Date` передавался как параметр
внутрь выражения `sql``​`` — там нет колонки, по типу которой драйвер мог бы
его преобразовать. Ошибку не видели ни проверка типов, ни тесты, ни линтер:
она возникала только при обращении к базе.

Добавлен `shared/db/params.ts` с функцией `timestampParam` и объяснением
правила. Исправлены четыре места в `songs/editor-repository.ts`
и `streams/editor-repository.ts`.
