# ADR-0003. Серверные сессии вместо JWT

**Статус:** принято · **Дата:** 2026-08 · **Изменяет:** PRD v0.1 §7.2

## Контекст

В PRD была заложена связка «access-JWT на 15 минут + refresh-токен на 90 дней».
Это правильный выбор для распределённого API с несколькими серверами.
У нас один сервер и база данных на той же машине.

## Решение

Одна случайная строка-сессия в cookie (`httpOnly`, `Secure`, `SameSite=Lax`).
Её хеш хранится в таблице `sessions`. Срок — 90 дней, продлевается при активности.

|                            | JWT + refresh                | Серверная сессия               |
| -------------------------- | ---------------------------- | ------------------------------ |
| Отзыв доступа              | задержка до 15 минут         | мгновенно                      |
| Список устройств в профиле | требует отдельного механизма | получается само                |
| Объём кода                 | ~400 строк, легко ошибиться  | ~120 строк                     |
| Стоимость запроса          | 0                            | один индексный запрос, ~0,2 мс |

При 250 пользователях 0,2 мс не значат ничего, а мгновенный отзыв доступа
значит много: «увели аккаунт», «участник раздал доступ знакомым».

## Сопутствующее правило безопасности

Проверка прав **не** размещается в middleware Next.js.
Middleware выполняет только дешёвый редирект «нет cookie — на страницу входа».
Настоящая проверка происходит в слое доступа к данным, при каждом действии.

Причины две: middleware в Next.js уже имел уязвимость обхода (CVE-2025-29927,
март 2025), и архитектурно он не является границей безопасности —
до данных можно дойти путями, которые через него не проходят.

## Последствия

- Каждый запрос к закрытой зоне делает один запрос в БД. Смягчается
  кратковременным кэшем в памяти процесса.
- Сессии не переносятся между независимыми серверами без общей БД.
  При нашей архитектуре это не проблема.
