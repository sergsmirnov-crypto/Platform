# ADR-0010. Пересборка изображений на сервере и собственный кадратор

**Статус:** принято · **Дата:** 2026-08 · **Шаг:** 4.3

## Контекст

Участник загружает фотографию профиля. Позже так же будут загружаться
обложки разборов и эфиров. Нужно решить три вопроса: как файл попадает
на хранение, как его подготовить и как участник выбирает кадр.

Ограничения, из которых пришлось исходить:

- присланному файлу нельзя верить: расширение подделывается, заголовок
  формата присылает браузер, внутрь картинки дописывается что угодно;
- фотографии с телефона содержат данные съёмки, включая координаты;
- айфоны отдают снимки в формате HEIC, которого нет ни в одном
  распространённом наборе библиотек для сервера;
- аудитория пользуется платформой в основном с телефона.

## Рассмотренные варианты

### Как файл попадает в хранилище

**Прямая загрузка в хранилище по временной ссылке, минуя наш сервер.**
Правильный выбор для видео: файлы гигабайтные, и пропускать их через
приложение бессмысленно. Для фотографии профиля не подходит по решающей
причине: хранилище не проверяет содержимое. Файл с расширением `.jpg`
и скриптом внутри лёг бы на постоянный адрес в публичном разделе.
Пришлось бы добавлять обратный вызов, состояние «загружено, но ещё
не проверено» и уборку того, что проверку не прошло, — сложность
несоразмерна файлу на сорок килобайт.

**Загрузка через приложение с пересборкой.** Выбрано.

### Как обрабатывать

**Проверять и класть как есть.** Отвергнуто: проверка присланного
не решает ни одной из перечисленных задач. Данные съёмки остаются,
формат остаётся, лишние кадры остаются.

**Пересобирать заново.** Выбрано. Из файла читаются только пиксели,
на выходе — новый файл, собранный нами. Побочный эффект оказывается
главным: пересборка одновременно является и проверкой. Что не удалось
разобрать как изображение — не станет изображением на выходе.

### Чем кадрировать

**Готовая библиотека (`react-easy-crop`).** Распространённое решение,
но требует подключения собственного файла стилей и тянет ещё одну
зависимость. Главное возражение другое: математика рамки оказывается
внутри библиотеки, и проверить её тестами нельзя.

**Собственный кадратор.** Выбрано. Нужное взаимодействие — движение
и масштаб внутри квадрата — это около тридцати строк вычислений.
Вынесенные в отдельный файл, они покрываются тестами целиком, включая
главное свойство: рамка не выходит за край снимка ни при каком сочетании
масштаба и сдвига. Выход за край браузер рисует пустой полосой, то есть
ошибка выглядела бы как срезанный подбородок на аватаре.

Дополнительный довод: в проекте нет ни одной библиотеки готовых
элементов интерфейса — поля, переключатели, аватар, хлебные крошки
написаны свои. Одна чужая на весь проект выбивалась бы из кодовой базы
и обзавелась бы собственными правилами обновления.

## Решение

```
браузер                            сервер
────────                           ──────
выбор файла
  ↓ рисуется на холсте          ← заодно решается вопрос HEIC
кадрирование
  ↓ вырезается кадр, 1024 точки ← вместо 5–10 МБ уходит ~200 КБ
отправка (FormData)
                                   пересборка библиотекой обработки
                                     ↓ два размера, WebP
                                   запись в публичный раздел хранилища
                                     ↓
                                   идентификатор фотографии в базу
```

Сопутствующие решения:

- **В базе хранится идентификатор фотографии, а не адрес.** Адрес
  складывается из настроек хранилища; сохранённая ссылка сделала бы
  смену поставщика ручной правкой строк у каждого участника.
- **Два размера, 128 и 512 точек.** На странице участников будет две
  с половиной сотни фотографий: разница между размерами — десять
  мегабайт против одного при каждом открытии списка.
- **Имя файла меняется при каждой замене.** Позволяет разрешить
  кэширование на год: «загрузил новое, а висит старое» становится
  технически невозможным.
- **Публичный раздел хранилища.** Фотография профиля — сведения малой
  чувствительности, имя файла неугадываемо. Закрытая выдача означала бы
  отказ от кэширования и превращала список участников в две с половиной
  сотни обращений к нашему серверу.
- **Файл передаётся действием сервера, а не отдельным адресом API.**
  После кадрирования он маленький, а действие даёт единый разбор ошибок,
  журнал и ограничение частоты бесплатно. Двоичные данные едут внутри
  `FormData` — единственный способ, поддерживаемый при любой версии среды.

## Последствия

**Хорошее**

- Данные съёмки, включая координаты, до хранилища не доезжают.
  Свойство закреплено тестом.
- Формат на выходе всегда один, и остальная платформа не разбирается,
  что именно загрузил участник.
- Обработка изображений (`shared/images`) и кадратор (`ui`) не знают
  про аватары и переиспользуются для обложек.

**Плохое, принятое осознанно**

- Обработка занимает процессорное время нашего сервера. При двух
  с половиной сотнях участников, меняющих фотографию раз в несколько
  месяцев, это неизмеримо мало.
- Нет процентной шкалы загрузки: действия сервера её не дают.
  При двухстах килобайтах достаточно индикатора ожидания.
- Файлы прежней фотографии удаляются «по возможности». При недоступном
  хранилище в этот момент остаётся мусор на сорок килобайт и запись
  в журнале. Уборка осиротевших файлов появится вместе с медиатекой.
- Библиотека обработки содержит машинный код под конкретную
  операционную систему: образ приложения становится больше, а установка
  зависимостей — чуть дольше.

## Что бы отменило это решение

Если на платформу придут пользовательские загрузки в объёмах, при
которых обработка на своём сервере станет заметна — например, участники
начнут выкладывать видео своего исполнения, — конвейер переедет
в фоновые задачи, а для крупных файлов появится прямая загрузка
в хранилище по временной ссылке. Слой `shared/images` при этом остаётся:
меняется только то, кто и когда его вызывает.
