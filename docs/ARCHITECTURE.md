# Архитектура

Документ для разработчика, который открыл проект впервые.
Читать сверху вниз — примерно двадцать минут.

---

## 1. Что это за система

Закрытая платформа гитарного клуба: разборы песен, онлайн-курс, записи
эфиров, профили участников. Около 250 человек, из них десяток за рубежом.
Три куратора, не имеющих технического образования. Вход по коду на почту,
доступ по подписке, оформленной в Telegram.

**Ключевой продуктовый принцип:** платформа обязана работать при недоступном
Telegram. Мессенджер участвует ровно в двух местах — однократное подключение
к аккаунту и изменение статуса подписки. Входа на платформу он не касается
(ADR-0030), состояние подписки хранится локально.

```
│  └───────────────┬─────────────┘             │               │

        │                    │                    │
        ▼                    ▼                    ▼
  Telegram Bot API    Kinescope              S3 (табы, PDF,
  (подключение,       (видео + CDN)          аватары, бэкапы)
   вебхуки,
   уведомления)

  Почтовый сервер (SMTP): письма с кодом входа
```

**Видео и файлы никогда не проходят через наш сервер при чтении.** Мы
проверяем права, дальше браузер идёт напрямую в сеть доставки контента.
Поэтому небольшого сервера хватает при любом объёме просмотров.

При **записи** правило другое, и это осознанно: материалы, загружаемые
кураторами, идут через приложение. Три куратора и несколько файлов
в неделю не создают нагрузки, а прямая загрузка в хранилище потребовала
бы настройки CORS у поставщика и второго пути кода для локальной
разработки ([ADR-0016](adr/0016-file-uploads.md)). Видео не загружается
через нас никогда.

Проверка при этом устроена по-разному, и разница существенная:

|                 | Файлы (табы, минусовки)        | Видео                         |
| --------------- | ------------------------------ | ----------------------------- |
| Как отдаём      | подписанная ссылка на 15 минут | адрес плеера с ключом доступа |
| Кто проверяет   | мы, в момент нажатия «Скачать» | мы, но по запросу хостинга    |
| Когда проверяем | один раз, при выдаче ссылки    | при каждом воспроизведении    |

Для видео это означает, что подписка, закончившаяся после открытия страницы,
останавливает просмотр, а не доигрывает его до конца. Разбор —
[ADR-0014](adr/0014-video-playback-authorization.md).

Обоснование выбора каждой технологии — в [ADR-0001](adr/0001-tech-stack.md).

## 3. Правило зависимостей

Главное правило проекта. Всё остальное следует из него.

```
app/       маршруты и страницы    — тонкие, только «показать» и «вызвать сервис»
   ↓
modules/   бизнес-логика          — вся суть продукта живёт здесь
   ↓
shared/    инфраструктура         — БД, логи, ошибки, конфигурация
   ↓
(ничего)
```

Стрелки только вниз. `shared/` ничего не знает о модулях. `ui/` ничего
не знает о бизнес-логике.

**Правило проверяется линтером,** а не устной договорённостью:
попытка нарушить границу — ошибка сборки. Настройка — в `eslint.config.mjs`.

### Три модуля с серверным публичным входом

`identity`, `access` и `subscription` отдают наружу не только чистые
функции, но и запросы к базе. Их `index.ts` помечен `server-only`
косвенно — через `service.ts`, — и **браузерный компонент его импортировать
не может**: сборка падает десятками ошибок про Pages Router, в которых
настоящая причина не названа.

Правило для файлов с `'use client'`:

```
можно     import { toggleState } from '@/modules/access/team-rules'
можно     import { subscriptionStrings } from '@/modules/subscription/strings'
можно     import type { TeamMember } from '@/modules/access/team'   // типы стираются
нельзя    import { overridesLabel } from '@/modules/access'
```

У остальных модулей (`songs`, `streams`, `course`, `club`, `media`)
публичный вход чистый, и это правило к ним не относится.

Разнобой стоит однажды убрать, разделив вход на `index.ts` и `server.ts`.
Это заденет каждое место, где вызывается `requirePermission`, поэтому
делать это стоит отдельным шагом, а не попутно.

### Два задокументированных исключения

| Исключение                                           | Почему                                                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `src/shared/db/schema.ts` может импортировать модули | Это «точка сборки»: инструмент миграций должен видеть все таблицы сразу                              |
| Модуль может импортировать `schema.ts` соседа        | Внешние ключи между таблицами по своей природе пересекают границы модулей. База — общее пространство |

Оба исключения узкие и никуда не расширяются.

## 4. Анатомия модуля

Каждый модуль устроен одинаково — открыв любой, разработчик сразу понимает,
где что лежит:

```
src/modules/songs/
├─ schema.ts        описание таблиц
├─ types.ts         типы и схемы проверки данных
├─ repository.ts    запросы к БД — единственное место, где есть SQL
├─ service.ts       бизнес-правила
├─ permissions.ts   какие права нужны для каких действий
├─ actions.ts       точки входа с фронтенда
├─ strings.ts       тексты интерфейса
├─ components/      React-компоненты модуля
├─ index.ts         публичный API модуля
└─ __tests__/
```

Деление по предметным областям, а не по техническим слоям.
Обоснование — в [ADR-0004](adr/0004-modular-structure.md).

**Практическое следствие:** «удалить функциональность» — это удалить папку
и строку из меню, а не археология по всему проекту.

### Существующие модули

| Модуль          | Отвечает за                                 |
| --------------- | ------------------------------------------- |
| `identity`      | Пользователи, вход, сессии, модерация       |
| `access`        | Роли, права, проверка доступа               |
| `subscription`  | Подписки, вебхуки Telegram, сверка          |
| `media`         | Реестр видео и файлов, загрузка, выдача     |
| `songs`         | Разборы: песни, варианты, части, метки      |
| `course`        | Курс: модули, уроки, содержимое блоками     |
| `progress`      | Прохождение содержимого участником          |
| `streams`       | Эфиры: анонсы, записи, оглавление           |
| `taxonomy`      | Метки: жанры, техники, настроение           |
| `club`          | Кураторы, страницы о клубе                  |
| `audit`         | Журнал действий: запись и чтение            |
| `settings`      | Настройки платформы, правимые из интерфейса |
| `library`       | Личная библиотека: отложенное и заметки     |
| `notifications` | Уведомления: создание, доставка, настройки  |

Все запланированные модули созданы.

Модуль `library` намеренно ничего не знает о том, **что** отложено
и к чему написана заметка:
он хранит вид и идентификатор. Название разбора и адрес урока собирает
слой приложения (`app/app/_lib/library.ts`) — тем же приёмом, что
и кнопка «Продолжить». Так модуль не тянет за собой ни разборы, ни курс,
ни эфиры, а новый вид содержимого добавляется одной веткой `switch`.

### Правило, удерживающее модули без колец

**Модуль, у которого спрашивают права, не пишет в журнал сам.**

Журнал обязан спросить у `access` право `audit.view`. Значит, `access`
не может зависеть от журнала — иначе два модуля замкнутся в кольцо,
а кольцо при загрузке даёт пустые ссылки в самых неожиданных местах,
причём не всегда и не сразу.

Поэтому изменения ролей и прав записывает в журнал слой действий
(`app/app/manage/team/_actions/team.ts`), а модуль `access` возвращает
ему то, что изменилось. Так же устроены эфиры, курс и материалы —
это общий приём проекта, а не особый случай.

Остальные модули пишут в журнал сами: `identity`, `subscription`,
`songs`, `settings` прав у себя не проверяют и в кольцо не попадают.
Обоснование — в [ADR-0022](adr/0022-audit-write-direction.md).

Модуль `progress` стоит особняком: он ничего не знает о содержимом
и отвечает на один вопрос — что и насколько человек прошёл. Курс
пользуется им, соединяясь с его таблицей и применяя его чистые
функции; разборы и эфиры подключены так же
([ADR-0019](adr/0019-progress-model.md)). Кнопка «Продолжить» на главной
поэтому одинаково поднимает урок, разбор и недосмотренную запись эфира —
на каждый новый вид содержимого приходится одна ветка `switch`
в `app/app/_lib/resume.ts`.

### Право на странице управления

Каждый экран раздела «Управление» начинается с `requireManagePermission`
(`app/app/_lib/guards.ts`). Помощник отвечает на вопрос «пускать ли сюда»
одной строкой, возвращает смотрящего с уже суженным типом и уводит
на «страница не найдена», а не на «нет доступа»: человек попадает туда
только по прямой ссылке, и подтверждать существование раздела незачем.

Для страницы это полноценная защита — серверный компонент выполняется
на сервере. Но она не заменяет проверку в модуле: и чтение журнала,
и правка настроек начинаются с `requirePermission` внутри `audit`
и `settings`. Помощник закрывает интерфейс, модуль — данные.

### Кто видит неопубликованное

Модули содержимого не спрашивают права сами. Они принимают `ContentViewer`
из `shared/content` — `{ userId, canSeeDrafts }`, — который собирается
единственным способом: helper `getContentViewer` в слое приложения.

Причина в режиме «смотреть как участник»: он живёт в cookie, то есть
в слое приложения, и модуль о нём знать не может — тот же код работает
в процессе фоновых задач, где браузера нет. Модуль, спрашивающий права
напрямую, обходит маску режима и показывает куратору черновики ровно
тогда, когда тот проверяет, всё ли видно участнику. Так и случилось
на шаге 5.2; разбор — в [ADR-0013](adr/0013-song-page-and-file-delivery.md).

## 5. Как проходит запрос

### Открытие страницы

```
Браузер → Traefik → Next.js
   → middleware: есть ли cookie сессии? нет — редирект на вход
   → серверный компонент вызывает сервис модуля
   → сервис проверяет права и вызывает repository
   → repository делает запрос к PostgreSQL
   → готовая страница уходит в браузер
```

Отдельного API между фронтендом и бэкендом **нет** — они в одном процессе.
Это экономит целый слой кода и класс ошибок «фронт и бэк разошлись в типах».

### Действие пользователя

```
Форма → действие сервера (обёрнуто в defineAction)
   → проверка входных данных
   → requirePermission(...)
   → сервис → repository → PostgreSQL
   → запись в журнал действий
   → страница обновляется
```

Правила серверного слоя — в [API.md](API.md).

## 6. Безопасность

### Проверка прав — на сервере, всегда

**Правило без исключений:** любое действие, меняющее данные или отдающее
закрытое содержимое, начинается с `requirePermission`.

Скрытая в интерфейсе кнопка — это удобство, а не защита: обратиться
к серверу можно и минуя интерфейс.

### Middleware не является границей безопасности

Middleware выполняет только дешёвый редирект «нет cookie — на страницу
входа». Он не знает, действительна ли сессия, и не ходит в базу.

Причины две: у Next.js уже была уязвимость обхода middleware
(CVE-2025-29927, март 2025), и архитектурно до данных можно дойти путями,
которые через него не проходят. Подробнее — [ADR-0003](adr/0003-server-sessions.md).

### Модель прав

```
права всех ролей человека
+ персональные разрешения
− персональные запреты
─────────────────────────
= что человек реально может
```

Запрет всегда сильнее разрешения. У прав на редактирование есть область
действия: `own` (только свой контент) или `all`.

Вычисление — чистые функции в `src/modules/access/effective-permissions.ts`,
покрытые 16 тестами. Для модели прав это обязательно: ошибка означает
либо утечку доступа, либо заблокированного куратора.

### Одна дверь к правам: `getViewer`

Страницы закрытой зоны не спрашивают права у модуля напрямую. Они
обращаются к `src/app/app/_lib/viewer.ts` — тонкой прослойке слоя
приложения, которая знает две вещи: кто передо мной и что ему можно
показать прямо сейчас.

```
страница → getViewer() → права модуля access
                       → маска режима «смотреть как участник»
                       = то, чем пользуется интерфейс
```

Прослойка нужна из-за режима «смотреть как участник»: куратор может
одной кнопкой посмотреть платформу глазами обычного участника, и в этом
режиме прав у него не остаётся. Место применения маски должно быть ровно
одно — страница, забывшая про режим, покажет черновик именно тогда, когда
куратор проверяет, всё ли видно участнику.

Прямой импорт `can`, `canOn` и `getEffectivePermissions` внутри `src/app/`
запрещён правилом линтера.

**Почему прослойка, а не правка модуля.** Модуль `access` не знает
о текущем запросе и cookie: тот же модуль работает в процессе фоновых
задач, где браузера нет. Смешение уже ломало запуск процесса задач
на шаге 2.4.

**Режим только отнимает права и никогда не добавляет.** Поэтому его
состояние можно держать в cookie: даже подделанная, она даёт человеку
меньше возможностей, а не больше. Это же означает, что режим не является
защитой — защита остаётся в `requirePermission`, и она смотрит
на настоящие права, а не на маскированные.

### Что защищено дополнительно

| Мера                                          | От чего                                            |
| --------------------------------------------- | -------------------------------------------------- |
| Ключи сессий хранятся хешированными           | Утечка базы не даёт войти под чужим аккаунтом      |
| IP-адреса хранятся хешированными              | Адрес — персональные данные                        |
| Cookie с префиксом `__Host-`                  | Подмена cookie с поддомена, работа по HTTP         |
| Секреты вырезаются из журнала автоматически   | Токен, случайно записанный в журнал целым объектом |
| Ограничение частоты запросов                  | Перебор при входе                                  |
| `server-only` на серверных модулях            | Секреты, случайно затянутые в код браузера         |
| Разрешение на каждое воспроизведение          | Просмотр после окончания подписки                  |
| Ключ файла в хранилище не попадает в разметку | Прямое скачивание в обход проверки подписки        |
| Водяной знак с именем участника на видео      | Пересылка записи в чужой чат                       |

## 7. Настройки

Три вида, разделённые физически:

| Вид                 | Где                           | Пример                                     |
| ------------------- | ----------------------------- | ------------------------------------------ |
| Секретные серверные | `shared/config/env.server.ts` | токен бота, подключение к базе             |
| Публичные           | `shared/config/env.client.ts` | адрес платформы                            |
| Продуктовые         | `shared/config/app.config.ts` | льготный период 7 дней, размер страницы 24 |

Переменные окружения проверяются **при запуске**. Приложение с неверными
настройками не запускается, а на боевом сервере ещё и завершает процесс —
чтобы система развёртывания увидела неудачу и оставила работать предыдущую
версию.

Правила, которые нельзя нарушить на боевом сервере: проверка входа включена,
адрес по `https`, подключение к базе задано.

## 8. Ошибки и наблюдаемость

Ошибки делятся на два вида:

| Вид               | Примеры                                    | Что происходит                                               |
| ----------------- | ------------------------------------------ | ------------------------------------------------------------ |
| Ожидаемые         | «не найдено», «нет прав», «ошибка в форме» | Одна строка в журнале, понятное сообщение человеку           |
| Настоящие поломки | база не отвечает, сбой видеохостинга       | Стек в журнале, отправка в Sentry, код происшествия человеку |

Без такого разделения журнал за неделю заполняется шумом, настоящие поломки
в нём тонут, и на оповещения перестают смотреть.

Журнал структурный, с идентификатором запроса: по одному коду из сообщения
об ошибке видно всю цепочку событий. Секреты и персональные данные вырезаются
автоматически.

## 9. Фоновые задачи

Отдельный процесс (`pnpm worker`), использующий те же модули, что и сайт.
Очередь живёт в той же PostgreSQL — без отдельного сервиса.

Почему отдельный процесс: перезапуск сайта не обрывает задачи, перезагрузка
кода при разработке не запускает их заново, тяжёлая задача не замедляет
открытие страниц.

Расписания собраны в `src/worker/schedules.ts` — чтобы через полгода
можно было ответить на вопрос «что и когда у нас запускается». Сейчас
там уборка сессий, оборванных загрузок и журнала действий, закрытие
истёкшего доступа и ночная сверка подписок с Telegram.

⚠️ Процесс задач запускается с условием разрешения модулей `react-server`:
без него защита `server-only` ломает запуск вне Next.js.

## 9а. Слой Telegram

Всё общение с мессенджером собрано в `src/shared/telegram/`. Это
инфраструктура: она умеет разговаривать с Telegram, но ничего не знает
ни об участниках клуба, ни о подписках. Решения принимают модули
`identity` (чей это Telegram) и `subscription` (есть ли доступ).

| Файл            | Отвечает за                                                  |
| --------------- | ------------------------------------------------------------ |
| `verify.ts`     | Проверка подписи данных входа — виджет (выключен) и Mini App |
| `client.ts`     | Обращения к Bot API по сети. Адрес — `TELEGRAM_API_BASE_URL` |
| `membership.ts` | Толкование статуса человека в канале                         |
| `types.ts`      | Типы Bot API — только используемые поля                      |

### Почему проверка подписи вынесена в чистые функции

`verify.ts` не зависит ни от настроек, ни от базы, ни от журнала: токен бота
приходит аргументом. Это единственное место, отделяющее закрытую платформу
от входа под чужим именем, поэтому оно должно быть полностью покрыто тестами
без запуска приложения. Тестов там больше, чем кода.

Две вещи, которые легко упустить и которые уже закрыты:

- **Данные входа живут 5 минут.** Подпись Telegram сама по себе не истекает —
  перехваченный ответ виджета годен вечно. Ограничение по времени и есть
  защита от повторного использования.
- **Подписи сравниваются за постоянное время.** Иначе по времени ответа
  подпись подбирается посимвольно.

### Два разных вида отказа Telegram

Различие принципиально для политики fail-open:

| Что случилось                                           | Как выглядит в коде    | Что делаем                              |
| ------------------------------------------------------- | ---------------------- | --------------------------------------- |
| Сеть, таймаут, блокировка, ошибка 5xx                   | `upstream_unavailable` | Верим последнему известному состоянию   |
| Telegram ответил отказом (нет в канале, бот лишён прав) | `TelegramApiError`     | Состояние достоверно, действуем по нему |

Молчание мессенджера никогда не означает «подписка кончилась».

### ⚠️ `chat_member` не приходит по умолчанию

Telegram присылает события о составе канала только если тип явно перечислен
в `allowed_updates` при регистрации вебхука. Отказ молчаливый: ни ошибки,
ни записи в журнале — просто подписки перестают обновляться.

Поэтому список задан константой `REQUIRED_UPDATE_TYPES` в коде и используется
скриптом регистрации, а не вводится руками при настройке сервера.

### Промежуточный сервер

Адрес Bot API не зашит в код: `TELEGRAM_API_BASE_URL`, по умолчанию
`https://api.telegram.org`. Если сервер платформы не достучится до Telegram
из страны размещения, запросы пойдут через промежуточный сервер за рубежом,
который только передаёт их дальше и ничего не хранит. Настройка — в OPERATIONS.

## 9б. Вход и сессии

Модуль `identity` отвечает на вопрос «кто передо мной». На вопрос
«что ему можно» отвечает `access`, на «оплачено ли» — `subscription`.

### Как устроена сессия

В cookie лежит случайная строка на 256 бит. В базе — только её хеш,
посчитанный с секретом приложения. Из хеша строку не восстановить,
поэтому утечка базы не даёт войти под чужим именем.

Проверка на каждый запрос стоит один индексный запрос к базе. Взамен
получаем мгновенный отзыв доступа и список устройств в профиле,
который получается сам собой (ADR-0003).

| Свойство               | Значение  | Почему так                                     |
| ---------------------- | --------- | ---------------------------------------------- |
| Срок жизни             | 90 дней   | Человек не должен входить заново каждую неделю |
| Продление              | раз в час | Срок сдвигается на 90 дней — точность не нужна |
| Устройств одновременно | 3         | Мера против раздачи аккаунта (PRD v0.2 §2.1)   |
| Уборка мёртвых записей | 30 дней   | Хватает разобрать жалобу «меня разлогинило»    |

**Ротации ключа нет.** Она решает проблему JWT, который нельзя отозвать.
Серверную сессию мы отзываем мгновенно, поэтому ротация не даёт ничего,
а гонки между вкладками браузера создаёт.

**Кэша сессии с временем жизни нет.** Он означал бы, что закрытая сессия
ещё полминуты работает, — и главное преимущество модели пропало бы.
Вместо этого результат запоминается в пределах одной отрисовки страницы:
сколько бы компонентов ни спросили «кто вошёл», запрос будет один.

### Путь входа

Вход по коду на почту (ADR-0030). Пароля нет.

```
Страница входа: почта
   → ограничение частоты по адресу запроса и по почте
   → код из 6 цифр: в базу — хеш, в письмо — сам код (код стоит в теме)
Страница входа: код
   → попытка засчитывается до сравнения, на пятой код сгорает
   → код гасится атомарно: одним кодом одна сессия
   → участник найден по почте или создан (первый вход и есть регистрация)
   → открывается сессия, cookie уходит в браузер
   → куда дальше — решает sign-in-destination.ts:
       нет Telegram и нет доступа → /auth/connect (подключить Telegram)
       новичок                    → знакомство
       остальные                  → туда, куда шли
```

| Файл                     | Отвечает за                                     |
| ------------------------ | ----------------------------------------------- |
| `email-code-policy.ts`   | Правила кодов — чистые функции, покрыты тестами |
| `email-login.ts`         | Запрос кода и вход по нему                      |
| `email-login-repository` | Запросы к кодам и аккаунтам по почте            |
| `email-templates.ts`     | Текст письма                                    |
| `sign-in-destination.ts` | Куда вести после входа — чистая функция         |
| `owner-bootstrap.ts`     | Роль владельца тому, чья почта в `OWNER_EMAIL`  |

Действия входа (`app/(public)/_actions/auth.ts`) живут в слое приложения:
куда вести человека, зависит и от `identity`, и от `subscription`.

Письма уходят через интерфейс `EmailSender` (`shared/email`): `console`
печатает письмо в журнал для разработки, `smtp` отправляет по-настоящему.
На боевом сервере `console` запрещён проверкой настроек.

На `localhost` остаётся служебный вход `/dev/login`, существующий только
при `NODE_ENV=development`.

### Подключение Telegram

Нужно один раз, чтобы платформа узнала, чей Telegram проверять на членство
в закрытом канале.

```
/auth/connect → ссылка t.me/бот?start=ключ (ключ одноразовый, 15 минут)
   → человек нажимает «Старт» → Telegram присылает /start ключ на вебхук
   → identity: ключ → аккаунт, отправитель → Telegram; привязка
   → subscription: членство в канале проверяется сразу (fail-open)
   → бот отвечает «готово», страница на сайте сама ведёт дальше
```

Связывает два модуля обработчик вебхука (`api/telegram/webhook/_lib`),
а не один из модулей: ни `identity`, ни `subscription` друг друга не вызывают.
Чужой Telegram не переносится на другой аккаунт молча — бот объясняет,
что делать.

### Вход через виджет Telegram — выключен

Прежний путь входа сохранён в `telegram-login.ts` и `/auth/telegram`
и включается переключателем `TELEGRAM_LOGIN_ENABLED=true`. Выключен,
потому что виджет загружается с сайта Telegram в браузере участника
и не работает там, где сайт заблокирован. При выключенном переключателе
закрыт и сам адрес, а не только кнопка.

### Открытое перенаправление

Адрес возврата после входа приходит параметром. Принимать его как есть
нельзя: ссылка `/?next=https://похожий-сайт.ru` уведёт человека на чужую
страницу сразу после успешного входа, и выглядеть это будет нормально —
он ведь только что вошёл на настоящем сайте.

Проверка — в `identity/return-to.ts`, покрыта тестами. Отсекаются также
формы `//сайт` и `/\сайт`: они выглядят внутренними путями, но уводят наружу.

## 10. Смена внешних поставщиков

Три места, где мы заранее защищаемся от привязки к поставщику:

```
VideoProvider          Kinescope | none
StorageProvider        S3-совместимое хранилище
NotificationChannel    Telegram | почта | веб
EmailSender            smtp | console
```

Значение `none` у видеохостинга — не заглушка ради полноты: оно позволяет
поднять проект и увидеть все экраны, не заводя учётной записи и не платя.
Разработчик, впервые открывший репозиторий, не должен упираться
в «сначала зарегистрируйтесь на видеохостинге».

Приложение работает с интерфейсом, конкретная реализация выбирается
переменной окружения. Смена видеохостинга — новый файл и строка в настройках,
а не переделка контента.

Это прямо закрывает риск «оплата зарубежного сервиса из России перестала
проходить».

Глобального хранилища нет и пока не нужно. Режим репетиции, ради
которого оно предполагалось, обошёлся без него: отрезок, темп и скорость
не покидают одно поддерево и не переживают уход со страницы (шаг 10.5,
[ADR-0027](adr/0027-rehearsal-mode.md)). Фильтры в адресной строке дают
бесплатно работающую кнопку «Назад», возможность отправить ссылку
на отфильтрованный каталог и сохранение состояния при перезагрузке.

## Связь плеера с соседями по странице (шаг 10.2)

Заметке нужны две вещи от плеера: узнать текущее место записи и
перемотать к сохранённому. Плеер и заметки — соседи по странице, но
не родственники: ни один не содержит другого.

Передать это свойствами нельзя — страница серверная, а текущее место
ролика существует только в браузере. Глобального хранилища в проекте
нет, и заводить его ради одной кнопки было бы слишком.

Решение — контекст с одной ссылкой (`app/app/_components/playback-context.tsx`):

```
PlaybackProvider
├─ VideoPlayer     → при создании сообщает о себе: getCurrentTime, seekTo
└─ NotesPanel      → спрашивает управление, когда человек нажал
```

**Ссылка, а не состояние:** управление плеером меняется дважды за жизнь
страницы, и держать это в состоянии значило бы перерисовывать поддерево
в момент, когда плеер только начал загружаться.

**Плеера может не быть.** Разбор без записи, урок без видео, участник
без подписки — заметки при этом остаются, просто без кнопки «отметить
место». Поэтому всё необязательное: `null` здесь норма, а не ошибка.

## Общий поиск (шаг 10.4)

Одна строка ищет по четырём разделам сразу. Устроено так же, как всё
остальное, что пересекает границы модулей:

```
shared/search/query.ts        разбор запроса: раскладка, транслитерация
   ↓
модули: search-repository.ts  свой запрос, свой индекс, свой вектор
   ↓
app/_lib/search.ts            сведение результатов в группы
```

Ни один модуль не узнал о существовании других. Разбор запроса переехал
в общий слой из модуля разборов — исправление раскладки не бизнес-правило
разборов, а инструмент.

**Результаты не смешиваются в общий список.** Ранги из четырёх запросов
несопоставимы: `ts_rank_cd` считает вес внутри своего вектора, а векторы
у разборов и эфиров разной формы. Общая сортировка по ним выглядела бы
случайной перетасовкой. [ADR-0026](adr/0026-global-search.md).
