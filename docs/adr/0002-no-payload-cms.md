# ADR-0002. Отказ от Payload CMS

**Статус:** принято · **Дата:** 2026-08 · **Отменяет:** рекомендацию из PRD v0.2 §5

## Контекст

В PRD v0.2 Payload CMS был рекомендован ради экономии примерно пяти недель
на разработке админки. Позже в PRD v0.3 было принято продуктовое решение:
отдельной админки не существует, права — свойство обычного аккаунта,
куратор правит контент прямо на странице, которую видит.

Эти два решения несовместимы.

## Варианты

**А. Payload CMS.** Отдельная панель на `/admin` со своим входом,
своей таблицей пользователей, своей моделью доступа и своим внешним видом.

**Б. Собственные экраны управления внутри платформы.**

## Решение

Вариант Б. Payload не используется.

## Обоснование

С Payload пришлось бы:

1. Связывать вход через Telegram с внутренним пользователем Payload —
   второй источник истины об аккаунте.
2. Перекладывать модель прав из v0.3 (роль + персональные разрешения и запреты
   - область действия own/all) на систему доступа Payload, устроенную иначе.
3. Всё равно писать вручную: страницу песни с контекстной кнопкой правки,
   редактор разбора с частями, экран «Миграция», экран «Команда»,
   режим «смотреть как участник».
4. Держать в одной базе две системы миграций — Payload и Drizzle.

После вычета всего этого экономия сводится к трём простым экранам:
новости, кураторы, настройки.

Вместо CMS на шаге F5 создаётся набор переиспользуемых компонентов
(таблица с фильтрами, форма из описания полей, выбор медиафайла,
список с перетаскиванием, автосохранение). С ними каждый экран управления
собирается за 1–2 дня.

## Последствия

- **Срок проекта увеличивается примерно на 2–3 недели.** Это принято осознанно.
- Одна кодовая база, один дизайн, одна модель прав.
- Кураторы не переключаются между двумя разными интерфейсами.
- Полный контроль над UX редактора — критично, потому что скорость публикации
  разбора (цель: ≤10 минут) определяет, будет ли платформа наполняться.
