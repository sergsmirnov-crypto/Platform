# База данных

PostgreSQL. Работа с ней — через Drizzle ORM.

---

## Как это устроено

Таблицы описаны на TypeScript и живут внутри своих модулей:

```
src/modules/identity/schema.ts      пользователи, способы входа, сессии
src/modules/access/schema.ts        роли и права
src/modules/subscription/schema.ts  подписки и события Telegram
src/modules/media/schema.ts         реестр видео и файлов
src/modules/audit/schema.ts         журнал действий, настройки, уведомления
```

Из этих описаний создаются **миграции** — файлы с SQL-командами в папке
`drizzle/`. Они хранятся в git, применяются по порядку и **никогда
не изменяются задним числом**: если что-то пошло не так, создаётся новая
миграция, а не правится старая. Иначе на разных серверах база окажется
в разном состоянии, и найти причину будет невозможно.

---

## Команды

| Команда            | Что делает                                              |
| ------------------ | ------------------------------------------------------- |
| `pnpm db:generate` | Создать миграцию после изменения таблиц                 |
| `pnpm db:migrate`  | Применить миграции к базе                               |
| `pnpm db:seed`     | Заполнить справочники: права, роли, владелец            |
| `pnpm db:studio`   | Открыть базу в браузере и посмотреть данные             |
| `pnpm db:reset`    | ⚠️ Стереть всё и создать заново (только при разработке) |

**Порядок при изменении таблиц:** правим `schema.ts` → `pnpm db:generate` →
смотрим получившийся SQL → `pnpm db:migrate`.

`db:migrate` и `db:seed` можно запускать сколько угодно раз: применённые
миграции пропускаются, существующие справочники обновляются, а не дублируются.

## Соглашения

Зафиксированы один раз и действуют для всех таблиц.

| Правило                                              | Почему                                                                                                                                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Первичный ключ — UUID версии 7                       | Содержит внутри метку времени, поэтому записи ложатся в индекс по порядку. Обычный случайный UUID разрастается в индексе. Значение вычисляет приложение: встроенная функция появилась только в PostgreSQL 18 |
| Все даты — `timestamptz`, в UTC                      | Перевод в часовой пояс — только на экране. Иначе участник из Сербии увидит чужое время                                                                                                                       |
| Имена — `snake_case`, таблицы во множественном числе | Общепринято в PostgreSQL                                                                                                                                                                                     |
| `created_at` и `updated_at` — везде                  | Без них невозможно разобрать ни одну спорную ситуацию                                                                                                                                                        |
| `deleted_at` вместо удаления — там, где есть связи   | Удалённый участник не должен ломать историю подписок и авторство разборов                                                                                                                                    |
| Каскадное удаление — только внутри одной сущности    | Удаление песни убирает её варианты и части. Между разными сущностями — запрет, чтобы случайное удаление не унесло половину базы                                                                              |
| IP-адреса хранятся хешированными                     | Адрес — персональные данные                                                                                                                                                                                  |
| Ключи сессий хранятся хешированными                  | Если содержимое базы утечёт, войти по этим данным будет нельзя                                                                                                                                               |

## Что уже создано

Миграция `0000_init_identity_access` — 16 таблиц.

### Пользователи и вход

| Таблица           | Назначение                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| `users`           | Профиль участника: имя, город, стаж игры, уровень, цели, фотография                              |
| `auth_identities` | Способы входа. Вынесены отдельно, чтобы Telegram не был единственной дверью в оплаченный контент |
| `sessions`        | Активные устройства. Хранится хеш ключа, не сам ключ                                             |

Таблицы входа по почте и подключения Telegram — в разделе
«Вход по почте и подключение Telegram» ниже.

**Про фотографию.** В `users.avatar_id` лежит идентификатор загруженного
снимка, а не его адрес. Имена файлов всех размеров собираются из него,
адрес — уже из настроек хранилища. Готовая ссылка в базе означала бы,
что смена сети доставки требует правки строк у каждого участника.
Пусто — фотографии нет, интерфейс показывает силуэт.

**Про удаление аккаунта.** Строка участника не удаляется физически:
на неё ссылаются журнал действий и история подписки. Вместо этого личные
поля затираются, `deleted_at` заполняется, а строки в `auth_identities`
удаляются — войти под таким аккаунтом невозможно, а идентификатор
Telegram освобождается. Подробнее — [ADR-0011](adr/0011-account-deletion.md).

### Роли и права

| Таблица            | Назначение                                                 |
| ------------------ | ---------------------------------------------------------- |
| `permissions`      | Справочник всех прав платформы                             |
| `roles`            | Пресеты: куратор, старший куратор, администратор, владелец |
| `role_permissions` | Какие права входят в роль                                  |
| `user_roles`       | Какие роли у человека                                      |
| `user_permissions` | Персональные исключения: точечно выдать или отнять право   |

Итоговые права считаются так:

```
права всех ролей человека
+ персональные разрешения
− персональные запреты
─────────────────────────
= что человек реально может
```

Запрет всегда сильнее разрешения. У прав на редактирование есть область
действия: `own` (только свой контент) или `all` (любой).

Справочник прав и пресеты ролей описаны в коде и попадают в базу командой
`pnpm db:seed`:

```
src/modules/access/permissions.catalog.ts   33 права
src/modules/access/roles.catalog.ts         4 роли
```

Добавили право — допишите его в справочник и запустите `pnpm db:seed`.

### Медиа и системное

| Таблица         | Назначение                                                               |
| --------------- | ------------------------------------------------------------------------ |
| `media_assets`  | Реестр видео и файлов. Смена видеохостинга не требует переделки контента |
| `attachments`   | Привязка файла к содержимому: табы у песни, минусовка у варианта         |
| `audit_log`     | Кто, что и когда изменил                                                 |
| `app_settings`  | Настройки из интерфейса. Модуль `settings` (шаг 9.6.1)                   |
| `feature_flags` | Переключатели возможностей без перезапуска. Модуль `settings`            |
| `notifications` | Уведомления: создаются платформой, доставляются через Telegram           |

**Три поля `media_assets`, которые легко понять неправильно.**

- `external_id` — идентификатор у поставщика. Для видео это ключ ролика
  в Kinescope, для загруженного файла — **ключ объекта в хранилище**.
  Наружу не уходит никогда: участник получает подписанную ссылку.
- `processing_status` — `uploading` до тех пор, пока байты не доехали.
  Строка заводится ДО записи в хранилище, чтобы оборванная загрузка
  оставила след; такие строки старше суток убирает ночная задача
  `media.cleanup` ([ADR-0016](adr/0016-file-uploads.md)).
- `is_downloadable` — свойство файла, а не привязки. Тот же файл,
  приложенный в двух местах, не может скачиваться в одном и не
  скачиваться в другом: ссылка-то одна.

**Поисковый образ песни.** Колонка `songs.search_vector` — вычисляемая:
база пересобирает её сама при любом изменении названия, исполнителя,
альбома или описания. Заполнять её из приложения не нужно и нельзя.
Веса полей: название → A, исполнитель → B, альбом → C, описание → D.
Индекс GIN, а не GiST: читаем несравнимо чаще, чем пишем.

Рядом живёт расширение **`pg_trgm`** — оно даёт устойчивость к опечаткам
и подсказки «возможно, вы имели в виду». Его создание требует прав
суперпользователя базы: см. OPERATIONS.md §3 и
[ADR-0017](adr/0017-song-search.md).

### Курс и прогресс

| Таблица          | Отвечает за                                       |
| ---------------- | ------------------------------------------------- |
| `courses`        | Курс. Сегодня один, таблица заведена сразу        |
| `course_modules` | Модуль — глава курса                              |
| `lessons`        | Урок: видео, содержимое блоками, материалы        |
| `progress`       | Прохождение — общее для уроков, разборов и эфиров |

**Содержимое урока лежит в `jsonb` списком блоков** нашего формата,
не форматом стороннего редактора. Чтение всегда идёт через проверку:
у `jsonb` нет типа, и лежать там может запись прошлогодней версии
или правка руками. [ADR-0018](adr/0018-lesson-content-blocks.md).

**`progress` полиморфна и без внешнего ключа на объект.** Это плата
за главную кнопку платформы: «Продолжить» отвечает на вопрос «что
человек трогал последним» по всем видам содержимого одним запросом
по индексу. Отсутствие строки означает «не начато» — заранее строки
не заводятся. [ADR-0019](adr/0019-progress-model.md).

### Личная библиотека

| Таблица      | Отвечает за                                 |
| ------------ | ------------------------------------------- |
| `favorites`  | Что человек отложил на потом                |
| `user_notes` | Личные заметки с привязкой к моменту ролика |

**Отдельно от `progress`, хотя таблицы похожи.** Прогресс пишет плеер сам,
каждые несколько секунд; избранное — только человек, руками. Разный
источник записи и разный жизненный цикл. В общей таблице половина строк
существовала бы ради `position_sec`, половина — ради галочки, и каждый
запрос «что отложено» начинался бы с отсеивания второй половины.

**Избранное привязано к песне, прогресс — к варианту разбора.** Это
единственное место в проекте, где похожие сущности сидят на разных
уровнях иерархии, и это намеренно: проходят конкретный уровень
конкретного куратора, а откладывают песню целиком. Иначе переход
с начального уровня на средний осыпал бы отложенное.

**Собственного идентификатора у строки нет** — только составной первичный
ключ `(user_id, entity_type, entity_id)`. «Отложить дважды» не событие,
а то же самое состояние, и вторую вставку запрещает база, а не
внимательность приложения. Внешнего ключа на объект нет по той же
причине, что у `progress`. [ADR-0023](adr/0023-favorites-model.md).

### Эфиры

| Таблица           | Отвечает за                                 |
| ----------------- | ------------------------------------------- |
| `streams`         | Эфир: и анонс, и запись — одна запись       |
| `stream_chapters` | Оглавление записи по таймкодам              |
| `stream_songs`    | Какие песни разбирали — связь в обе стороны |

**Одна таблица на анонс и запись.** Это один эфир на разных этапах
жизни; разделение означало бы переносить строку из таблицы в таблицу
в момент публикации видео.

**Состояние («идёт», «запись») в базе не хранится** — вычисляется
из поля `state`, времени начала и наличия видео. Записанное значение
устаревает молча: через час после эфира база утверждала бы, что он идёт.

**`status` и `state` — разные вещи.** `state` отвечает «что с эфиром
происходит», `status` — «видят ли его участники».

**Адреса модулей и уроков уникальны внутри родителя, а не глобально:**
«основы» может быть и в курсе гитары, и в будущем курсе укулеле.

**Почему `attachments` полиморфна.** Внешнего ключа на объект нет:
объектом может быть песня, вариант разбора, часть, урок, эфир или
новость. Колонка `pdf_asset_id` в каждой таблице ломается на втором
файле — у разбора бывают и PDF, и Guitar Pro, и минусовка, а иногда два
PDF для разных строёв. Подпись живёт на привязке, а не на файле: один
файл в разных местах может называться по-разному.

### Разборы и метки

| Таблица                | Назначение                                                         |
| ---------------------- | ------------------------------------------------------------------ |
| `songs`                | Песня: исполнитель, строй, темп, тональность, состояние публикации |

**Главное про эту часть схемы.** Уровень сложности — это отдельная запись
(`arrangements`), а не колонка песни. Иначе не выразить два разбора одного
уровня от разных кураторов, «версию на акустике» рядом с электрической
и своего куратора у каждого уровня. Уникальности по паре «песня + уровень»
намеренно нет. Подробно — [ADR-0012](adr/0012-arrangements-model.md).

**Про общие перечисления.** Состояние публикации и список видов
содержимого лежат в `src/shared/db/enums.ts`: они одинаковы у разборов,
уроков, эфиров и новостей. Файл подключён к настройке миграций отдельным
путём — без этого инструмент видит ссылки на такой тип в колонках,
но не видит его объявления, и молча выпускает миграцию, которая падает
при применении.

## Правило работы с данными в коде

Запросы к базе пишутся **только** в файлах `repository.ts` внутри модулей.
Компоненты и обработчики обращаются к данным через сервисы модуля.

Причина простая: когда запросы разбросаны по всему проекту, изменение одной
таблицы превращается в поиск по сотне файлов, а проверки прав неизбежно
где-нибудь забываются.

## Карточки кураторов (шаг 8.1)

```
curator_profiles
  user_id        uuid PK FK → users     — карточка расширяет участника
  slug           text UNIQUE            — адрес страницы, не меняется
  headline       text                   — «Фингерстайл и акустика»
  bio            text
  teaches        text[]
  influences     text[]
  gear           text[]
  teaching_since int                    — год, а не стаж числом
  is_public      bool                   — показана ли карточка
  order_index    int                    — порядок задаётся руками
```

Первичный ключ — идентификатор участника: куратор не заводится заново,
у него уже есть профиль, прогресс и подписка. Отдельная таблица нужна
потому, что этих полей десяток, а у ста пятидесяти участников из ста
пятидесяти они пустые.

`is_public` — скрытие, а не удаление: куратор уходит в отпуск, его
разборы остаются, связь «кто вёл» не рвётся.

`teaching_since` хранит год, а не стаж: записанное число «двенадцать лет»
устаревает молча и через год врёт.

## Видимость визитки (шаг 8.2)

```
users.profile_visibility  enum(private, club)  default 'private'
```

`private` по умолчанию: согласие показывать город и рассказ о себе нельзя
получить задним числом настройкой по умолчанию. `club` означает «видно
участникам клуба» — публичной витрины у визиток нет, платформа закрыта
целиком.

Условие видимости определено ровно один раз, в `modules/club/members-repository.ts`,
и стоит в `where` каждого запроса о визитках. Проверка на стороне страницы
была бы слабее: страницу однажды перепишут, а условие в запросе останется.

Прогресс, подписка, заметки и дата последнего входа в эти запросы
не входят вовсе — показать их нельзя даже по ошибке.

## Блокировка участника (шаг 9.1)

```
users.blocked_at      timestamptz         — пусто означает «не заблокирован»
users.blocked_reason  text                — обязательна при блокировке
users.blocked_by      uuid FK → users     — on delete set null
```

**Блокировка — это не отсутствие подписки.** Подписка отвечает на вопрос
«оплачено ли», блокировка — «пускать ли вообще». Вышедший из платного канала
теряет доступ к урокам, но остаётся участником: у него есть профиль, прогресс
и возможность вернуться, оплатив снова. Заблокированный не попадает
на платформу вовсе.

Причина хранится рядом с датой не для порядка: через полгода «а почему он
заблокирован» спрашивает уже другой человек, и ответ должен находиться,
а не вспоминаться.

Ссылка `blocked_by` обнуляется при удалении аккаунта администратора —
причина и дата при этом остаются.

**Где проверяется.** В двух местах, и оба обязательны:

| Место                    | Что закрывает                          |
| ------------------------ | -------------------------------------- |
| `findSessionByTokenHash` | Действующие сессии на всех устройствах |
| `signInWithTelegram`     | Повторный вход через виджет            |

Первая проверка стоит в самом низком слое намеренно. Блокировка закрывает
сессии, но это две операции, и между ними возможен сбой; условие в запросе
переживёт и сбой, и того, кто однажды напишет отзыв блокировки без закрытия
сессий.

## Роли и исключения в работе (шаг 9.2)

Таблицы созданы на Этапе 1, миграция шагу не понадобилась. Стоит знать
два соглашения, принятых при их использовании:

**Роль у человека одна.** Модель допускает несколько (`user_roles` —
связь многие-ко-многим), но интерфейс выбирает роль переключателем
и заменяет прежнюю. Несколько ролей завести из интерфейса нельзя:
для точечных отличий существуют исключения, а два пресета на одном
человеке — источник вопросов «откуда у него это право».

**Область действия имеет смысл только у выданного права.** В записи
с `effect = 'deny'` поле `scope` всегда пустое: запрет снимает право
целиком, независимо от области, — так устроено вычисление итоговых прав.

**Бессмысленные записи не считаются отклонением.** Запрет права, которого
роль и так не даёт, хранится, но в пометке «+2 −1» не участвует: иначе
человек видел бы пометку об отклонении там, где ничего не изменилось.

## Уведомления Telegram и сверка (шаг 9.3)

Таблицы созданы на Этапе 2, миграция не понадобилась. Начали
использоваться две из них:

**`telegram_updates` — защита от повторов, а не архив.** Telegram
повторяет доставку, пока не получит ответ 200, и однажды повторит уже
обработанное. Уведомление занимается по `update_id` до ответа: повтор
просто не проходит дальше. Записи старше месяца убираются — хранить
их дольше незачем.

Поле `status` показывает, чем кончилась обработка: `processed`,
`ignored` (не про наш канал), `failed`. Последнее — то, что стоит
смотреть при разборе «почему у человека не открылся доступ».

**`channel_memberships` наполняется из двух источников.** Уведомление
проставляет `last_event_at`, сверка — `last_verified_at`. Разделение
позволяет отличить «мы знаем это, потому что нам сказали» от «мы это
проверили сами».

**`entitlements.verification_state`** переходит в `tg_unreachable`,
когда сверка не смогла достучаться до Telegram. Доступ при этом
не отбирается: молчание мессенджера никогда не означает «подписка
кончилась».

## Новости клуба и реакции (ADR-0032)

Миграция `0019_club_feed_reactions`.

**`news_posts` получила три колонки:**

| Колонка          | Что хранит                                                        |
| ---------------- | ----------------------------------------------------------------- |
| `kind`           | `news`, `digest`, `announcement`, `greeting`; по умолчанию `news` |
| `pinned_until`   | До какого момента закреплено; пусто — пока не снимут              |
| `discussion_url` | Ссылка на обсуждение в Telegram, только `https://t.me/…`          |

Закреплён пост, если `is_pinned` и срок не вышел. Порядок ленты

**`reactions` — одна реакция от человека на объект.**

| Колонка       | Что хранит                                                   |
| ------------- | ------------------------------------------------------------ |
| `target_type` | К чему реакция: сегодня только `news_post`                   |

| `user_id`     | Кто поставил                                                 |
| `emoji`       | Какая реакция — текстом; набор задан в коде                  |

Первичный ключ — `(target_type, target_id, user_id)`: вторая реакция

## Подписки в Toolsy (ADR-0031)

Миграция `0018_toolsy_subscriptions`.

**`toolsy_subscriptions` — сырой факт от сервиса оплаты.** Устроена как
`channel_memberships` и по той же причине: ключ — подписка Toolsy
и идентификатор Telegram, а не участник платформы. Человек мог оплатить,
не подключив Telegram, — факт учтётся, когда подключит.

| Колонка             | Что хранит                                                                       |
| ------------------- | -------------------------------------------------------------------------------- |
| `id`                | Идентификатор подписки в Toolsy                                                  |
| `telegram_id`       | Telegram ID человека, как его знает Toolsy                                       |
| `status`            | `active`, `delayed`, `expired`, `canceled`; `missing` — Toolsy подписку не нашёл |
| `expires_at`        | Конец оплаченного периода. Только для справки: доступ по нему не закрывается     |
| `product_id`        | Продукт Toolsy — для отсева чужих подписок (`TOOLSY_PRODUCT_ID`)                 |
| `source_updated_at` | Когда подписку меняли в самом Toolsy                                             |
| `last_verified_at`  | Когда сверялись с Toolsy напрямую                                                |

Доступ дают `active` и `delayed`. Строка на подписку, а не на человека:
у одного человека их может быть несколько.

**Устаревшее не затирает новое.** Запись обновляется, только если
`source_updated_at` пришедших сведений не старше сохранённого.
Уведомления приходят не по порядку, и без этой проверки запоздавшее
«подписка активна» вернуло бы доступ отменившему.

**`entitlement_source` получил значение `toolsy`.** Записывается, когда
оплату подтверждает Toolsy; если подтверждают и Toolsy, и чат — тоже
`toolsy`. Существующие записи не менялись.

## Что читает экран подписок (шаг 9.4)

Новых таблиц нет. Стоит знать два соглашения:

**Участники без записи в `entitlements` на экране не показываются.**
Экран отвечает на вопрос «что с подписками», а человек, ни разу
не касавшийся подписки, ответа на него не содержит. Он есть в списке
участников.

**Отбор «требуют внимания»** собирает две разные беды в одну: тех, кого
не сверяли дольше двух суток, и тех, у кого `verification_state`
переключился в `tg_unreachable`. Разделять их незачем — действие в обоих
случаях одно: проверить, работает ли вебхук.

**Идентификатор `subscription_events.id` — `bigint`,** и он не переживает
передачу из серверного компонента в браузерный: JSON такого типа не знает.
Наружу он отдаётся строкой.

## Название объекта в журнале (шаг 9.6)

У `audit_log` появилась колонка **`entity_title`** — как объект назывался
**в момент действия**.

**Почему снимок, а не ссылка.** Разбор удаляют — строка из `songs`
исчезает, и восстановить название по идентификатору становится нечем.
Между тем «куда делся разбор Nothing Else Matters» — ровно тот вопрос,
ради которого журнал заведён (PRD v0.3 §6). Без снимка на экране остался
бы идентификатор, не значащий ни для кого ничего.

**Для участников сделано наоборот: имя берётся при чтении.** Строки людей
удаляются мягко, поэтому `users.display_name` доступен всегда — и,
в отличие от снимка, не устаревает после переименования. Соединение
делает `modules/audit/log-repository.ts`, обращаясь к таблице участников
напрямую: спросить об этом модуль `identity` нельзя, он сам пишет
в журнал, и получилось бы кольцо импортов.

Правило коротко:

| Что за объект                                              | Откуда берётся название |
| ---------------------------------------------------------- | ----------------------- |
| Участник (`entity_type = 'user'`)                          | При чтении, из `users`  |
| Всё остальное: разборы, эфиры, уроки, материалы, настройки | Снимок в `entity_title` |

**Записи, сделанные до этой миграции, останутся без названия** — колонка
необязательная, и на экране такая запись показывается как «без названия».
Задним числом заполнить её нечем, и терять историю ради этого не стоило.

**Индекс `audit_log_created_idx`** — по убыванию времени. Это единственный
порядок, в котором журнал листают.

**Записи старше года удаляются** ночной задачей `audit.cleanup` (3:45).
Срок задан в `app.config.ts` → `manage.logRetentionDays`.

## Заметки (шаг 10.2)

`user_notes` лежит в том же модуле, что и `favorites`, но привязана
к **варианту разбора**, а не к песне. Это не расхождение, а разная
природа: отложить — намерение про произведение, заметка привязана
к моменту конкретной записи. У среднего уровня запись другая, чем
у начального, и пометка про 2:14 к ней не относится.

`timecode_sec` необязателен: половина заметок про запись вообще
(«вернуться, когда выучу баррэ»).

**Заметка всегда личная.** Поля «видна всем» нет и не планируется:
смысл заметки в том, что человек пишет её для себя и в тех выражениях,
в каких думает. Обсуждение разбора — другая сущность с другим
жизненным циклом (комментарии, PRD v0.1 §12).

Два индекса на два разных вопроса: `(user_id, entity_type, entity_id)` —
заметки открытой записи, `(user_id, updated_at desc)` — страница
«Мои заметки».

⚠️ **Каждый запрос ограничен `user_id`, включая правку и удаление.**
Не «загрузить и сверить владельца», а условие прямо в запросе: забытая
сверка не видна ни в коде, ни в типах, а стоит чужой заметки.

## Уведомления (шаг 10.3)

`notifications` существует с Этапа 2 и до этого шага лежала в схеме
модуля `audit`. Переехала в собственный модуль; **миграции это
не потребовало** — имя таблицы и колонки не менялись, drizzle-kit
подтверждает отсутствие изменений в схеме. Тот же переезд, что
у настроек на шаге 9.6.1.

**Строка создаётся всегда, независимо от доставки.** Отправить сообщение
ботом и забыть — самый простой путь, и он ломает главный принцип:
платформа обязана работать при недоступном Telegram. `sent_at` отвечает
на вопрос «почему мне не пришло» без похода в логи, а лента показывает
историю тому, у кого мессенджер заблокирован.

**Заголовок и текст сохраняются целиком**, а не собираются при показе:
разбор переименуют, эфир отменят — уведомление обязано остаться тем,
что человек получил. `type` текстовый, а не ссылка на таблицу типов:
тип, которого в каталоге больше нет, должен остаться в истории
читаемым.

`notification_preferences` хранит **только отклонения** от значения
по умолчанию. Строка на каждый тип для каждого человека потребовала бы
миграции при появлении нового типа, а забытая вставка означала бы
человека, который молча не получает половину уведомлений. Пусто —
значит «как задумано». Тот же приём, что у персональных исключений
в правах.

Само `sent_at` служит очередью: неотправленные уведомления с доставкой
«сводкой» ночная задача собирает в одно сообщение.
[ADR-0025](adr/0025-notifications.md).

## Вход по почте и подключение Telegram (ADR-0030)

Миграция `0017_email_login_and_telegram_link`.

| Таблица                | Назначение                                                   |
| ---------------------- | ------------------------------------------------------------ |
| `email_login_codes`    | Одноразовые коды входа. Хранится хеш кода, не сам код        |
| `telegram_link_tokens` | Одноразовые ключи ссылки «Подключить Telegram». Хранится хеш |

**Способы входа в `auth_identities`.** Почта — строка с `provider = 'email'`
и адресом в `provider_user_id` (строчными буквами, без пробелов). Telegram —
строка с `provider = 'telegram'` и идентификатором Telegram. У почты
`is_primary = true`: это способ входа; Telegram подтверждает подписку.

**Новый уникальный индекс `(user_id, provider)`.** У человека не больше
одного способа входа каждого вида. Иначе вопрос «какой Telegram проверять
на подписку» перестал бы иметь ответ. Прежний индекс `(provider,
provider_user_id)` по-прежнему не даёт привязать один Telegram или одну
почту к двум людям. Отдельный индекс по `user_id` удалён: новый индекс
начинается с той же колонки и обслуживает те же запросы.

**Код не привязан к участнику.** Код запрашивают и те, у кого аккаунта
ещё нет: аккаунт создаётся только после успешного ввода. Поэтому ключ
поиска кода — адрес почты, а не `user_id`.

**В хеш кода входит идентификатор строки.** Код из одного письма нельзя
предъявить к другой записи, даже если цифры совпали.

**Действует только последний код адреса.** При выдаче нового кода прежние
гасятся (`consumed_at`) в той же транзакции.

**Уборка.** Ночная задача `session-cleanup` удаляет коды и ключи,
истёкшие или использованные больше суток назад.

## Правило: даты в «сырых» кусках SQL

В обычных условиях — `eq`, `lt`, `gt` по колонке — драйвер знает тип
колонки и сам превращает `Date` в понятное PostgreSQL значение. Внутри
выражения, написанного строкой, знать этого неоткуда:

```ts
// НЕЛЬЗЯ: драйвер получит объект Date и упадёт с сообщением
// «string argument must be of type string»
sql`${songs.publishedAt} >= ${since}`

// НУЖНО
import { timestampParam } from '@/shared/db'
sql`${songs.publishedAt} >= ${timestampParam(since)}`
```

Ошибка коварна тем, что её не видит ничто из автоматических проверок:
TypeScript считает такой код нормальным, тесты не обращаются к базе,
линтер тут ни при чём. Ломается только живая страница у пользователя —
именно так и случилось с экраном `/app/manage`.
